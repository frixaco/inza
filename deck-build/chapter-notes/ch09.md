### Card Content Candidates

#### Concepts

- Errors are a fact of life in software.
- Rust has features for handling situations in which something goes wrong.
- In many cases, Rust requires code to acknowledge the possibility of an error and take some action before compilation succeeds.
- Requiring error acknowledgement makes programs more robust.
- Rust's compile-time error-handling requirements help ensure errors are discovered and handled before production deployment.
- Rust groups errors into two major categories: recoverable and unrecoverable.
- A recoverable error is a situation where the program can plausibly report the problem and retry or otherwise continue.
- The overview's recoverable-error example is a file not found error.
- An unrecoverable error is always a symptom of a bug according to this overview.
- The overview's unrecoverable-error example is trying to access a location beyond the end of an array.
- For unrecoverable errors, Rust's overview framing says the program should immediately stop.
- Many languages do not distinguish recoverable and unrecoverable errors in the same way.
- Many languages handle both categories with mechanisms such as exceptions.
- Rust does not have exceptions.
- Rust uses `Result<T, E>` for recoverable errors.
- Rust uses the `panic!` macro for unrecoverable errors.
- `panic!` stops execution when the program encounters an unrecoverable error.
- CH-09 first covers calling `panic!`.
- CH-09 then covers returning `Result<T, E>` values.
- CH-09 also covers considerations for deciding whether to recover from an error or stop execution.

### Card Content Candidates

#### Concepts

- `panic!` is Rust's macro for unrecoverable errors when there is nothing useful the program can do.
- There are two practical ways to cause a panic: take an action that makes code panic or explicitly call `panic!`.
- Accessing past the end of an array or vector is an example action that causes a panic.
- Explicitly calling `panic!` directly causes a panic.
- By default, a panic prints a failure message, unwinds, cleans up the stack, and quits.
- An environment variable can display the call stack for a panic.
- Displaying the call stack helps track down the source of the panic.
- Unwinding means Rust walks back up the stack and cleans up data from each function it encounters.
- Unwinding can do a lot of work.
- Aborting immediately ends the program without cleaning up.
- When aborting, memory used by the program is cleaned up by the operating system.
- Projects that need the smallest possible binary can switch from unwinding to aborting on panic.
- Panic aborting is configured by adding `panic = 'abort'` to the appropriate `[profile]` section in `Cargo.toml`.
- The section's release-mode abort example uses `[profile.release]`.
- A simple `panic!("crash and burn")` program panics at the macro call.
- Panic output includes the thread name, source file, line, column, and panic message.
- In the simple panic example, `src/main.rs:2:5` means line 2, column 5 of `src/main.rs`.
- The source location in panic output is where `panic!` is called.
- Sometimes the reported `panic!` location is in library code called by your code, not directly in your code.
- A backtrace can show the chain of function calls that led to the panic.
- Listing 9-1 attempts to access `v[99]` in a vector with three elements.
- Vector indexing starts at zero, so `v[99]` asks for the 100th element.
- `[]` indexing is supposed to return an element; when the index is invalid, there is no correct element to return.
- Rust panics on out-of-bounds indexing.
- In C, reading beyond a data structure can be undefined behavior.
- Reading beyond a data structure can produce memory that does not belong to that structure.
- Buffer overread can create security vulnerabilities if an attacker can manipulate an index to read unauthorized data.
- Rust stops execution and refuses to continue on invalid out-of-bounds reads to protect against this vulnerability class.
- Panic output for Listing 9-1 points to `src/main.rs:4:6` and reports the vector length and invalid index.
- The panic note says to set `RUST_BACKTRACE=1` to display a backtrace.
- A backtrace is a list of all functions called to reach the panic point.
- To read a Rust backtrace, start at the top and read until you see a file you wrote.
- The first frame mentioning a file you wrote is where the problem originated.
- Lines above that frame are code your code called.
- Lines below that frame are code that called your code.
- Backtrace lines can include core Rust code, standard library code, and crates your project uses.
- Setting `RUST_BACKTRACE` to any value except `0` enables a backtrace.
- Listing 9-2 uses `RUST_BACKTRACE=1 cargo run`.
- Backtrace output can differ by operating system and Rust version.
- Useful backtrace file/line details require debug symbols.
- Debug symbols are enabled by default for `cargo build` and `cargo run` without `--release`.
- In Listing 9-2, the frame for `panic::main` points to the project's `src/main.rs:4:6`.
- To fix Listing 9-1's panic, do not request an element beyond the vector's valid indexes.
- When future code panics, investigate what action was taken, what values caused it, and what the code should do instead.
- Choosing when to use or avoid `panic!` for error conditions is covered later in CH-09.


  ```console

  ```
- Verbose backtrace hint:
  ```text

  ```

#### Failure Modes

- Assuming `panic!` is for ordinary recoverable errors.
- Assuming panic always aborts immediately; default behavior is unwinding unless configured otherwise.
- Assuming unwinding and aborting both clean up stack data in the same way.
- Forgetting that aborting leaves cleanup to the operating system.
- Adding `panic = 'abort'` outside the relevant Cargo profile section.
- Reading only the top frame of a backtrace and stopping in core/std code without finding the first frame from your own project.
- Assuming exact backtrace output is stable across OS and Rust versions.
- Expecting detailed file/line backtraces from release builds without considering debug symbols.
- Treating Rust out-of-bounds indexing like C undefined behavior; Rust stops execution instead.
- Trying to fix Listing 9-1 by expecting a default element from `[]`; invalid `[]` indexing panics.
- Using this section for detailed guidelines on when to panic versus return `Result`; those are covered in `ch09-03-to-panic-or-not-to-panic`.

#### Comparisons

- Explicit panic vs panic caused by code action: direct `panic!` call vs invalid operation such as out-of-bounds indexing.
- Unwinding vs aborting: unwind walks the stack and cleans up data; abort ends immediately and leaves memory cleanup to the OS.
- Default panic behavior vs configured abort: default prints, unwinds, cleans up, and quits; configured abort skips unwinding to reduce work/binary size.
- Rust out-of-bounds access vs C out-of-bounds access: Rust panics and stops; C can produce undefined behavior and buffer overread.
- Panic location vs problem origin: panic output may name the direct panic call site; backtrace helps locate the chain back to your code.
- `RUST_BACKTRACE=1` vs `RUST_BACKTRACE=full`: normal backtrace vs verbose backtrace.
- Debug build vs release flag for backtraces: default `cargo run`/`cargo build` includes debug symbols; release may not have the same useful details.

### Card Content Candidates

#### Concepts

- Most errors are not serious enough to require stopping the whole program.
- A recoverable failure is one the program can interpret and respond to.
- A file-open failure because the file does not exist can be handled by creating the file instead of terminating.
- `Result` has two variants: `Ok` and `Err`.
- `Result<T, E>` uses generic type parameters.
- `T` is the success value type held inside `Ok`.
- `E` is the error value type held inside `Err`.
- `Result` can represent many different success and error type combinations.
- `File::open` returns `Result<T, E>` because opening a file can fail.
- For `File::open`, `T` is `std::fs::File`.
- For `File::open`, `E` is `std::io::Error`.
- A successful `File::open` returns an `Ok` containing a file handle.
- A failed `File::open` returns an `Err` containing information about what went wrong.
- `Result` and its `Ok` and `Err` variants are in the prelude, so match arms can write `Ok` and `Err` without `Result::`.
- A `match` on `Result` can return the inner success value from `Ok`.
- A `match` on `Result` can handle the `Err` value separately.
- Listing 9-4 panics for any `File::open` error.
- Listing 9-4 panic output includes an `Os` error with `kind: NotFound` when `hello.txt` is absent.
- Different error reasons often require different actions.
- `io::Error` has a `kind` method.
- `error.kind()` returns an `io::ErrorKind`.
- `io::ErrorKind` is an enum of possible I/O error categories.
- `ErrorKind::NotFound` represents a missing file.
- Listing 9-5 creates `hello.txt` when `File::open` fails with `NotFound`.
- Listing 9-5 panics for failure to create the file.
- Listing 9-5 panics for file-open errors other than `NotFound`.
- Nested `match` is useful but verbose.
- `Result<T, E>` has helper methods that can be more concise than `match`.
- `unwrap_or_else` with closures can express the Listing 9-5 behavior without explicit `match`.
- `unwrap` is a shortcut method similar to the Listing 9-4 panic-on-`Err` match.
- If a `Result` is `Ok`, `unwrap` returns the value inside `Ok`.
- If a `Result` is `Err`, `unwrap` calls `panic!`.
- The book's `unwrap` example panics on missing `hello.txt` with a default `Result::unwrap()` panic message.
- `expect` is like `unwrap` but lets the caller choose the panic message.
- `expect` returns the success value or calls `panic!` with the provided message.
- The book says most Rustaceans choose `expect` rather than `unwrap` in production-quality code when an operation is expected to always succeed.
- A good `expect` message conveys why the operation is expected to succeed.
- If an `expect` assumption is wrong, the message gives more debugging context.
- Propagating an error means returning it to the calling code instead of handling it inside the current function.
- Error propagation gives the caller more control.
- The caller may have more context or logic for deciding how to handle the error.
- Listing 9-6 manually propagates errors from reading a username file.
- `read_username_from_file` returns `Result<String, io::Error>`.
- In `Result<String, io::Error>`, `String` is the success value and `io::Error` is the error value.
- Listing 9-6 uses `io::Error` because both `File::open` and `read_to_string` return `io::Error` on failure.
- In Listing 9-6, `return Err(e)` returns early from the function when `File::open` fails.
- In Listing 9-6, a successful `read_to_string` returns `Ok(username)`.
- In Listing 9-6, a failed `read_to_string` returns `Err(e)` as the final expression.
- The calling code decides what to do with `Ok(username)` or `Err(io::Error)`.
- The caller might panic, use a default username, or look up a username elsewhere.
- `?` is a shortcut for common error propagation.
- `?` after a `Result` behaves almost like the manual `match` expressions in Listing 9-6.
- If a `Result` is `Ok`, `?` yields the value inside `Ok` and execution continues.
- If a `Result` is `Err`, `?` returns early from the whole function with the error.
- `?` applies error conversion through the `from` function from the `From` trait.
- `From::from` can convert the received error type into the current function's return error type.
- This conversion is useful when one return error type represents many possible failure causes.
- Listing 9-7 uses `?` after `File::open("hello.txt")` and after `read_to_string`.
- Listing 9-8 chains `read_to_string` directly after `File::open("hello.txt")?`.
- Listing 9-9 uses `fs::read_to_string`.
- `fs::read_to_string` opens the file, creates a new `String`, reads the file contents, puts the contents into the `String`, and returns it.
- `?` eliminates boilerplate and can make error propagation easier to read.
- `?` can only be used in functions whose return type is compatible with the value it is used on.
- The `?` operator early-returns a value from the current function.
- Listing 9-10 fails because `main` returns `()` but `File::open("hello.txt")?` would need to return a `Result` residual.
- E0277 says `?` can only be used in a function returning `Result`, `Option`, or another type implementing `FromResidual`.
- To fix an incompatible `?`, either change the function return type or handle the value with `match` or a `Result` method.
- `?` can be used with `Option<T>` in functions returning `Option`.
- For `Option`, `?` returns early with `None` when the value is `None`.
- For `Option`, `?` yields the value inside `Some` and execution continues when the value is `Some`.
- Listing 9-11 uses `?` in `last_char_of_first_line`.
- `last_char_of_first_line` returns `Option<char>`.
- In Listing 9-11, `text.lines().next()?` returns `None` early if there is no first line.
- If there is a first line, `?` extracts the `&str` line and the function calls `.chars().last()`.
- `chars().last()` returns an `Option<char>` because the first line might be empty.
- `?` can be used on `Result` in functions returning `Result`.
- `?` can be used on `Option` in functions returning `Option`.
- `?` does not automatically convert `Result` to `Option` or `Option` to `Result`.
- Use `ok` on `Result` or `ok_or` on `Option` to convert explicitly between these types.
- `main` usually returns `()`, but it can return `Result<(), E>`.
- Listing 9-12 changes `main` to return `Result<(), Box<dyn Error>>`.
- `Box<dyn Error>` is a trait object.
- At this point in the book, `Box<dyn Error>` can be read as "any kind of error."
- `main() -> Result<(), Box<dyn Error>>` allows `?` to return any `Err` value early in simple examples.
- `Box<dyn Error>` keeps the signature correct if later code in `main` returns other error types.
- When `main` returns `Result<(), E>`, returning `Ok(())` exits with code 0.
- When `main` returns `Result<(), E>`, returning `Err` exits with a nonzero value.
- Rust executable exit behavior is compatible with the C convention of 0 for success and nonzero for error.
- `main` may return any type implementing `std::process::Termination`.

#### Syntax Forms

- `Result` enum shape:
  ```rust
  enum Result<T, E> {
      Ok(T),
      Err(E),
  }
  ```
- Open a file and receive a `Result`:
  ```rust
  use std::fs::File;

  fn main() {
      let greeting_file_result = File::open("hello.txt");
  }
  ```
- Match on `Result`:
  ```rust
  let greeting_file = match greeting_file_result {
      Ok(file) => file,
      Err(error) => panic!("Problem opening the file: {error:?}"),
  };
  ```
- Match different `io::ErrorKind` values:
  ```rust
  use std::fs::File;
  use std::io::ErrorKind;

  fn main() {
      let greeting_file_result = File::open("hello.txt");

      let greeting_file = match greeting_file_result {
          Ok(file) => file,
          Err(error) => match error.kind() {
              ErrorKind::NotFound => match File::create("hello.txt") {
                  Ok(fc) => fc,
                  Err(e) => panic!("Problem creating the file: {e:?}"),
              },
              _ => {
                  panic!("Problem opening the file: {error:?}");
              }
          },
      };
  }
  ```
- `unwrap_or_else` alternative shown in the book:
  ```rust
  let greeting_file = File::open("hello.txt").unwrap_or_else(|error| {
      if error.kind() == ErrorKind::NotFound {
          File::create("hello.txt").unwrap_or_else(|error| {
              panic!("Problem creating the file: {error:?}");
          })
      } else {
          panic!("Problem opening the file: {error:?}");
      }
  });
  ```

### Card Content Candidates

#### Concepts

- When code panics, there is no way to recover in that execution path.
- Calling `panic!` for a failure decides that the situation is unrecoverable on behalf of the caller.
- Returning `Result` gives the calling code options.
- A caller that receives `Result` can attempt recovery or decide to panic itself.
- Returning `Result` is a good default when defining a function that might fail.
- Examples can use `unwrap` or similar panic-on-error code when robust error handling would distract from the concept being illustrated.
- In examples, `unwrap` is understood as a placeholder for application-specific error handling.
- During prototyping, `unwrap` and `expect` are useful because they leave clear markers for later robust handling.
- In tests, a failed helper call should usually fail the whole test.
- Because `panic!` marks a test as failed, `unwrap` and `expect` are appropriate in many tests.
- `expect` is appropriate when other logic ensures a `Result` will be `Ok` but the compiler cannot prove it.
- The operation can still fail in general even if failure is impossible in the current hardcoded context.
- A good `expect` message documents why an `Err` variant is not expected.
- The hardcoded IP address example can use `expect` because `"127.0.0.1"` is known to be valid.
- If the IP address string came from a user, the code should handle the `Result` robustly instead of relying on `expect`.
- A program is in a bad state when an assumption, guarantee, contract, or invariant has been broken.
- Bad-state inputs include invalid values, contradictory values, and missing values.
- The book's bad-state guideline adds that the bad state is unexpected, rather than likely occasional user input.
- The guideline also adds that later code needs to rely on not being in the bad state rather than checking at every step.
- The guideline also adds that there is no good way to encode the information in the types being used.
- If a caller passes nonsensical values, returning an error is best when the caller can reasonably choose what to do.
- If continuing after nonsensical values could be insecure or harmful, panicking may be better so the caller's bug is fixed during development.
- `panic!` is often appropriate when external code returns an invalid state that current code has no way to fix.
- Expected failures should usually return `Result` instead of panicking.
- Malformed parser input is an expected failure example that should return `Result`.
- An HTTP rate-limit status is an expected failure example that should return `Result`.
- Operations that could put a user at risk when called with invalid values should verify inputs first and panic if invalid.
- The standard library panics on out-of-bounds memory access because operating on invalid memory can create security vulnerabilities.
- Function contracts define requirements inputs must meet for behavior to be guaranteed.
- A contract violation indicates a caller-side bug, not an ordinary recoverable error.
- Panic conditions in public functions should be explained in API documentation.
- Rust's type system can move many checks from runtime into compile time.
- A parameter typed as a concrete value rather than `Option<T>` means callers cannot pass nothing.
- A parameter typed as `u32` cannot be negative.
- A custom type can encode a narrower validity rule that primitive types cannot express.
- The guessing game needs guesses between 1 and 100.
- Parsing a guess as `i32` plus an `if guess < 1 || guess > 100` check works, but the check must be repeated wherever the invariant matters.
- A dedicated `Guess` type centralizes the range check in its constructor.
- `Guess::new` only returns a `Guess` when the value is between 1 and 100.
- `Guess::new` panics outside the valid range because constructing an invalid `Guess` violates the type's contract.
- The `Guess` field is private so outside code cannot bypass validation by setting `value` directly.
- The public `value` method is a getter that exposes the stored `i32` without allowing mutation of the private field.
- Functions can accept or return `Guess` instead of `i32` to state the invariant in their signature.
- Once a function receives `Guess`, it does not need another range check for 1 through 100.
- `panic!` signals a state the program cannot handle and stops before proceeding with invalid or incorrect values.
- `Result` signals that an operation might fail in a recoverable way and requires callers to handle success or failure.

#### Failure Modes

- Panicking for ordinary expected failures, such as malformed input, when returning `Result` would let callers recover.
- Returning `Result` for every impossible contract violation even when continuing would be insecure or harmful.
- Using `expect` because success is merely hoped for, rather than because logic proves failure impossible in the current context.
- Writing an `expect` message that does not document the assumption behind the expected success.
- Copying the hardcoded-IP `expect` pattern to user-provided data.
- Treating examples and prototypes as proof that production code should freely use `unwrap`.
- Forgetting that tests panic to indicate failure, so `unwrap` and `expect` have a different tradeoff there.
- Repeating runtime range checks everywhere instead of encoding an invariant in a type when the invariant is critical.
- Making the `Guess` field public, which would allow callers to bypass `Guess::new`.
- Letting functions accept `i32` when they actually require a checked 1-through-100 value and could accept `Guess`.
- Failing to document public panic conditions for a constructor such as `Guess::new`.
- Treating `panic!` and `Result` as interchangeable; one stops execution while the other gives the caller a recoverable branch.

#### Comparisons

- `panic!` vs `Result`: `panic!` stops because the state cannot be handled; `Result` represents success or recoverable failure for caller-controlled handling.
- Library choosing `panic!` vs caller choosing to panic: panicking inside the library decides unrecoverability for callers; returning `Result` lets each caller decide.
- Example/prototype/test code vs production code: panic shortcuts can clarify examples, mark prototype gaps, or fail tests, but production code usually needs explicit policy.
- `unwrap` vs `expect` in this section: both can panic; `expect` can document the invariant that makes failure logically impossible.
- Hardcoded valid input vs user-provided input: hardcoded `"127.0.0.1"` supports an `expect` assumption; user input requires recoverable handling.
- Expected failure vs bad state: expected failure should usually return `Result`; a broken invariant or contract may justify `panic!`.
- Runtime check vs type-system guarantee: an `if` range check protects one code path; a checked type such as `Guess` carries the invariant across function boundaries.
- Primitive `i32` vs custom `Guess`: `i32` can represent invalid values; `Guess` is constructed only after validation.
- Public field vs private field plus getter: a public field can bypass validation; a private field forces construction through `Guess::new`.
- `Option<T>` parameter vs non-optional parameter: `Option<T>` requires handling present and absent cases; non-optional `T` means the caller must supply a value.
