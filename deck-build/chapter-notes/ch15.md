## Section: Smart Pointers

### Learning Objectives

- Learner can define a pointer as a variable containing a memory address that points at other data.
- Learner can explain why references are the most common kind of pointer in Rust.
- Learner can contrast references with smart pointers at the overview level.
- Learner can explain that references borrow data, while many smart pointers own the data they point to.
- Learner can identify `Deref` and `Drop` as traits commonly implemented by smart pointers.

- Learner can name the standard library smart pointers covered in CH-15 and the high-level use case for each.
- Learner can identify interior mutability and reference cycles as CH-15 topics.

### Card Content Candidates

#### Concepts

- A pointer is a general concept: a variable that contains an address in memory.
- A pointer's address refers to, or points at, other data.
- Rust references are indicated by `&`.
- A reference borrows the value it points to.
- References have no special capabilities beyond referring to data.
- References have no overhead.
- A smart pointer is a data structure that acts like a pointer.
- Smart pointers also have additional metadata or capabilities.
- Smart pointers are not unique to Rust; the source notes they originated in C++ and exist in other languages.
- Rust's standard library defines multiple smart pointers.
- Reference counting is one smart pointer pattern.
- A reference counting smart pointer enables data to have multiple owners.
- Reference counting tracks the number of owners.
- When no owners remain, a reference counting smart pointer can clean up the data.
- In Rust, references only borrow data.
- In many cases, smart pointers own the data they point to.
- Smart pointers are usually implemented using structs.
- Smart pointers commonly implement `Deref` and `Drop`.
- `Deref` allows an instance of a smart pointer struct to behave like a reference.
- `Deref` lets code work with either references or smart pointers.
- `Drop` lets a type customize code that runs when an instance goes out of scope.
- The smart pointer pattern is a common Rust design pattern.
- CH-15 does not cover every existing smart pointer.
- Libraries can define their own smart pointers.
- Rust programmers can write their own smart pointers.
- `Box<T>` allocates values on the heap.
- `Rc<T>` is a reference counting type for multiple ownership.
- `Ref<T>` and `RefMut<T>` are accessed through `RefCell<T>`.
- `RefCell<T>` enforces borrowing rules at runtime instead of compile time.
- Interior mutability is a pattern where an immutable type exposes an API for mutating an interior value.
- Reference cycles can leak memory.
- CH-15 also covers how to prevent reference-cycle leaks.

#### Syntax Forms

- Ordinary reference:

- Standard library smart pointer type names introduced by the overview:

- Smart pointer traits named by the overview:
  ```rust

  ```

#### Failure Modes

- Treating all pointers as owning values; references borrow, while many smart pointers own their pointed-to data.
- Treating all smart pointers as just references; smart pointers can carry metadata and additional capabilities.
- Assuming smart pointers are a single Rust-only type; the source describes a general pattern with many standard-library and library-defined examples.
- Treating compile-time borrow checking and `RefCell<T>` runtime borrow checking as the same mechanism.
- Assuming reference counting alone prevents every memory leak; CH-15 later covers reference cycles that can leak memory.

#### Comparisons

- Pointer vs reference: a pointer is the broad concept of an address-containing variable; a reference is Rust's common borrowing pointer form.
- Reference vs smart pointer: a reference only borrows and has no extra capabilities or overhead; a smart pointer acts like a pointer and adds metadata or capabilities.
- Borrowing reference vs owning smart pointer: references only borrow data; many smart pointers own the data they point to.
- Ordinary struct vs smart pointer struct: smart pointers are usually structs, but they commonly implement pointer-like behavior through `Deref` and cleanup behavior through `Drop`.
- Compile-time borrowing vs runtime borrowing: ordinary references are checked at compile time; `RefCell<T>` enforces borrowing rules at runtime.

### Card Content Candidates

#### Concepts

- `Box<T>` is the most straightforward smart pointer.
- Boxes store data on the heap instead of on the stack.
- The stack stores the pointer to the heap data.
- A box has no performance overhead other than storing its data on the heap instead of on the stack.
- Boxes have few extra capabilities compared with other smart pointers.
- Common use case 1: a type's size cannot be known at compile time, but the value is needed in a context requiring an exact size.
- Common use case 2: a large amount of data needs ownership transfer without copying the large data around on the stack.
- Common use case 3: owning a value by a trait it implements rather than by a specific concrete type; the source defers this to trait objects in Chapter 18.
- When large data is boxed, only the small pointer data is copied around on the stack during ownership transfer.
- The large heap data stays in one place when ownership of the box moves.
- `Box::new(5)` allocates the integer `5` on the heap and returns a box pointing to it.
- A boxed `i32` can be printed similarly to a stack-stored `i32` in the book's example.
- When a box goes out of scope, the box stored on the stack is deallocated.
- When a box goes out of scope, the heap data it points to is deallocated too.
- Putting a single small value such as an `i32` in a box is usually not useful.
- Values are stored on the stack by default in the majority of ordinary cases.
- A recursive type can contain another value of the same type as part of itself.
- Rust must know at compile time how much space a type takes.
- Direct recursive types can theoretically nest infinitely, so Rust cannot compute their size.
- Boxes have a known size because a pointer's size does not change based on the amount of pointed-to data.
- A box can enable a recursive type by inserting known-size indirection into the recursive type definition.
- A cons list is made of nested pairs.
- A cons-list item contains the current item value and the next item.
- The last item in the book's cons list is `Nil`, the recursive base case.
- The source's `Nil` is not the same as the "null" or "nil" concept from Chapter 6.
- `Vec<T>` is usually a better choice than a cons list for ordinary lists in Rust.
- The unboxed `List` enum's `Cons(i32, List)` variant stores another `List` directly.
- `Cons(i32, List)` makes the compiler recurse forever when computing the size of `List`.
- E0072 reports that recursive type `List` has infinite size.
- The compiler suggests inserting indirection such as `Box`, `Rc`, or `&` to break the recursive cycle.
- Replacing `Cons(i32, List)` with `Cons(i32, Box<List>)` gives `List` a known size.
- In `Cons(i32, Box<List>)`, the `Cons` variant needs the size of an `i32` plus the size of the box's pointer data.
- The boxed cons list still represents a list conceptually, but the next list value is on the heap rather than inside the `Cons` variant.
- Boxes provide indirection and heap allocation.
- Boxes do not provide the extra capabilities shown by later smart pointer types.
- `Box<T>` is a smart pointer because it implements `Deref`.
- `Deref` allows `Box<T>` values to be treated like references.
- `Box<T>` also implements `Drop`, so pointed-to heap data is cleaned up when the box goes out of scope.

#### Syntax Forms

- Allocate a value on the heap:
  ```rust
  let b = Box::new(5);
  println!("b = {b}");
  ```
- Direct recursive enum that does not compile:
  ```rust
  enum List {
      Cons(i32, List),
      Nil,
  }
  ```
- Unboxed cons-list construction that uses the direct recursive enum:
  ```rust

  fn main() {
      let list = Cons(1, Cons(2, Cons(3, Nil)));

  ```


  ```text
  (1, (2, (3, Nil)))
  ```

#### Failure Modes

- Boxing a small single value such as one `i32` as if it were usually useful; the source says stack storage is usually more appropriate.
- Defining recursive enum variants with direct self-storage, such as `Cons(i32, List)`.
- Reading `Nil` in the cons-list example as Rust's null concept; in this example it is the base-case variant.

- Thinking `Box<T>` removes all allocation cost; the source says the overhead is heap storage rather than stack storage.

#### Comparisons

- Stack value vs boxed value: a normal value is stored on the stack by default; a boxed value stores the data on the heap and a pointer on the stack.
- `Box<T>` vs later smart pointers: `Box<T>` provides heap allocation and indirection with little extra capability; later smart pointers add behavior such as reference counting or runtime borrow checking.
- Direct recursive enum vs boxed recursive enum: `Cons(i32, List)` has infinite size; `Cons(i32, Box<List>)` has known size because the recursive part is behind a pointer.
- Non-recursive enum sizing vs recursive enum sizing: Rust sizes a non-recursive enum by its largest variant, but a directly recursive enum makes size computation recurse indefinitely.
- Cons list vs `Vec<T>`: a cons list demonstrates recursive type mechanics; `Vec<T>` is usually the better Rust collection for lists of items.
- `Box<T>` for recursive types vs trait objects: this section demonstrates recursive types; trait objects are named as a later Chapter 18 use case.

### Card Content Candidates

#### Concepts

- Implementing `Deref` customizes the behavior of the dereference operator `*`.
- In this section, `*` means dereference, not multiplication and not glob import syntax.
- `Deref` can make a smart pointer behave like a regular reference.
- Reference-oriented code can also work with smart pointers when those smart pointers implement `Deref` appropriately.
- A regular reference is a pointer to a value stored somewhere else.
- `*y` follows the reference `y` to the value it points at.
- Without dereferencing, `y` has reference type, so `assert_eq!(5, y)` compares an integer with `&{integer}` and fails.
- `Box<T>` supports dereferencing with `*` in the same way a reference does.
- In Listing 15-7, `y = Box::new(x)` is a box pointing to a copied value of `x`, not a reference to `x`.
- A custom tuple struct such as `struct MyBox<T>(T);` is not automatically dereferenceable.
- The book's `MyBox<T>` example is shaped like `Box<T>` but does not store data on the heap.
- The `MyBox<T>` example focuses on pointer-like behavior rather than heap allocation.
- `MyBox::new(x)` takes a value of type `T` and returns a `MyBox<T>` holding that value.
- Before implementing `Deref`, `*y` on `MyBox<T>` fails with E0614 because the type cannot be dereferenced.
- The standard library's `Deref` trait requires a `deref` method.
- `deref` borrows `self` and returns a reference to the inner data.
- `type Target = T;` sets the associated target type used by `Deref`.
- In `MyBox<T>`, `&self.0` returns a reference to the first tuple-struct field.
- Without `Deref`, the compiler can only dereference `&` references.
- With `Deref`, the compiler can call `deref` on a type and then dereference the returned reference.
- When code writes `*y`, Rust effectively runs `*(y.deref())`.
- Rust substitutes the `*` operator with a `deref` call and then a plain dereference.
- The substitution occurs once for each `*` in source code; it does not recurse infinitely.
- `deref` returns a reference so the inner value is not moved out of `self`.
- Deref coercion converts a reference to a type implementing `Deref` into a reference to another type.
- `&String` can coerce to `&str` because `String` implements `Deref` with a target that produces `&str`.
- Deref coercion is a convenience applied to arguments of functions and methods.
- Deref coercion works only on types that implement `Deref` or `DerefMut` for the relevant case.
- Deref coercion happens automatically when an argument reference type does not match the parameter type but can be converted through deref calls.
- Rust can apply a sequence of `deref` calls to convert the provided reference type into the parameter's required reference type.
- Deref coercion reduces explicit `&` and `*` noise in function and method calls.
- Deref coercion helps code work for either references or smart pointers.
- Calling `hello(&m)` can work when `m: MyBox<String>` and `hello` expects `&str`.
- The `hello(&m)` coercion path is `&MyBox<String>` to `&String` through `MyBox<T>::deref`, then `&String` to `&str` through `String`'s `Deref`.
- Without deref coercion, the equivalent call is `hello(&(*m)[..])`.
- `(*m)` dereferences `MyBox<String>` into a `String`.
- `&(*m)[..]` takes a full string slice of that `String`.
- The number of inserted `Deref::deref` calls is resolved at compile time.
- Deref coercion has no runtime penalty.
- `DerefMut` overrides the `*` operator on mutable references.
- Rust supports deref coercion from `&T` to `&U` when `T: Deref<Target = U>`.
- Rust supports deref coercion from `&mut T` to `&mut U` when `T: DerefMut<Target = U>`.
- Rust supports deref coercion from `&mut T` to `&U` when `T: Deref<Target = U>`.
- Rust can coerce a mutable reference to an immutable reference.
- Rust cannot coerce an immutable reference to a mutable reference.
- A mutable reference must be the only reference to its data; turning it into one immutable reference cannot violate borrowing rules.
- An immutable reference is not guaranteed to be the only immutable reference, so converting it to a mutable reference would be unsound.

#### Syntax Forms

- Dereferencing a regular reference:
  ```rust
  fn main() {
      let x = 5;
      let y = &x;

      assert_eq!(5, x);
      assert_eq!(5, *y);
  }
  ```

- Dereferencing a `Box<i32>`:

  ```rust
  impl<T> MyBox<T> {

      }

  ```

  ```rust

      }

  ```

  ```rust

  ```


  ```rust

  hello(&m);
  ```
- Equivalent explicit call without deref coercion:
  ```rust
  let m = MyBox::new(String::from("Rust"));
  hello(&(*m)[..]);
  ```
- Deref coercion cases:
  ```text
  &T     -> &U     when T: Deref<Target = U>
  &mut T -> &mut U when T: DerefMut<Target = U>
  &mut T -> &U     when T: Deref<Target = U>
  ```

### Card Content Candidates

#### Concepts

- In most Rust code, ownership is clear: one variable owns a given value.
- Some data structures need a single value to have multiple owners.
- Graph data structures can have multiple edges pointing to the same node.
- A graph node should not be cleaned up while any edge still points to it.
- Multiple ownership must be enabled explicitly with `Rc<T>`.
- `Rc<T>` abbreviates reference counting.
- `Rc<T>` tracks the number of references to a value.
- The reference count determines whether the value is still in use.
- When there are zero references to an `Rc<T>` value, the value can be cleaned up without invalidating references.
- `Rc<T>` is for heap-allocated data that multiple parts of a program need to read.
- `Rc<T>` is useful when compile-time ownership cannot know which part will finish using the data last.
- If the last user is known at compile time, ordinary ownership should make that part the owner instead.
- `Rc<T>` in this chapter is only for single-threaded scenarios.
- Multithreaded reference counting is deferred to Chapter 16.
- The shared-list example has `b` and `c` share ownership of tail list `a`.
- The original `Box<List>` cons list cannot be shared by both `b` and `c` because `Box<T>` ownership moves.
- In Listing 15-17, creating `b` moves `a` into `b`.
- After `a` moves into `b`, creating `c` with `a` fails with E0382 use of moved value.
- Changing `Cons` to hold references would require lifetime parameters.
- Reference lifetimes would require every list element to live at least as long as the whole list.
- `Rc<T>` avoids the direct ownership move by sharing ownership through reference counting.
- Replacing `Box<List>` with `Rc<List>` lets each `Cons` hold a shared pointer to the next list.
- `Rc<T>` is not in the prelude; `use std::rc::Rc;` is needed.
- `Rc::new(value)` creates a new reference-counted owner.
- `Rc::clone(&a)` creates another owner of the same allocation.
- `Rc::clone(&a)` increments the reference count.
- `Rc::clone` does not deep-copy all the underlying list data.
- `Rc::clone` is usually cheap because it increments a count.
- Deep-copy `clone` implementations can be expensive.
- Using `Rc::clone(&a)` rather than `a.clone()` visually distinguishes reference-count increments from deep copies.
- This naming convention helps performance review focus on potentially expensive clone calls.
- `Rc::strong_count(&a)` returns the strong reference count.
- The source names `strong_count` rather than `count` because `Rc<T>` also has `weak_count`.
- `weak_count` is deferred by the source to the later `Weak<T>` reference-cycle section.
- The initial `Rc<List>` owner `a` has strong count 1.
- Creating `b` with `Rc::clone(&a)` increases the strong count to 2.
- Creating `c` with `Rc::clone(&a)` increases the strong count to 3.
- When `c` goes out of scope, the strong count decreases to 2.
- The count decreases automatically through the `Drop` implementation when an `Rc<T>` owner goes out of scope.
- When all strong owners go out of scope, the count reaches 0 and the `Rc<List>` allocation is cleaned up completely.
- `Rc<T>` keeps shared data valid as long as any owner still exists.
- `Rc<T>` shares data for reading via immutable references.
- `Rc<T>` does not allow multiple mutable references to the same place.
- Allowing multiple mutable references through `Rc<T>` would violate the borrowing rules and could cause data races or inconsistencies.
- Mutating data shared by `Rc<T>` is deferred to interior mutability with `RefCell<T>` in the next section.

#### Concepts

- Interior mutability allows mutating data even when immutable references to that data exist.
- Ordinary borrowing rules normally disallow mutating through immutable references.

- `RefCell<T>` follows the interior mutability pattern.
- `RefCell<T>` represents single ownership over the data it holds.
- With references and `Box<T>`, borrowing rules are enforced at compile time.
- With `RefCell<T>`, borrowing rules are enforced at runtime.
- Breaking borrowing rules with references gives a compiler error.
- Breaking borrowing rules with `RefCell<T>` makes the program panic and exit.
- Compile-time borrow checking catches errors earlier and has no runtime performance impact.
- Runtime borrow checking can allow memory-safe programs that conservative static analysis cannot prove correct.
- The compiler is conservative: rejecting a correct program is inconvenient, but accepting an incorrect program would break Rust's guarantees.
- `RefCell<T>` is useful when code follows borrowing rules but the compiler cannot understand that fact.
- Like `Rc<T>`, `RefCell<T>` is only for single-threaded scenarios.
- `RefCell<T>` gives a compile-time error if used in a multithreaded context.
- Chapter 16 covers multithreaded equivalents.
- `Rc<T>` enables multiple owners; `Box<T>` and `RefCell<T>` have single owners.
- `Box<T>` allows immutable or mutable borrows checked at compile time.
- `Rc<T>` allows only immutable borrows checked at compile time.
- `RefCell<T>` allows immutable or mutable borrows checked at runtime.
- Because `RefCell<T>` allows runtime-checked mutable borrows, an immutable `RefCell<T>` can mutate its inner value.
- The ordinary code `let x = 5; let y = &mut x;` fails because `x` is not mutable.
- E0596 reports that `x` cannot be borrowed as mutable because it is not declared mutable.
- Some values need methods that mutate internal state while appearing immutable to outside code.
- `RefCell<T>` does not bypass the borrowing rules; it moves enforcement from compile time to runtime.
- Violating `RefCell<T>` borrowing rules produces `panic!` instead of a compiler error.
- Test doubles stand in for other types during tests.
- Mock objects record what happens during a test so assertions can check behavior.
- The `Messenger` trait's `send(&self, msg: &str)` method uses immutable `self`.
- `LimitTracker::set_value` stores the current value and sends quota messages through `Messenger`.
- At 100 percent or more, `LimitTracker` sends an over-quota error.
- At 90 percent or more, it sends an urgent warning.
- At 75 percent or more, it sends a warning.
- A mock messenger needs to record sent messages without changing the production `Messenger` trait.
- A plain `Vec<String>` field cannot be mutated from `send(&self)`.
- Changing `Messenger::send` to `&mut self` solely for testing would change the library design.
- `RefCell<Vec<String>>` lets the mock object mutate its message log while `send` still takes `&self`.
- `RefCell::new(vec![])` wraps the mock message vector.
- `self.sent_messages.borrow_mut()` returns mutable access to the inner vector so `push` can record a message.
- `self.sent_messages.borrow()` returns immutable access to inspect the inner vector length.
- With `RefCell<T>`, `borrow` and `borrow_mut` are the safe API equivalents to ordinary `&` and `&mut`.
- `borrow` returns `Ref<T>`.
- `borrow_mut` returns `RefMut<T>`.
- `Ref<T>` and `RefMut<T>` both implement `Deref`, so they can be treated like regular references.
- `RefCell<T>` tracks how many active `Ref<T>` and `RefMut<T>` smart pointers exist.
- Each `borrow` increments the active immutable borrow count.
- When a `Ref<T>` goes out of scope, the active immutable borrow count decreases by 1.
- `RefCell<T>` allows many immutable borrows or one mutable borrow at any point in time.
- Creating two active `RefMut<T>` values for the same `RefCell<T>` compiles but panics at runtime.
- Listing 15-23 panics with `RefCell already borrowed`.
- Runtime borrow checking can find mistakes later than compile-time checking.
- Runtime borrow tracking has a small performance cost.
- `RefCell<T>` can still be worth the tradeoff when it enables safe patterns such as mock objects.
- A common pattern is combining `Rc<T>` with `RefCell<T>`.
- `Rc<T>` allows multiple owners but only immutable access.
- `Rc<RefCell<T>>` provides multiple ownership plus runtime-checked mutation.
- In the mutable cons-list example, `Cons` stores `Rc<RefCell<i32>>` for the value and `Rc<List>` for the next list.
- The `value` variable is an `Rc<RefCell<i32>>` so it can be shared directly and mutated later.

- `RefCell<T>` does not work for multithreaded code.
- `Mutex<T>` is the thread-safe version of `RefCell<T>` discussed in Chapter 16.

#### Comparisons

- Compile-time borrow checking vs runtime borrow checking: references and `Box<T>` enforce borrowing at compile time; `RefCell<T>` enforces the same rules at runtime.
- `Box<T>` vs `Rc<T>` vs `RefCell<T>`: `Box<T>` has one owner with compile-time immutable/mutable borrows; `Rc<T>` has multiple owners with compile-time immutable borrows; `RefCell<T>` has one owner with runtime-checked immutable/mutable borrows.
- Ordinary mutable borrow vs interior mutability: ordinary mutation requires a mutable binding/reference; interior mutability can mutate inner data through an outwardly immutable value.
- Compiler error vs runtime panic: ordinary reference violations fail compilation; `RefCell<T>` violations compile but panic if the rule is broken at runtime.
- Mock object with plain `Vec<String>` vs `RefCell<Vec<String>>`: the plain vector cannot be pushed through `send(&self)`; the `RefCell` vector can be pushed through `borrow_mut`.
- `borrow` vs `borrow_mut`: `borrow` returns `Ref<T>` for immutable access; `borrow_mut` returns `RefMut<T>` for mutable access.
- `Rc<T>` alone vs `Rc<RefCell<T>>`: `Rc<T>` permits shared read-only ownership; `Rc<RefCell<T>>` permits shared ownership plus runtime-checked mutation.
- `RefCell<T>` vs `Mutex<T>`: `RefCell<T>` is single-threaded; `Mutex<T>` is the thread-safe analogue covered in Chapter 16.
- Unsafe implementation vs safe abstraction: `RefCell<T>` uses internal unsafe code but exposes a safe API that enforces borrowing rules at runtime.

#### Concepts

- Rust's memory safety guarantees make memory leaks difficult but not impossible.
- A memory leak is memory that is never cleaned up.
- Preventing memory leaks entirely is not one of Rust's guarantees.
- Memory leaks are memory safe in Rust.
- `Rc<T>` and `RefCell<T>` can be combined to create references where items refer to each other in a cycle.
- A reference cycle leaks memory because each item in the cycle keeps the other item's reference count above 0.
- Values in a reference cycle are never dropped if their reference counts never reach 0.
- Listing 15-25 changes the cons list tail to `RefCell<Rc<List>>`.
- `RefCell<Rc<List>>` lets code mutate which `List` value a `Cons` variant points to.
- `tail(&self) -> Option<&RefCell<Rc<List>>>` provides access to the tail link for `Cons` variants.
- Listing 15-26 creates `a` as `Rc<List>` containing `5, Nil`.
- Listing 15-26 creates `b` as `Rc<List>` containing `10` and pointing to `a`.
- Mutating `a`'s tail to `Rc::clone(&b)` creates a cycle: `a` points to `b`, and `b` points to `a`.
- After changing `a` to point to `b`, both `a` and `b` have strong count 2.
- At the end of `main`, dropping `b` decreases `b`'s strong count from 2 to 1, so its heap allocation is not dropped.
- Dropping `a` then decreases `a`'s strong count from 2 to 1, so its heap allocation is not dropped.
- The allocated list memory remains uncollected forever.
- Uncommenting the final debug print in Listing 15-26 would try to print `a -> b -> a -> ...` until stack overflow.
- Reference cycles are logic bugs.
- Rust cannot be relied on to catch reference cycles.
- Tests, code reviews, and design practices should minimize reference-cycle bugs.
- One way to avoid reference cycles is to distinguish ownership relationships from non-ownership relationships.
- Only ownership relationships should affect whether a value can be dropped.
- A graph can contain cycles made of ownership and non-ownership relationships without leaking if ownership counts can still reach 0.
- Strong references share ownership of an `Rc<T>` value.
- Weak references do not express ownership.
- Weak references do not affect when an `Rc<T>` allocation is cleaned up.
- Cycles involving weak references break once the strong count of the involved values reaches 0.
- `Rc::downgrade(&rc_value)` creates a `Weak<T>` reference to the value inside an `Rc<T>`.
- `Rc::downgrade` increments `weak_count` rather than `strong_count`.
- `weak_count` tracks the number of `Weak<T>` references.
- `weak_count` does not need to be 0 for an `Rc<T>` allocation to be cleaned up.
- A `Weak<T>` reference might point to a value that has already been dropped.
- `Weak<T>::upgrade` checks whether the pointed-to value still exists.
- `upgrade` returns `Option<Rc<T>>`.
- `upgrade` returns `Some(Rc<T>)` if the `Rc<T>` value has not been dropped.
- `upgrade` returns `None` if the `Rc<T>` value has been dropped.
- Returning `Option<Rc<T>>` forces code to handle both live and dropped cases, avoiding invalid pointers.
- In the tree example, a node should own its children.
- If a parent node is dropped, its child nodes should be dropped too.
- A child node should not own its parent.
- If a child node is dropped, the parent should still exist.
- Parent-to-child edges are ownership relationships in the tree example.
- Child-to-parent edges are non-ownership relationships in the tree example.
- `children: RefCell<Vec<Rc<Node>>>` lets a node own child nodes and mutate the child list.
- `parent: RefCell<Weak<Node>>` lets a child refer to its parent without owning it.
- `Weak::new()` creates an empty weak reference for a node with no parent.
- Before assigning a parent, `leaf.parent.borrow().upgrade()` returns `None`.
- Assigning `*leaf.parent.borrow_mut() = Rc::downgrade(&branch)` gives `leaf` a weak parent link.
- After assigning the parent, `leaf.parent.borrow().upgrade()` returns `Some(branch)` while `branch` still exists.
- Debug output prints `Weak<Node>` references as `(Weak)` and avoids infinite output.
- Listing 15-29 starts with `leaf` strong count 1 and weak count 0.
- Inside the inner scope, `branch` has strong count 1 and weak count 1 because `leaf.parent` points to it weakly.
- Inside the inner scope, `leaf` has strong count 2 and weak count 0 because `branch.children` owns a clone of `leaf`.
- When the inner scope ends, `branch`'s strong count drops to 0 and the branch node is dropped.
- The weak count from `leaf.parent` does not keep `branch` alive.
- After `branch` is dropped, upgrading `leaf.parent` returns `None`.
- At the end of Listing 15-29, `leaf` has strong count 1 and weak count 0.
- `Rc<T>` and `Weak<T>` manage counts and dropping through their `Drop` implementations.
- CH-15 summary: `Box<T>` gives known size and heap allocation.
- CH-15 summary: `Rc<T>` tracks references to heap data for multiple ownership.
- CH-15 summary: `RefCell<T>` enables interior mutability and runtime borrow checking.
- CH-15 summary: `Deref` and `Drop` enable much of smart pointer behavior.
- CH-15 summary: `Weak<T>` prevents reference cycles that would leak memory.

#### Comparisons

- Memory safety vs memory leaks: Rust prevents many invalid memory behaviors, but memory leaks remain memory safe and possible.
- Strong reference vs weak reference: strong references express ownership and affect cleanup; weak references do not express ownership and do not keep values alive.
- `Rc::clone` vs `Rc::downgrade`: `Rc::clone` increments `strong_count`; `Rc::downgrade` creates `Weak<T>` and increments `weak_count`.
- `strong_count` vs `weak_count`: `strong_count` must reach 0 for cleanup; `weak_count` tracks weak references and need not be 0 for cleanup.
- `Rc<T>` parent link vs `Weak<T>` parent link: an `Rc<T>` parent link would create an ownership cycle; a `Weak<T>` parent link records the relationship without ownership.
- Parent-to-child vs child-to-parent tree relationship: parent owns child; child refers to parent without owning it.
- `RefCell<Rc<List>>` cons-list cycle vs `RefCell<Weak<Node>>` parent link: the former can create an owning cycle; the latter creates a non-owning back-reference.
- `upgrade` `Some` vs `None`: `Some` means the target still has strong owners; `None` means the target has been dropped.
