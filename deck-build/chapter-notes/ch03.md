### Learning Objectives

- Learner can explain Rust's default variable rule: variables are immutable unless declared with `mut`.
- Learner can diagnose E0384 when code assigns a second value to an immutable variable.
- Learner can write the `mut` syntax that allows reassignment and explain how it communicates intent to future readers.
- Learner can distinguish immutable variables from constants, including `const`, required type annotations, allowed scopes, and constant-expression limits.
- Learner can write a constant declaration using Rust's all-uppercase-with-underscores convention.
- Learner can explain shadowing: a new `let` binding with the same name hides the previous binding until another shadow or scope end.
- Learner can predict values across nested shadowing scopes.
- Learner can distinguish shadowing from mutation, especially that shadowing can change a value's type while mutation cannot.

### Card Content Candidates

#### Concepts

- Variables are immutable by default in Rust.
- Immutability is a deliberate safety and concurrency nudge: once a value is bound to an immutable name, the value cannot be changed.
- Compiler errors on attempted mutation are useful because they catch code that violates the stated "this value will not change" intent.
- Error E0384 appears when assigning a second value to an immutable variable, as in `x = 6` after `let x = 5`.
- `mut` opts a binding into mutability: `let mut x = 5;`.
- Adding `mut` lets code reassign the same variable, and it signals to readers that later code changes this value.
- Choosing mutability is a clarity decision for the particular situation.
- Constants are bound names that cannot change, but they differ from immutable variables.
- Constants cannot be used with `mut`; they are always immutable.
- Constants use `const` instead of `let`.
- Constant declarations must include a type annotation.
- Constants can be declared in any scope, including global scope.
- Constants may be set only to constant expressions, not values computed only at runtime.
- Constant names conventionally use all uppercase letters with underscores between words.
- Constants are valid for the entire time a program runs, within their declaration scope.
- Constants are useful for domain values many parts of the program need to know, such as maximum points or speed of light.
- Naming hardcoded values as constants communicates meaning and centralizes future changes.
- Shadowing creates a new variable with the same name as a previous variable by repeating `let`.
- The newer binding shadows the earlier one; uses of that name refer to the newer binding until it is shadowed again or its scope ends.
- Inner-scope shadowing ends when the inner scope ends, revealing the outer binding again.
- Shadowing differs from `mut`: omitting `let` during reassignment causes a compile-time error for immutable bindings.
- Shadowing allows transformations while leaving the final binding immutable.
- Shadowing creates a new variable, so it can reuse the same name with a different type.
- `mut` changes the value of the same variable and cannot change that variable's type.

#### Syntax Forms

- Create the variables project:
  ```console
  $ cargo new variables
  ```
- Immutable reassignment example, intentionally compile-fail:
  ```rust
  fn main() {
      let x = 5;
      println!("The value of x is: {x}");
      x = 6;
      println!("The value of x is: {x}");
  }
  ```
- Mutable reassignment example:
  ```rust
  fn main() {
      let mut x = 5;
      println!("The value of x is: {x}");
      x = 6;
      println!("The value of x is: {x}");
  }
  ```
- Constant declaration:
  ```rust
  const THREE_HOURS_IN_SECONDS: u32 = 60 * 60 * 3;
  ```
- Shadowing with nested scope:
  ```rust
  fn main() {
      let x = 5;

      let x = x + 1;

      {
          let x = x * 2;
          println!("The value of x in the inner scope is: {x}");
      }

      println!("The value of x is: {x}");
  }
  ```
- Shadowing can change types:
  ```rust
  fn main() {
      let spaces = "   ";
      let spaces = spaces.len();
  }
  ```
- `mut` cannot change a variable's type, intentionally compile-fail:
  ```rust
  fn main() {
      let mut spaces = "   ";
      spaces = spaces.len();
  }
  ```

#### Prediction / Diagnostic Examples

- Given `let x = 5; x = 6;`, predict compile failure E0384 because `x` is immutable.

- Given the mutable `x` example, predict output:
  ```text

  The value of x is: 6
  ```
- Given `const THREE_HOURS_IN_SECONDS: u32 = 60 * 60 * 3;`, identify the name, type annotation, and compile-time expression.
- Given the shadowing example, predict inner output `12` and outer output `6`.

#### Failure Modes

- Trying to assign twice to an immutable variable without `mut`.
- Assuming compiler errors mean personal failure; this section frames errors as feedback that the program is not safely doing the intended thing yet.
- Using `mut` with a constant; constants are always immutable.
- Omitting a type annotation on a `const`.
- Setting a constant from a runtime-only value rather than a constant expression.
- Naming constants in lowercase when following Rust convention.
- Treating shadowing as mutation; shadowing creates a new variable with `let`.
- Forgetting `let` during a shadowing-style transformation, which turns it into reassignment.
- Trying to use `mut` to change a variable's type.

#### Comparisons

- Immutable variable vs mutable variable: default no reassignment vs explicit `mut` reassignment.
- Immutable variable vs constant: both cannot change, but constants use `const`, require type annotation, cannot use `mut`, can be global, and must be constant expressions.
- `let` vs `const`: runtime binding syntax vs always-immutable constant declaration syntax.
- Constant expression vs runtime-computed value: allowed for `const` vs disallowed for `const`.
- Shadowing vs mutation: new binding with `let` vs changing the same binding.
- Shadowing type change vs `mut` type stability: shadowing can reuse a name for a different type, while mutable reassignment keeps the same inferred type.
- Inner-scope shadowing vs outer binding: inner binding hides the outer binding only until the inner scope ends.

### Card Content Candidates

#### Concepts

- Every Rust value has a data type that tells Rust what kind of data it is and how to work with it.
- This section splits data types into scalar and compound subsets.
- Rust is statically typed: it must know the types of all variables at compile time.
- Type inference often determines the intended type from the value and usage.
- Type annotations are required when many types are possible, such as parsing `"42"` into a numeric type.
- Missing a type annotation for `parse` can produce E0284: type annotations needed.
- Scalar type: represents a single value.
- Rust's four primary scalar types: integers, floating-point numbers, Booleans, and characters.
- Integer: number without a fractional component.
- Integer type naming: signed integer types start with `i`; unsigned integer types start with `u`; the suffix number gives bit width.
- Built-in integer widths: 8, 16, 32, 64, 128, and architecture-dependent `isize`/`usize`.
- Signed integer range: from `-(2^(n - 1))` to `2^(n - 1) - 1` inclusive for an n-bit signed type.
- `i8` range: -128 through 127.
- Unsigned integer range: from 0 to `2^n - 1` inclusive for an n-bit unsigned type.
- `u8` range: 0 through 255.
- `isize` and `usize`: 64 bits on 64-bit architectures, 32 bits on 32-bit architectures.
- Integer literals can be decimal, hex, octal, binary, or byte literals.
- Integer literals can carry type suffixes such as `57u8`.
- Numeric literals can use `_` visual separators; `1_000` has the same value as `1000`.
- Integer default: `i32` when Rust cannot infer another integer type.
- Main `isize`/`usize` use case in this section: indexing collections.
- Integer overflow: assigning a value outside a type's range.
- Debug integer overflow behavior: runtime panic from overflow checks.
- Release integer overflow behavior: no overflow panic checks; two's complement wrapping occurs.
- Relying on wrapping overflow behavior is considered an error.
- Explicit overflow-handling method families: `wrapping_*`, `checked_*`, `overflowing_*`, and `saturating_*`.
- Floating-point types: `f32` and `f64`.
- Floating-point default: `f64`, because it is roughly the same speed as `f32` on modern CPUs but has more precision.
- Floating-point values are signed and represented according to IEEE-754.
- Numeric operations covered: addition, subtraction, multiplication, division, and remainder.
- Integer division truncates toward zero.
- Boolean type: `bool`, one byte, values `true` and `false`.
- Main Boolean use case: conditionals such as `if` expressions.
- Character type: `char`, written with single quotes.
- String literals use double quotes, unlike `char` literals.
- `char` is 4 bytes and represents a Unicode scalar value.
- Unicode scalar value range: `U+0000` to `U+D7FF` and `U+E000` to `U+10FFFF` inclusive.
- Compound type: groups multiple values into one type.
- Rust's primitive compound types: tuples and arrays.
- Tuple: fixed-length grouping of values that may have different types.
- Tuple values are written as a comma-separated list in parentheses.
- Tuple type annotation lists each element type in parentheses.
- Tuple destructuring uses a pattern with `let` to split a tuple into separate variables.
- Tuple indexing uses `.` followed by a zero-based index.
- Unit `()`: tuple with no values; represents an empty value or empty return type.
- Expressions implicitly return unit if they return no other value.
- Array: fixed-length collection where every element has the same type.
- Array literal syntax: comma-separated list in square brackets.
- Arrays are useful when data should be allocated on the stack or must have a fixed number of elements.
- Vector boundary: vectors are standard-library collections whose heap-backed contents can grow or shrink.
- Array type syntax: `[element_type; length]`.
- Repeated array initialization: `[value; length]`.
- Array indexing uses square brackets, such as `a[0]`.
- Out-of-bounds array access compiles when the index is only known at runtime, but panics at runtime.
- Array indexing safety rule: Rust checks that the index is less than array length and panics if index is greater than or equal to length.
- Runtime bounds checking protects against invalid memory access.

#### Failure Modes

- Omitting type annotations when Rust cannot infer a type, especially for `parse`.
- Assuming `u32` can hold negative numbers; unsigned types cannot.
- Assuming `isize`/`usize` have fixed width independent of architecture.
- Relying on release-mode integer wrapping behavior instead of explicit overflow handling.
- Treating debug overflow and release overflow as identical.
- Treating `f32` as the floating-point default; Rust defaults to `f64`.
- Expecting integer division to preserve a fractional value; integer division truncates toward zero.
- Using double quotes for a `char`; `char` literals use single quotes.
- Treating Rust `char` as equivalent to a user-perceived character or ASCII byte.
- Expecting tuples or arrays to grow/shrink after declaration; both have fixed length.
- Assuming tuple elements must all have the same type; tuple element types can differ.
- Assuming array elements can have different types; array elements must all have the same type.
- Using a tuple index as if it were one-based; tuple indices start at 0.
- Assuming arrays are as flexible as vectors; vectors can grow/shrink and are discussed later.
- Assuming compile-time prevention for every out-of-bounds access; runtime input requires runtime bounds checking and may panic.

#### Comparisons

- Scalar vs compound type: single value vs grouping multiple values.
- Type inference vs type annotation: compiler infers from value/use vs programmer supplies type when many types are possible.
- Signed vs unsigned integers: can represent negative and positive values vs only nonnegative values.
- Fixed-width integer vs architecture-dependent integer: explicit bit size vs `isize`/`usize` width depending on target architecture.
- Debug overflow vs release overflow: panic checks vs two's complement wrapping.
- `wrapping_*` vs `checked_*` vs `overflowing_*` vs `saturating_*`: wrap, return `None`, return value plus overflow flag, or clamp to min/max.
- `f32` vs `f64`: 32-bit vs 64-bit, with `f64` as default and more precise.
- Boolean vs numeric condition boundary: Boolean values are used in conditionals; later control-flow cards should keep `if` conditions Boolean.
- `char` vs string literal: single-quoted Unicode scalar value vs double-quoted string.
- Tuple vs array: heterogeneous fixed-length grouping vs homogeneous fixed-length collection.
- Tuple destructuring vs tuple indexing: pattern split into variables vs direct `.index` access.
- Array vs vector: fixed-length, stack-friendly array vs growable/shrinkable standard-library vector on the heap.
- Array literal vs repeated initialization: explicit element list vs `[value; length]`.
- Compile-time type error vs runtime panic: missing parse type annotation is a compile-time error; invalid user-provided array index panics at runtime.

### Card Content Candidates

#### Concepts

- Functions are common in Rust; `main` is the entry point of many programs.
- `fn` declares a new function.
- Rust naming convention for function and variable names is snake case: lowercase letters with underscores between words.
- Function definition syntax: `fn`, function name, parentheses, and a body in curly brackets.
- A function can be called by writing its name followed by parentheses.
- Rust does not care whether a function is defined before or after its caller, only that it is defined in a scope visible to the caller.
- Function body execution follows calls from `main`; in the example, `main` prints first, then calls `another_function`.
- Parameter: special variable that is part of a function's signature.
- Argument: concrete value supplied when calling a function.
- Parameter and argument are often used interchangeably in casual conversation, but source distinguishes definition variable vs call value.
- Function parameter types must be declared in function signatures.
- Required parameter annotations help the compiler infer types elsewhere and produce more useful errors.
- Multiple parameter declarations are separated with commas.
- Function bodies contain a series of statements optionally ending in an expression.
- Statement: instruction that performs an action and does not return a value.
- Expression: evaluates to a resultant value.
- `let y = 6;` is a statement.
- Function definitions are statements.
- Statements do not return values, so a `let` statement cannot be assigned to another variable.
- Rust differs from languages such as C and Ruby where assignment may return the assigned value.
- Math operations such as `5 + 6` are expressions.
- Expressions can be part of statements, as `6` is part of `let y = 6;`.
- Function calls are expressions.
- Macro calls are expressions.
- Scope blocks created with curly brackets are expressions.
- A block expression's final expression without a semicolon determines the block's value.
- Expressions do not include ending semicolons.
- Adding a semicolon to an expression turns it into a statement and removes its returned value.
- Function return values are declared after `->`.
- Rust functions do not name return values.
- The return value of a function is the value of the final expression in the function body.
- `return` can return early, but most functions in the book return the final expression implicitly.

### Card Content Candidates

#### Concepts

- Control flow lets code run conditionally or repeatedly.
- The most common Rust control-flow constructs in this section are `if` expressions and loops.
- An `if` expression starts with `if`, followed by a condition and a curly-braced block to execute when the condition is `true`.
- The block associated with an `if` condition is an arm, analogous to a `match` arm.
- `else` is optional; if no `else` is provided and the condition is `false`, Rust skips the `if` block and continues after it.
- The condition in an `if` expression must be a `bool`.
- Rust does not automatically convert non-Boolean values, such as integers, into Booleans.
- To branch on whether a number is nonzero, write an explicit Boolean expression such as `number != 0`.
- `else if` chains check conditions in order.
- In an `else if` chain, Rust executes only the first block whose condition is `true` and does not check the remaining conditions.
- Too many `else if` expressions can clutter code; the book points to `match` in Chapter 6 as a better branching construct for some cases.
- `if` is an expression, so it can appear on the right side of a `let` statement.
- Blocks evaluate to their last expression, so the value of an `if` expression depends on the executed arm.
- Every possible result arm of an `if` expression used as a value must have the same type.
- Rust requires a single compile-time type for a variable; it does not allow a variable's type to depend on which branch runs at runtime.
- Rust has three loop constructs in this section: `loop`, `while`, and `for`.
- `loop` repeats a block forever or until code explicitly stops it.
- `break` exits the current loop.
- `continue` skips the remaining code in the current loop iteration and starts the next iteration.
- A `loop` can return a value by writing the value after `break`.
- In `let result = loop { ... break counter * 2; };`, the semicolon after the loop ends the `let` statement that receives the loop value.
- `return` inside a loop exits the current function, while `break` exits only the current loop.
- In nested loops, unlabeled `break` and `continue` apply to the innermost loop.
- A loop label can be put on a loop and then used with `break` or `continue` to target that labeled loop instead of the innermost loop.
- Loop labels must begin with a single quote, as in `'counting_up: loop`.
- A `while` loop runs while its condition is `true` and exits once the condition is no longer `true`.
- `while` can express a pattern that would otherwise require `loop`, `if`, `else`, and `break`.
- A `while` loop can index through a collection, but this approach is error-prone if the collection length or condition changes.
- Index-based `while` iteration can panic if it indexes beyond the end of an array.
- Index-based `while` iteration is slower because the compiler adds runtime bounds checks for each indexed access.
- A `for` loop runs code for each item in a collection.
- `for` loops are safer and more concise for collection iteration than manually indexing with `while`.
- The book describes `for` as the most commonly used loop construct in Rust.
- `for` can also run code a fixed number of times by iterating over a standard-library `Range`.
- A range such as `1..4` starts at `1` and ends before `4`.
- The `rev` method reverses the range for countdown-style iteration.
- Chapter 3's practice prompts are temperature conversion, nth Fibonacci, and printing "The Twelve Days of Christmas" lyrics using repetition.

#### Comparisons

- `if` without `else` vs `if` with `else`: false condition skips the block vs runs an alternate block.
- `if` condition in Rust vs truthy/falsy languages: Rust requires `bool`; Ruby and JavaScript are named as languages where non-Boolean conversion exists.
- `else if` chain vs `match`: `else if` works for multiple conditions but can clutter code; `match` is introduced later as a powerful branching construct.
- `if` statement-like branch vs `if` expression in `let`: control-only branching vs value-producing branching.
- Compatible arm values vs incompatible arm values: all possible `if` expression results must have one type.
- `loop` vs `while`: repeat until explicit stop vs repeat while a Boolean condition is true.
- `break` vs `continue`: exit loop vs skip to next iteration.
- `break` vs `return`: exit current loop vs exit current function.

- `while` array indexing vs `for element in a`: manual index and bounds checks vs direct collection iteration.
- `while` countdown vs `for` range countdown: condition-mutating loop vs range iteration with `rev`.
