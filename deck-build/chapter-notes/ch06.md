### Learning Objectives

- Learner can explain when an enum is more appropriate than a struct: when a value must be exactly one of a known set of alternatives.
- Learner can define enum variants with no associated data.
- Learner can construct enum values with namespaced variant paths such as `IpAddrKind::V4`.
- Learner can explain why namespacing variants under the enum lets different variants share one type.
- Learner can compare storing an enum variant in a struct field with putting data directly on enum variants.
- Learner can define enum variants with associated data, including different data types and arities per variant.
- Learner can explain that enum variant names become constructor functions.
- Learner can model a family of related message shapes as one enum instead of separate struct types.
- Learner can define methods on enums with `impl`.
- Learner can explain why Rust uses `Option<T>` instead of null and how `Some(T)` and `None` represent presence and absence.
- Learner can explain why `Option<T>` forces explicit handling before using the inner `T`.
- Learner can diagnose E0277 when trying to use an `Option<T>` directly as a `T`.
- Learner can explain why `None` often needs a type annotation when inference cannot determine `T`.

### Card Content Candidates

#### Concepts

- Structs group related fields and data.
- Enums express that a value is one of a possible set of values.
- An enum value can only be one of its variants at a time.
- IP address versions are a motivating example because an IP address can be either version four or version six, but not both at the same time.
- Both IPv4 and IPv6 addresses are still fundamentally IP addresses, so they should be handled as the same type when code applies to any IP address.
- `IpAddrKind` is a custom data type after the enum is defined.
- `V4` and `V6` are variants of `IpAddrKind`.
- Enum variants are namespaced under the enum identifier.
- `IpAddrKind::V4` and `IpAddrKind::V6` are both values of the same type: `IpAddrKind`.
- The double colon `::` separates the enum name from the variant name.
- A function that takes `IpAddrKind` can accept either `IpAddrKind::V4` or `IpAddrKind::V6`.
- Listing 6-1 uses a struct `IpAddr` with a `kind: IpAddrKind` field and an `address: String` field to bundle the variant with address data.
- Putting data directly into enum variants can remove the need for an extra struct.
- `enum IpAddr { V4(String), V6(String) }` attaches address data directly to each variant.
- Each enum variant name also becomes a constructor function for that enum variant.
- `IpAddr::V4(String::from("127.0.0.1"))` calls the `V4` variant constructor and returns an `IpAddr`.
- Enum variants can have different types and amounts of associated data.
- `IpAddr::V4(127, 0, 0, 1)` can store four `u8` values while `IpAddr::V6(String::from("::1"))` stores one `String`.
- The standard library has an `IpAddr` enum with `V4(Ipv4Addr)` and `V6(Ipv6Addr)` variants.
- Enum variants can contain strings, numeric types, structs, or even another enum.
- A user-defined `IpAddr` can coexist with the standard library's `IpAddr` if the standard library type has not been brought into scope.
- `Message` in Listing 6-2 demonstrates variants with no data, named fields, a single value, and multiple values.
- `Message::Quit` has no associated data.
- `Message::Move { x: i32, y: i32 }` has named fields like a struct.
- `Message::Write(String)` has one `String`.
- `Message::ChangeColor(i32, i32, i32)` has three `i32` values.
- A variant with named fields resembles a struct-like variant.
- A variant with unnamed positional values resembles a tuple-struct-like variant.
- An enum can group variants with different data shapes under one type.
- Separate structs for each message shape would each have their own type.
- Using one `Message` enum makes it easier to define a function that accepts any message variant.
- Enums, like structs, can have methods defined with `impl`.
- In an enum method, `self` is the enum value the method is called on.
- In the `Message` example, `m` has value `Message::Write(String::from("hello"))`, and `self` is that value when `m.call()` runs.
- `Option` is a standard-library enum that models a value that could be something or could be nothing.
- Rust does not have the null feature found in many other languages.
- Null means there is no value there.
- The useful concept behind null is a value being invalid or absent for some reason.
- Rust encodes presence or absence with `Option<T>` rather than null.
- `Option<T>` has two variants: `None` and `Some(T)`.
- `Some(T)` means a value is present and held inside `Some`.
- `None` means there is no valid value.
- `Option<T>` is included in the prelude, so it usually does not need to be brought into scope.
- `Some` and `None` are also included in the prelude, so they can be written without the `Option::` prefix.
- `Option<T>` is still a regular enum, and `Some(T)` and `None` are variants of `Option<T>`.
- `<T>` is a generic type parameter, covered in detail later in Chapter 10.
- In this section, `<T>` means `Some` can hold one piece of data of any type.
- Each concrete type used in place of `T` creates a different `Option<T>` type.
- `Some(5)` can infer an `Option<i32>` in the source example.
- `Some('e')` can infer an `Option<char>`.
- `None` by itself does not tell the compiler what type a corresponding `Some` would hold.
- `let absent_number: Option<i32> = None;` supplies the missing type information for `None`.
- `Option<T>` and `T` are different types.
- The compiler does not let code use an `Option<T>` value as if it were definitely a valid `T`.
- Before performing `T` operations, code must convert an `Option<T>` into a `T` by handling the possible absence.
- `Option<T>` makes possible absence explicit in the type.
- Non-`Option<T>` values can be assumed not-null in Rust.
- Rust requires explicit opt-in to possible absence by making the value's type `Option<T>`.
- Using an `Option<T>` value requires explicitly handling the `None` case before using the inner value.
- The section ends by motivating `match`: to use an `Option<T>`, code generally handles both `Some(T)` and `None`, and matching code can use the data inside the matching variant.

  ```rust

      V4,
      V6,
  }
  ```

  let six = IpAddrKind::V6;
  ```

  route(IpAddrKind::V6);
  ```

      V4,

#### Comparisons

- Struct vs enum: a struct groups related fields; an enum represents one value from a possible set of variants.
- `IpAddrKind` enum plus `IpAddr` struct vs `IpAddr` enum with data: separate kind/data fields vs data attached directly to variants.
- Same data on every variant vs different data per variant: enums can do either, unlike a single ordinary struct field layout.
- Enum variant with named fields vs struct: similar data shape, but the variant is still grouped under one enum type.
- Enum variant with unnamed fields vs tuple struct: similar positional data shape, but the variant is still one case of an enum.
- `Message` enum vs separate message structs: one type with multiple variants vs multiple unrelated types.
- Enum methods vs struct methods: both use `impl` and `self`; the receiver is an enum value for enum methods.
- Rust `Option<T>` vs null: `Option<T>` explicitly encodes absence in the type, while null is a pervasive implicit state in other languages.
- `Some(T)` vs `None`: present value with inner `T` vs no valid value.
- `Option<T>` vs `T`: possible absence vs definitely present value; the compiler treats them as different types.
- `Option<i32>` vs `Option<char>`: different concrete `Option<T>` types because `T` differs.

## Section: The match Control Flow Construct

### Learning Objectives

- Learner can describe `match` as a control-flow construct that compares a value against patterns and executes the code for the first matching pattern.
- Learner can identify the parts of a `match`: matched expression, arms, patterns, `=>`, arm code, and comma separators.
- Learner can explain how `match` differs from `if`: `if` conditions must be Boolean, while a `match` expression can match a value of any type against patterns.
- Learner can explain that each match arm's code is an expression and the matching arm's result becomes the value of the whole `match`.
- Learner can use curly braces for a multi-line match arm and explain that the comma after such an arm is optional.
- Learner can bind enum-variant payloads in match patterns, such as `Coin::Quarter(state)`.
- Learner can use `match` to handle `Option<T>` by covering both `Some(T)` and `None`.
- Learner can diagnose E0004 for a non-exhaustive match and explain which variant is missing.
- Learner can use a named catch-all pattern to handle all remaining values while still using the value.
- Learner can use `_` as a catch-all pattern that does not bind the value.
- Learner can use `_ => ()` to explicitly do nothing for all remaining values.
- Learner can explain why catch-all arms must come last.

### Card Content Candidates

#### Concepts

- `match` compares a value against a series of patterns.
- `match` executes code based on which pattern matches.
- Patterns can include literal values, variable names, wildcards, and many other forms.
- Chapter 19 covers the full set of pattern kinds.
- The power of `match` comes from expressive patterns and compiler checking that all possible cases are handled.
- Values are compared with match-arm patterns in order.
- The first pattern that fits the value determines which arm's code runs.
- The `match` keyword is followed by an expression.
- In Listing 6-3, the matched expression is `coin`.
- Unlike an `if` condition, the expression after `match` can be any type.
- In Listing 6-3, the matched expression has type `Coin`.
- A match arm has two parts: a pattern and some code.
- The `=>` operator separates the pattern from the code to run.
- Match arms are separated by commas.
- Listing 6-3 has four match arms for the four `Coin` variants.
- The code associated with each match arm is an expression.
- The resultant value of the matching arm expression is the value returned by the whole `match` expression.
- Short match-arm expressions usually do not use curly braces.
- Multi-line match-arm code must use curly braces.
- When a match arm uses a block, the comma after the arm is optional.
- A match-arm block still returns the block's final expression.
- In the lucky-penny example, the `Coin::Penny` arm prints a line and then returns `1`.
- Match arms can bind to parts of matched values.
- Binding in a match arm is how code extracts values from enum variants.
- `Coin::Quarter(UsState)` stores a `UsState` value inside the `Quarter` variant.
- `Coin::Quarter(state)` matches a `Quarter` and binds the inner `UsState` to `state`.
- For `Coin::Quarter(UsState::Alaska)`, the binding `state` is `UsState::Alaska`.
- After binding `state`, the arm code can use it in `println!`.
- `match` can handle `Option<T>` the same way it handles custom enums.
- Matching `Option<T>` compares against the `None` and `Some` variants.
- `plus_one` takes `Option<i32>` and returns `Option<i32>`.
- In `plus_one`, `None => None` returns no value when no inner value exists.
- In `plus_one`, `Some(i) => Some(i + 1)` binds the inner integer to `i`, adds one, and wraps the result back in `Some`.
- When `plus_one(Some(5))` runs, `Some(5)` does not match `None` and then matches `Some(i)`.
- When `Some(5)` matches `Some(i)`, `i` is bound to `5`.
- When `plus_one(None)` runs, the first arm matches and no other arms are compared.
- A common Rust pattern is to match against an enum, bind variables to data inside variants, and run code based on the variant.
- Match arms must cover all possibilities.
- Rust matches are exhaustive.
- A match that handles `Some(i)` but not `None` for `Option<i32>` is non-exhaustive.
- E0004 is the diagnostic shown for a non-exhaustive match in this section.
- The compiler can identify the missing pattern, such as `None`.
- Exhaustive `Option<T>` matching protects code from assuming a value exists when it may be absent.
- Catch-all patterns allow special actions for a few values and one default action for every other value.
- A named variable pattern, such as `other`, matches any value not matched earlier and binds that value.
- In the dice example, `other => move_player(other)` uses the unmatched dice value.
- A catch-all arm satisfies match exhaustiveness because it covers all remaining values.
- Catch-all arms must be written last because patterns are evaluated in order.
- If a catch-all arm appeared before more specific arms, the later arms would never run.
- Rust warns if code adds arms after a catch-all.
- `_` is a special pattern that matches any value and does not bind to it.
- Use `_` when a catch-all is needed but the value should not be used.
- `_` also avoids an unused-variable warning because it does not bind.
- `_ => reroll()` explicitly handles all remaining dice values by calling `reroll`.
- `_ => ()` explicitly handles all remaining dice values by doing nothing.
