- TCP stands for Transmission Control Protocol.
- Both HTTP and TCP are request-response protocols.
- In a request-response protocol, a client initiates requests.
- In a request-response protocol, a server listens to requests and provides responses.
- TCP is the lower-level protocol.
- TCP describes how information gets from one server to another.
- TCP does not specify what the information means.
- HTTP builds on top of TCP by defining the contents of requests and responses.
- HTTP can technically be used with other protocols, but most HTTP traffic sends data over TCP.
- This project works with raw bytes of TCP and HTTP requests and responses.
- The first implementation goal is listening to a TCP connection.

#### Failure Modes

- Treating TCP and HTTP as the same layer misses that HTTP defines request/response contents while TCP moves bytes.
- Assuming `bind` cannot fail misses port conflicts and other networking errors.
- Treating `incoming()` items as guaranteed connections misses that they are connection attempts and can error.
- Expecting one browser page load to equal one TCP stream ignores browser behavior such as favicon requests, retries, and idle preconnections.
- Forgetting to stop and rerun the server after code changes can leave an older server version running.
- Reading stream lines with `unwrap` can crash on invalid UTF-8 or read errors; the book accepts this only for a learning server.
- Reading until an empty line is important; otherwise one request boundary is not identified correctly.
- Omitting the HTTP response entirely leads browsers to show connection errors.
- Omitting `Content-Length` from a response with a body risks an invalid or ambiguous response in this project.
- Ignoring the request line makes every path return the same page.
- Only handling `/` without an `else` response causes other paths to fail with connection errors.
- Duplicating response construction in every route branch makes later response changes error-prone.
- Treating this single-threaded server as scalable misses that it can serve only one request at a time.

#### Comparisons

- TCP vs HTTP: TCP is lower-level byte transport; HTTP defines the text request and response content sent over TCP.
- Client vs server: the client initiates requests; the server listens and responds.
- Connection attempt vs successful stream: `incoming()` yields attempts that can fail; successful attempts are unwrapped to `TcpStream`.
- Request line vs headers: the request line says method/URI/version; headers provide additional metadata after it.
- URI vs URL: the book says they are almost but not quite the same and treats the distinction as unimportant for this chapter.
- Request format vs response format: requests start with method/URI/version; responses start with version/status-code/reason phrase.
- Tiny response vs HTML response: the tiny response has only `HTTP/1.1 200 OK\r\n\r\n`; the HTML response adds `Content-Length` and a body.
- Listing 21-5 vs Listing 21-7: Listing 21-5 ignores path and always returns `hello.html`; Listing 21-7 returns `hello.html` for `/` and `404.html` otherwise.
- Listing 21-7 vs Listing 21-9: Listing 21-7 duplicates response writing in branches; Listing 21-9 factors route differences into `(status_line, filename)`.
- Single-threaded server vs later concurrent server: this section serves one request at a time; later sections improve handling of simultaneous requests.

#### Project / Architecture Decisions

- Use `TcpListener` from the standard library to keep the project low-level and educational.
- Use port `7878` to avoid normal HTTP-port conflicts during local development.
- Use `unwrap` in this learning project to keep examples focused, while recognizing production code needs real error handling.

#### Failure Modes

- Treating the single-threaded server as concurrent misses that it handles one stream to completion before the next stream.
- Forgetting to rerun the server after adding `/sleep` can make the blocking demonstration misleading.
- Assuming a browser always sends requests in the order or concurrency pattern expected can make testing confusing because of browser behavior and caching.
- Matching on the owned `String` instead of a string slice can produce type mismatch confusion when comparing to string literals.
- Treating one-thread-per-request as the final fix ignores denial-of-service and resource-exhaustion risks.
- Treating a thread pool as unlimited concurrency misses the point of bounding active worker threads.
- Assuming a fixed pool eliminates all waiting is wrong; requests can still queue when all workers are busy.
- Assuming "code compiles" means the thread pool works misses that the initial `execute` implementation compiles while doing nothing.
- Choosing `i32` for pool size would allow a nonsensical negative thread count in the API.
- Allowing `ThreadPool::new(0)` creates a pool that can never execute work.
- Ignoring the result-returning alternative for pool creation can blur panic-vs-recoverable API design.
- Storing only `JoinHandle<()>` values is not enough to let threads receive jobs after creation.
- Making `Worker` public would expose implementation details that users of the pool do not need.
- Passing the channel receiver by value to every worker fails because the receiver is moved.
- Trying to clone the receiver would not match the desired semantics of one queued job being handled once.
- Sharing the receiver without a mutex would allow unsynchronized mutation from multiple workers.
- Forgetting `Arc` prevents multiple workers from owning the shared receiver across threads.
- Forgetting `move` on the worker closure would prevent the thread from owning the cloned receiver as needed.
- Omitting `Send` from `Job` would make it unsafe or impossible to move jobs between threads.
- Omitting `'static` from `Job` would allow jobs that might reference data that does not live long enough for the worker thread.
- Holding the mutex guard during `job()` can serialize work and erase most of the thread pool's benefit.
- Rewriting the receive loop as `while let` without understanding temporary lifetimes can reintroduce the exact blocking behavior the pool was meant to fix.
- This section leaves worker shutdown unresolved; infinite worker loops are cleaned up in the next section.

#### Comparisons

- Single-threaded server vs thread pool: the single-threaded server handles one request at a time; the thread pool lets several workers handle jobs concurrently.
- Thread per request vs thread pool: thread per request is simple but unbounded; the pool bounds resource use and queues extra jobs.
- Thread pool vs async: the book mentions async as another possible technique but implements a thread pool for this project.
- Desired API first vs implementation first: the section writes `ThreadPool::new` and `pool.execute` usage first, then lets compiler errors guide implementation.
- TDD vs compiler-driven development: TDD uses failing tests to drive behavior; this section uses compiler failures to drive API implementation.
- Compile success vs behavior success: compile success proves type checking, not that the no-op `execute` implementation actually handles requests.
- `usize` vs signed integer pool size: `usize` matches collection lengths and avoids negative sizes, but still needs a zero check.
- Panic on zero size vs `Result` return: the book chooses panic because a zero-thread pool is unrecoverable here; a production API might return a custom error.
- Raw `JoinHandle<()>` storage vs `Worker`: raw handles store threads, but `Worker` can carry identity and later receive pool jobs.
- Private worker internals vs public pool API: users call `ThreadPool`; `Worker` is an implementation detail.
- `mpsc::Sender<Job>` vs `mpsc::Receiver<Job>`: the pool sends submitted jobs; workers receive jobs to execute.
- `Arc` vs `Mutex`: `Arc` gives shared ownership across workers; `Mutex` gives exclusive mutable access to the receiver.
- Placeholder `struct Job` vs boxed closure job: the placeholder lets the channel shape compile; the boxed trait object is the actual executable unit of work.
- Listing 21-20 `let` receive loop vs Listing 21-21 `while let`: both compile, but the `let` version drops the lock guard before `job()` while the `while let` version holds it through `job()`.

#### Project / Architecture Decisions

- Keep the server educational and low-level rather than using a production web framework or production thread pool crate.
- Demonstrate the blocking problem concretely with `/sleep` before introducing concurrency.
- Use a `match` over the request line when route count grows beyond the basic root-vs-other split.
- Show one-thread-per-request as a useful intermediate step, then reject it as the final design because it is unbounded.
- Use a fixed-size pool of four workers in the example to make concurrency visible while keeping resource use bounded.
- Design the public interface from the caller's point of view: `ThreadPool::new(size)` plus `execute`.
- Put `ThreadPool` in `src/lib.rs` so it can be imported by the binary with `use hello::ThreadPool`.
- Store workers in the pool even though the field is not directly read yet; later cleanup needs those handles.
- Use a channel as the job queue between the accepting loop and worker threads.
- Use one shared receiver so each job is handled by exactly one worker.
- Use `Arc<Mutex<_>>` around the receiver because it must be owned by multiple workers and mutated safely.
- Use boxed `FnOnce + Send + 'static` closures to represent request-handling jobs uniformly.
- Use `unwrap` for channel send/receive and mutex locking in the learning implementation, while recording the production failure cases.

#### Failure Modes

- Treating Ctrl-C as graceful cleanup misses that it stops all threads immediately, including in-progress requests.
- Calling `join` on borrowed `worker.thread` fails because `JoinHandle::join` consumes the handle.
- Ignoring E0507 would leave the pool unable to compile its cleanup code.
- Wrapping a value in `Option` only because moving it is awkward can make all later access more error-prone.
- Using `Option<JoinHandle<()>>` everywhere before checking for a cleaner ownership move can add unnecessary complexity.
- Using `Vec::drain(..)` for workers without understanding that it empties the vector could surprise code that expects workers to remain after `drop`.
- Unwrapping `join` during panic unwinding can cause a double panic and abort cleanup.
- Joining worker threads before telling them to stop can block forever.
- Dropping only the pool value without dropping the sender leaves workers blocked in `recv`.
- Keeping another sender clone alive would keep the channel open and prevent workers from seeing `recv` errors.
- Continuing to call `recv().unwrap()` after sender shutdown would panic instead of shutting down gracefully.
- Forgetting the `Err(_) => break` arm leaves worker threads stuck in the receive loop.
- Dropping the sender after joining workers is the wrong order because the workers need the closed channel signal before they can exit.
- Treating the two-request server as production behavior misses that it is only a shutdown demonstration.
- Assuming shutdown logs always appear in the same order ignores nondeterministic thread scheduling.
- Keeping `unwrap` calls in production cleanup can turn recoverable or diagnosable failures into panics.
- Assuming the chapter's thread pool is production-ready contradicts the source's future-improvement list and earlier educational framing.

#### Comparisons

- Abrupt shutdown vs graceful shutdown: Ctrl-C stops all threads immediately; graceful shutdown lets current jobs finish and then joins worker threads.
- Joining threads vs signaling threads: joining waits for threads to finish; dropping the sender gives workers a reason to finish.
- `Vec::drain(..)` vs `Option<JoinHandle<()>>::take`: `drain` moves owned workers out of the vector; `Option::take` moves one field value out and leaves `None`.
- `Option<JoinHandle<()>>` workaround vs cleaner ownership move: the source prefers avoiding `Option` when the value is always present and a cleaner move is available.
- Worker handle `Option::take` in final reference code vs source's first `Vec::drain(..)` fix: both let `join` consume a handle; the final code also demonstrates the field-level `take` pattern.
- `sender: mpsc::Sender<Job>` vs `sender: Option<mpsc::Sender<Job>>`: plain sender is enough for normal job submission; optional sender lets `Drop` move and drop the sender before joining workers.
- `recv().unwrap()` vs matching `recv()`: unwrap panics on channel closure; matching lets workers treat closure as a shutdown signal.
- `Iterator::take(2)` demo vs real server loop: the demo proves cleanup; a real server would not stop after two requests.
- Example cleanup vs production cleanup: the example still uses `unwrap`; production code would use more robust error handling.
- Thread pool for web server vs thread pool for async runtime: this section's cleanup mechanics are the same because they do not depend on the submitted job's contents.

#### Project / Architecture Decisions

- Implement `Drop` on `ThreadPool` so cleanup is tied to normal ownership and scope exit.
- Join worker threads during `ThreadPool` cleanup to wait for active requests to finish.
- Move worker handles before joining them because `join` consumes `JoinHandle<()>`.
- Use `Vec::drain(..)` in the source's first fix to move workers out of the pool without wrapping their thread handles in `Option`.
- Store `sender` as `Option<mpsc::Sender<Job>>` because `Drop` must move it out and close the channel before joining.
- Drop the sender before joining workers so `recv` returns `Err` and worker loops can stop.
- Treat channel disconnection as the worker shutdown signal.
- Keep worker job execution unchanged; shutdown is expressed through channel ownership and loop control.
- Use `listener.incoming().take(2)` only as a visible demonstration of the shutdown path.
- Keep the project's final result educational: a basic web server with a manually implemented thread pool and graceful cleanup, not a production web framework.
