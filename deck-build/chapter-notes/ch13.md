### Card Content Candidates

#### Concepts

- Closures are anonymous functions.
- Closures can be saved in variables.
- Closures can be passed as arguments to other functions.
- A closure can be created in one place and called later in a different context.
- Unlike functions, closures can capture values from the scope where they are defined.
- Closure capture enables code reuse and behavior customization.
- Listing 13-1 models a shirt giveaway using `ShirtColor` and `Inventory`.
- `ShirtColor` has `Red` and `Blue` variants.
- `Inventory` stores current stock in `shirts: Vec<ShirtColor>`.
- `Inventory::giveaway` takes `user_preference: Option<ShirtColor>`.
- If `user_preference` is `Some`, `unwrap_or_else` returns the contained preference.
- If `user_preference` is `None`, `unwrap_or_else` calls the closure and returns its result.
- `Option<T>::unwrap_or_else` takes a closure with no arguments that returns `T`.
- In Listing 13-1, `T` is `ShirtColor`.
- The closure expression `|| self.most_stocked()` takes no parameters.
- The two vertical pipes contain closure parameters; empty pipes mean the closure takes no parameters.
- `|| self.most_stocked()` calls `self.most_stocked()` when evaluated.
- The `unwrap_or_else` implementation evaluates the closure only if it needs the fallback value.
- The closure in Listing 13-1 captures an immutable reference to `self`.
- The standard library does not need to know `Inventory`, `ShirtColor`, or giveaway logic because the closure carries that behavior.
- Functions cannot capture their environment in the same way closures can.
- Closures usually do not require parameter or return type annotations.
- Function type annotations are required because functions expose an explicit interface to users.
- Closures are usually stored in variables or used anonymously without being part of an exposed interface.
- Closures are usually short and relevant only in a narrow context.
- Within narrow contexts, the compiler can infer closure parameter and return types.
- Closure type annotations are allowed when explicitness is worth the extra verbosity.
- Listing 13-2 stores a fully annotated closure in a variable.
- Closure syntax uses pipes around parameters rather than parentheses.
- Closure return type annotations use `->` like function return type annotations.
- Braces are optional for a closure body that has only one expression.
- `|x| x + 1` is a one-expression closure body without braces.
- The compiler must evaluate how an inferred closure is used to infer types.
- A closure definition without type annotations is still monomorphic after inference.
- The compiler infers one concrete type for each closure parameter and return value.
- Listing 13-3 first calls `example_closure` with `String`.
- After the first call, the closure parameter and return type are inferred as `String`.
- Calling the same closure later with an integer causes E0308.
- Closure captures map to function parameter passing modes: immutable borrow, mutable borrow, and ownership.
- A closure chooses its capture mode based on what its body does with captured values.
- Listing 13-4 captures `list` by immutable reference because it only prints `list`.
- A variable can bind to a closure definition.
- A closure stored in a variable can be called with the variable name and parentheses.
- Multiple immutable references can coexist, so `list` remains accessible before and after the immutable-capturing closure call.
- Listing 13-5 captures `list` by mutable reference because the closure pushes into the vector.
- The closure variable must be mutable when calling it mutates captured state through the closure.
- While a closure holds a mutable borrow, no other borrows of that captured value are allowed.
- In Listing 13-5, no `println!` appears between closure definition and call because that would borrow `list` immutably while the mutable borrow is active.
- The mutable borrow ends after the closure is called and not used again.
- The `move` keyword before the closure parameter list forces ownership capture.
- `move` can force ownership capture even when the closure body only needs an immutable reference.
- `move` is especially useful when passing a closure to a new thread.
- Listing 13-6 passes a closure to `thread::spawn`.
- The spawned thread may outlive the main thread's current operations.
- If the main thread kept ownership and dropped `list` before the spawned thread used it, an immutable reference in the thread would be invalid.
- Therefore, the compiler requires `list` to move into the closure passed to the new thread.
- Removing `move` from Listing 13-6 or using `list` in the main thread after the closure is defined causes compiler errors.
- Capture mode affects what moves into a closure.
- The closure body affects what moves out of a closure when it is evaluated.
- A closure body can move a captured value out, mutate a captured value, neither move nor mutate it, or capture nothing.
- Closure capture and body behavior determine which `Fn` traits the closure implements.
- `Fn` traits let functions and structs specify what kinds of closures they can use.
- Closures automatically implement one, two, or all three `Fn` traits in an additive fashion.
- `FnOnce` applies to closures that can be called once.
- All closures implement at least `FnOnce`.
- A closure that moves captured values out of its body implements only `FnOnce`.
- A `FnOnce`-only closure can only be called once because moved captured values are no longer available for a second call.
- `FnMut` applies to closures that do not move captured values out but might mutate captured values.
- `FnMut` closures can be called more than once.
- `Fn` applies to closures that do not move captured values out and do not mutate captured values.
- `Fn` also applies to closures that capture nothing.
- `Fn` closures can be called more than once without mutating their environment.
- `Fn` is important when calling a closure multiple times concurrently.
- `Option<T>::unwrap_or_else` has an extra generic type parameter `F` for the closure argument.
- The `unwrap_or_else` bound is `F: FnOnce() -> T`.
- `FnOnce() -> T` means the closure can be called once, takes no arguments, and returns `T`.
- `unwrap_or_else` uses `FnOnce` because it will not call the fallback closure more than once.
- If an `Option` is `Some`, `unwrap_or_else` does not call the closure.
- If an `Option` is `None`, `unwrap_or_else` calls the closure once.
- Because all closures implement `FnOnce`, `unwrap_or_else` accepts all three closure kinds and is maximally flexible.
- If no environment capture is needed, a function name can be used where an `Fn` trait implementation is expected.
- `unwrap_or_else(Vec::new)` can create a new empty vector for `Option<Vec<T>>::None`.
- The compiler implements applicable `Fn` traits for function definitions.
- `sort_by_key` is defined on slices.
- `sort_by_key` takes a closure argument that receives a reference to each item.
- The `sort_by_key` closure returns a key value that can be ordered.
- Listing 13-7 uses `sort_by_key(|r| r.width)` to sort rectangles by width.
- `sort_by_key` uses `FnMut` because it calls the closure multiple times, once for each item in the slice.
- The closure `|r| r.width` captures nothing, mutates nothing, and moves nothing out.
- Listing 13-8 tries to push a captured `String` named `value` into `sort_operations`.
- Pushing `value` moves ownership of `value` out of the closure environment.
- That closure is only `FnOnce`, because `value` could not be moved again on a second call.
- `sort_by_key` requires `FnMut`, so the Listing 13-8 closure fails to compile.
- E0507 reports that `value` cannot be moved out of a captured variable in an `FnMut` closure.
- Listing 13-9 fixes the counting example by capturing a mutable reference to `num_sort_operations`.
- Incrementing `num_sort_operations` mutates captured state without moving it out.
- The Listing 13-9 closure can be called more than once and works with `sort_by_key`.
- Many iterator methods take closure arguments, so closure traits matter for the next section.

- Assuming closures are just named functions; closures are anonymous and can capture environment values.
- Forgetting that `unwrap_or_else` evaluates its closure lazily only when the fallback is needed.
- Putting closure parameters outside the `|...|` pipes.
- Over-annotating closures as if they always require function-like type annotations.
- Assuming an unannotated closure is generic over all future argument types.
- Calling the same inferred closure with `String` and then integer values.

- Using a moved-into-closure value again in the original thread.

- Trying to count sort operations by moving a `String` into a vector on every closure call.

#### Comparisons

- Function vs closure: functions have explicit interface types and cannot capture local environment; closures can infer types and capture local values.
- Annotated closure vs inferred closure: annotations improve explicitness but are often unnecessary in narrow contexts.
- Closure with braces vs without braces: braces can be omitted when the closure body is one expression.
- `Some` path vs `None` path in `unwrap_or_else`: `Some` returns the contained value; `None` evaluates the fallback closure.
- Immutable capture vs mutable capture: immutable capture allows other immutable uses; mutable capture excludes other borrows while active.
- Borrow capture vs ownership capture: borrow capture references external data; `move` can transfer ownership into the closure.
- Moving into a closure vs moving out of a closure: capture decides what enters the closure; body behavior decides what leaves when called.
- `FnOnce` vs `FnMut` vs `Fn`: `FnOnce` can be called once, `FnMut` can be called repeatedly while mutating, and `Fn` can be called repeatedly without mutating.
- `unwrap_or_else` vs `sort_by_key`: `unwrap_or_else` may call the closure once and uses `FnOnce`; `sort_by_key` calls the closure multiple times and uses `FnMut`.
- Closure fallback vs function fallback: a closure can capture environment; a function name such as `Vec::new` can be used when no capture is required.
- Moving `value` into `sort_operations` vs incrementing a counter: moving `value` makes the closure `FnOnce`; incrementing a counter only needs mutable capture and works as `FnMut`.

#### Concepts

- Iterators process a series of items.
- The iterator pattern lets code perform a task on a sequence of items in turn.
- An iterator is responsible for the logic of iterating over each item.
- An iterator is responsible for determining when the sequence is finished.
- Code that uses iterators does not need to reimplement sequence traversal logic.
- Iterator use can avoid manual index variables and index incrementing.
- Iterators are flexible enough to handle many kinds of sequences, not just vectors.
- Rust iterators are lazy.
- Lazy iterators have no effect until a method consumes them.
- Calling `v1.iter()` creates an iterator over `v1` but does not use the iterator.
- A `for` loop consumes an iterator by repeatedly retrieving values from it.
- Listing 13-11 prints each item from `v1_iter` as `Got: {val}`.
- The `Iterator` trait is in the standard library.
- Implementing the `Iterator` trait requires defining only `next`.
- The `Iterator` trait has an associated type named `Item`.
- `Item` is the type returned from the iterator.
- `Self::Item` refers to that associated item type in the `next` return type.
- Associated types are covered in more detail in Chapter 20; this section only needs the iterator-return-type meaning.
- `next` returns `Option<Self::Item>`.
- `next` returns `Some(item)` while the iterator still has items.
- `next` returns `None` after iteration is over.
- Calling `next` directly requires a mutable iterator variable because `next` changes the iterator's internal state.
- Each `next` call uses up one item from the iterator.
- A `for` loop can use a non-`mut` iterator variable because the loop takes ownership of the iterator and makes it mutable internally.
- `iter` produces an iterator over immutable references.
- `into_iter` produces an iterator that takes ownership of the collection and returns owned values.
- `iter_mut` produces an iterator over mutable references.
- Many `Iterator` methods have default implementations that call `next`.
- Consuming adapters are methods that call `next`.
- Consuming adapters use up the iterator.
- `sum` is a consuming adapter.
- `sum` takes ownership of an iterator, repeatedly calls `next`, adds the items, and returns the total.
- After `sum` consumes an iterator, that iterator cannot be used again.
- Iterator adapters are methods that return a new iterator.
- Iterator adapters do not consume the original iterator immediately.
- Iterator adapters are lazy and do nothing until consumed.
- `map` is an iterator adapter.
- `map` takes a closure to call on each item.
- Calling `v1.iter().map(|x| x + 1);` creates a lazy `Map` iterator but does not call the closure because nothing consumes it.
- The compiler warns about an unused `Map` result because the resulting iterator must be used.
- `collect` consumes an iterator and gathers its values into a collection.
- `collect` often needs a type annotation because many collection types can be built from an iterator.
- `let v2: Vec<_> = v1.iter().map(|x| x + 1).collect();` consumes the mapped iterator into a vector.
- In Listing 13-15, `v2` is `[2, 3, 4]`.
- Iterator adapter calls can be chained.
- A chain of iterator adapters needs a consuming adapter, such as `collect`, to produce results.
- `filter` is an iterator adapter.
- `filter` takes a closure that receives each item from an iterator.
- The `filter` closure returns `true` to keep an item.
- The `filter` closure returns `false` to omit an item.
- In Listing 13-16, `shoes_in_size` consumes a vector of `Shoe` values and returns only shoes with the requested size.
- The closure `|s| s.size == shoe_size` captures `shoe_size` from its environment.
- In Listing 13-16, `into_iter` takes ownership of the `shoes` vector.
- In Listing 13-16, `collect` gathers the filtered owned `Shoe` values into a `Vec<Shoe>`.
- Iterator adapters use closures to customize behavior while preserving reusable traversal logic from the `Iterator` trait.

#### Comparisons

- Consuming adapters vs iterator adapters: consuming adapters call `next` and use up the iterator; iterator adapters return another lazy iterator.

- `collect` in CH-13 vs `collect` in CH-12: both consume an iterator into a collection and both may need type context such as `Vec<_>` or `Vec<String>`.
