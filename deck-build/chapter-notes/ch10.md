### Card Content Candidates

#### Concepts

- Generics are one Rust tool for handling duplication of concepts.
- A generic is an abstract stand-in for a concrete type or another property.
- Generic code can express behavior without knowing the concrete replacement that will be used at compile time and runtime.
- A function can take a parameter of a generic type instead of a concrete type such as `i32` or `String`.
- Generic type parameters are analogous to function value parameters: the same code can operate on multiple concrete inputs.
- The book has already used generics in `Option<T>`, `Vec<T>`, `HashMap<K, V>`, and `Result<T, E>`.
- CH-10 teaches how to define custom types, functions, and methods with generics.
- CH-10 starts with ordinary function extraction to reduce duplication before introducing generic syntax.
- CH-10 then generalizes the same extraction technique to functions that differ only in parameter types.
- Generic types can be used in struct and enum definitions.
- Traits define behavior in a generic way.
- Traits can be combined with generic types to constrain a generic type to types that have particular behavior.
- Lifetimes are a variety of generics that describe how references relate to each other.
- Lifetimes give the compiler enough information about borrowed values to prove references are valid in more situations.
- Listing 10-1 stores a list of integers and keeps a reference named `largest` to the largest value seen so far.
- Listing 10-1 initializes `largest` to a reference to the first number in the list.
- Listing 10-1 iterates through references to the numbers in the list.
- Listing 10-1 replaces `largest` when the current number is greater than the largest value seen so far.
- Listing 10-1 leaves `largest` unchanged when the current number is less than or equal to the current largest.
- After the loop in Listing 10-1, `largest` refers to the largest number in the list, `100`.
- Listing 10-2 duplicates the largest-number loop to process two different integer lists.
- Duplicated code is tedious because the same logic is repeated in multiple places.
- Duplicated code is error-prone because changes must be remembered and applied in every duplicated location.
- Listing 10-3 removes duplication by extracting the largest-number logic into a function named `largest`.
- The extracted `largest` function operates on any concrete slice of `i32` values passed to it.
- Calling `largest(&number_list)` runs the function body on the specific list passed in.
- Function extraction creates an abstraction for the concept of finding the largest number in a list.
- The book's three extraction steps are: identify duplicate code; extract it into a function with inputs and return values in the signature; update duplicate sites to call the function.
- A function parameter such as `list` is an abstraction over multiple concrete values.
- A generic type parameter is an abstraction over multiple concrete types.
- The next section applies the same duplication-removal idea to two functions that differ only by element type, such as `i32` and `char`.

#### Comparisons

- Concrete type parameter vs generic type parameter: a concrete parameter such as `i32` fixes the accepted type; a generic parameter can stand in for multiple concrete types.
- Function value parameter vs generic type parameter: a value parameter abstracts over values; a generic type parameter abstracts over types or other properties.
- Duplicated loop vs extracted function: duplicated loop repeats logic in multiple places; extracted function names the concept once and calls it from each site.
- Listing 10-2 vs Listing 10-3: Listing 10-2 repeats the largest-number algorithm; Listing 10-3 puts the algorithm in `largest`.
- `list: &[i32]` vs `number_list`: the function parameter is an abstraction over any concrete `i32` slice passed by the caller.
- Generic types vs traits: generic types abstract over type placeholders; traits define behavior that can constrain those placeholders.
- Traits vs lifetimes: traits describe required behavior; lifetimes describe relationships among references.
- CH-10 overview vs later CH-10 sections: the overview introduces roadmap and function extraction; later sections cover generic syntax, trait bounds, and lifetime annotations in detail.

### Card Content Candidates

#### Concepts

- Generic definitions can be used for function signatures, structs, enums, and methods.
- Generic definitions let one item work with many concrete data types.
- Generic type parameters go in the function signature where concrete parameter and return types would normally appear.
- Declaring generic type parameters makes code more flexible and avoids duplication.
- Listing 10-4 has `largest_i32` and `largest_char`, which differ only by name and signature types.
- `largest_i32` works on `&[i32]` and returns `&i32`.
- `largest_char` works on `&[char]` and returns `&char`.
- The body of `largest_i32` and `largest_char` is otherwise the same.
- A generic type parameter must be named before it can be used in a signature.
- Rust generic type parameter names are usually short, often one letter.
- Rust type parameter names use UpperCamelCase.
- `T` is the conventional default generic type parameter name because it is short for "type."
- Generic type declarations go inside angle brackets after the function name and before the parameter list.
- `fn largest<T>(list: &[T]) -> &T` means `largest` is generic over some type `T`.
- In `fn largest<T>(list: &[T]) -> &T`, `list` is a slice of values of type `T`.
- In `fn largest<T>(list: &[T]) -> &T`, the return value is a reference to a value of the same type `T`.
- Listing 10-5 calls the generic `largest` with both `i32` and `char` slices.
- Listing 10-5 does not compile because `T` could be any type and not every type can be compared with `>`.
- The compiler error for Listing 10-5 is E0369: binary operation `>` cannot be applied to type `&T`.
- The compiler help suggests restricting `T` with `std::cmp::PartialOrd`.
- `PartialOrd` is the standard-library trait for values that can be ordered for comparisons such as `>`.
- The book defers detailed trait discussion to the next section.
- Generic structs declare type parameters after the struct name.
- A generic struct can use its type parameter anywhere it would otherwise specify a concrete field type.
- `struct Point<T> { x: T, y: T }` is generic over one type `T`.
- In `Point<T>`, both `x` and `y` must have the same concrete type for each instance.
- When `Point { x: 5, y: 10 }` is created, `T` is inferred as an integer type for that instance.
- When `Point { x: 1.0, y: 4.0 }` is created, `T` is inferred as a floating-point type for that instance.
- `Point { x: 5, y: 4.0 }` does not compile for `Point<T>` because `x` and `y` would need different concrete types.
- Multiple generic type parameters allow fields to have different concrete types.
- `struct Point<T, U> { x: T, y: U }` lets `x` and `y` have different types.
- Using many generic type parameters can make code hard to read.
- Needing many generic type parameters can indicate code should be restructured into smaller pieces.
- Generic enums can hold generic data in their variants.
- `Option<T>` is generic over one type `T`.
- `Some(T)` holds one value of type `T`.
- `None` holds no value.
- `Option<T>` expresses the abstract concept of an optional value for any contained type.
- `Result<T, E>` is generic over two types.
- `Ok(T)` holds a success value of type `T`.
- `Err(E)` holds an error value of type `E`.
- `Result<T, E>` expresses operations that might succeed with one type or fail with another type.
- In the file-open example from Chapter 9, `Result<T, E>` used `std::fs::File` for `T` and `std::io::Error` for `E`.
- If multiple struct or enum definitions differ only in contained value types, generic types can remove the duplication.
- Generic methods can be implemented on generic structs and enums.
- `impl<T> Point<T>` declares `T` after `impl` so methods can refer to the generic `T`.
- Declaring `T` after `impl` tells Rust the `T` in `Point<T>` is a generic type parameter, not a concrete type.
- A method inside `impl<T> Point<T>` is defined for any `Point<T>` instance, regardless of the concrete type substituted for `T`.
- The method `fn x(&self) -> &T` returns a reference to the `x` field.
- Methods can also be implemented only for a specific concrete instantiation of a generic type.
- `impl Point<f32>` defines methods only for `Point<f32>`.
- `distance_from_origin` exists on `Point<f32>` because it uses floating-point operations.
- A `Point<T>` where `T` is not `f32` does not get `distance_from_origin` from `impl Point<f32>`.
- Struct-level generic parameters and method-level generic parameters do not have to be the same.
- Listing 10-11 uses `X1` and `Y1` for the struct instance receiving the method.
- Listing 10-11 uses `X2` and `Y2` only in the `mixup` method signature.
- `mixup` returns a new `Point<X1, Y2>` using `x` from `self` and `y` from the other point.
- For `p1: Point<i32, f64>` and `p2: Point<&str, char>`, `p1.mixup(p2)` produces `Point<i32, char>`.
- Generic types usually have no runtime slowdown compared with concrete types.
- Rust achieves efficient generics through compile-time monomorphization.
- Monomorphization turns generic code into specific code by filling in the concrete types used by the program.
- During monomorphization, the compiler looks at every place generic code is called and generates concrete-type-specific code.
- For `Some(5)` and `Some(5.0)`, the compiler sees `Option<i32>` and `Option<f64>`.
- The book's illustrative monomorphized code shows separate `Option_i32` and `Option_f64` enum definitions.
- Because monomorphization produces concrete code, generic code runs as though each concrete definition had been duplicated by hand.

- Claiming generics are slower at runtime in typical Rust code; the book states monomorphization avoids that runtime cost.

#### Comparisons

- `largest_i32` vs `largest_char`: same algorithm and body structure, different concrete element and return-reference types.
- Concrete largest functions vs generic `largest<T>`: concrete functions duplicate logic; generic signature removes type-specific duplication but needs trait constraints for operations such as `>`.
- Function value parameter vs type parameter: a value parameter must be declared before use in a body; a type parameter must be declared before use in a signature.
- `Point<T>` vs `Point<T, U>`: one type parameter forces both fields to one concrete type; two type parameters allow different field types.
- `Option<T>` vs `Result<T, E>`: optional value abstraction with one generic type vs success-or-error abstraction with separate success and error types.
- Generic struct fields vs generic enum variants: structs use generic fields; enums use generic payloads in variants.
- `impl<T> Point<T>` vs `impl Point<f32>`: methods for every concrete `Point<T>` instantiation vs methods only for `Point<f32>`.
- Struct-level generics vs method-level generics: `X1`/`Y1` belong to the receiver type; `X2`/`Y2` belong only to the `mixup` method call.
- Generic source code vs monomorphized code: programmer writes one generic definition; compiler generates concrete definitions for used types.
- Hand-duplicated concrete definitions vs monomorphization: hand duplication is manual and error-prone; monomorphization performs equivalent specialization automatically at compile time.

#### Concepts

- A trait defines functionality a type has and can share with other types.

- `'a` is the conventional first lifetime parameter name.
- Lifetime annotations are placed after `&`, with a space before the referenced type.
- One lifetime annotation by itself has little meaning; its purpose is to relate multiple references.
- Generic lifetime parameters are declared in angle brackets between the function name and parameter list.
- In `fn longest<'a>(x: &'a str, y: &'a str) -> &'a str`, all three references are tied to the same generic lifetime parameter.
- The `longest` signature states that the returned reference is valid as long as both parameters are valid.
- In practice, the returned reference lifetime is the smaller of the lifetimes of the two argument referents.
- The `longest` function does not need to know exactly how long `x` and `y` live.
- The caller must pass references that satisfy a concrete lifetime that can be substituted for `'a`.
- Lifetime annotations in functions belong in the signature, not the body.
- Lifetime annotations are part of a function's contract, like types in the signature.
- When concrete references are passed to `longest`, `'a` is the overlapping part of the scopes of `x` and `y`.
- Listing 10-22 compiles because `result` is used while both `string1` and `string2` are still valid.
- Listing 10-23 fails because `result` is used after `string2` goes out of scope.
- Listing 10-23's diagnostic is E0597: `string2` does not live long enough.
- Humans can see Listing 10-23 will return `string1`, but the compiler uses the declared lifetime relationship rather than branch-specific string contents.
- Lifetime annotations should match what the function actually does.
- If a function always returns `x`, only `x` and the return type need the same lifetime; `y` can have an unrelated lifetime.
- A returned reference lifetime must match the lifetime of one of the parameters if the returned reference comes from a parameter.
- Returning a reference to a value created inside the function would create a dangling reference.
- No lifetime annotation can make a reference to a local value valid after the local value is dropped.
- The best fix for returning locally created data is usually to return an owned value.
- Lifetime syntax connects parameters and return values so Rust can allow memory-safe operations and reject dangling pointers.
- Structs that hold references need lifetime annotations on those references.
- `ImportantExcerpt<'a>` declares a generic lifetime parameter after the struct name.
- `part: &'a str` means an `ImportantExcerpt<'a>` instance cannot outlive the reference stored in `part`.
- In Listing 10-24, `novel` exists before `ImportantExcerpt` is created and outlives it, so the stored reference is valid.
- Lifetime elision rules let common lifetime patterns compile without explicit annotations.
- Lifetime elision rules are deterministic compiler rules, not rules programmers manually apply to change semantics.
- Elision rules do not provide full lifetime inference.
- If ambiguity remains after the elision rules, the compiler reports an error instead of guessing.
- Lifetimes on function or method parameters are input lifetimes.
- Lifetimes on return values are output lifetimes.
- Elision rule 1: the compiler assigns a lifetime parameter to each parameter that is a reference.
- Elision rule 2: if there is exactly one input lifetime parameter, that lifetime is assigned to all output lifetime parameters.
- Elision rule 3: if there are multiple input lifetime parameters and one is `&self` or `&mut self`, the lifetime of `self` is assigned to all output lifetime parameters.
- The elision rules apply to `fn` definitions and `impl` blocks.
- `first_word(s: &str) -> &str` compiles because rule 1 gives `s` a lifetime and rule 2 assigns that lifetime to the output.
- The original `longest(x: &str, y: &str) -> &str` fails elision because rule 1 gives two input lifetimes, rule 2 does not apply, and rule 3 does not apply to a non-method function.
- Methods often need fewer explicit lifetime annotations because of elision rule 3.
- When implementing methods on a struct with lifetimes, lifetimes tied to struct fields are declared after `impl` and used after the struct name.
- In `impl<'a> ImportantExcerpt<'a>`, `'a` is part of the struct type.
- The `level(&self) -> i32` method does not need an explicit `self` lifetime because the output is not a reference.
- The `announce_and_return_part(&self, announcement: &str) -> &str` method has two input lifetimes but rule 3 assigns the output lifetime to `&self`.
- `'static` means the affected reference can live for the entire duration of the program.
- All string literals have the `'static` lifetime.
- String literal text is stored directly in the program binary and is always available.
- Error suggestions to use `'static` often indicate an attempted dangling reference or lifetime mismatch.
- Most of the time, the right fix is to solve the dangling reference or lifetime mismatch rather than adding `'static`.
- Lifetimes are generic parameters and can appear in the same angle-bracket list as generic type parameters.
- `longest_with_an_announcement<'a, T>` combines a lifetime parameter `'a`, a type parameter `T`, a `where` clause requiring `T: Display`, and references tied to `'a`.
- Generic type parameters apply code to different types.
- Trait bounds ensure generic types have required behavior.
- Lifetime annotations ensure flexible borrowed code does not produce dangling references.
- Generic type, trait-bound, and lifetime analysis happens at compile time and does not affect runtime performance.

#### Prediction / Diagnostic Examples

- Given Listing 10-16, diagnose E0597 because `r` would point to `x` after `x` is dropped.
- Given lifetimes `'a` for `r` and `'b` for inner `x`, reject the program when `'b` is shorter than `'a`.
- Given Listing 10-18, predict it compiles because `x` outlives `r`.
- Given `fn longest(x: &str, y: &str) -> &str`, diagnose E0106 because the signature does not say whether the return is borrowed from `x` or `y`.
- Given `fn longest<'a>(x: &'a str, y: &'a str) -> &'a str`, explain that the returned reference is tied to the shorter overlapping lifetime of the two arguments.
- Given `longest(string1.as_str(), string2.as_str())` with `result` printed inside `string2`'s scope, predict it compiles.
- Given the same call with `result` printed after `string2` is dropped, diagnose E0597 even if `string1` is known to be longer by value.
- Given a function that always returns `x`, choose `fn longest<'a>(x: &'a str, y: &str) -> &'a str`.
- Given `let result = String::from(...); result.as_str()` returned from a function, diagnose E0515 because the returned reference points to local data.
- Given a need to return data created inside a function, choose an owned return type rather than a borrowed reference.
- Given `struct ImportantExcerpt<'a> { part: &'a str }`, infer an `ImportantExcerpt` cannot outlive the string slice stored in `part`.
- Given `first_word(s: &str) -> &str`, apply elision rules 1 and 2 to infer `first_word<'a>(s: &'a str) -> &'a str`.
- Given `longest(x: &str, y: &str) -> &str`, apply elision rule 1 to get two input lifetimes, then diagnose that rules 2 and 3 do not determine the output lifetime.
- Given a method `fn announce_and_return_part(&self, announcement: &str) -> &str`, apply elision rule 3 to assign the output lifetime to `&self`.
- Given `let s: &'static str = "..."`, identify the string literal as data that can live for the entire program.
- Given an error suggesting `'static`, first suspect a dangling reference or lifetime mismatch before adding `'static`.
- Given `longest_with_an_announcement<'a, T>`, identify `'a` as the lifetime parameter and `T` as the generic type parameter.
- Given the `ann: T` parameter printed with `{}`, identify `T: Display` as the needed trait bound.

#### Failure Modes

- Thinking lifetime annotations extend the lifetime of a value.
- Thinking a lifetime annotation by itself proves anything useful without relating references.
- Forgetting that every reference has a lifetime even when it is elided.
- Treating uninitialized variable declarations as null values; Rust still requires assignment before use.
- Returning a reference without tying it to an input lifetime when it may come from multiple input references.
- Assuming the compiler can use runtime branch outcomes or string lengths to prove a returned reference is valid.
- Using the same lifetime parameter on unrelated references and accidentally over-constraining callers.
- Adding a lifetime to a return type that points to local data and expecting it to fix a dangling reference.
- Returning a borrowed `&str` to a local `String`; return an owned `String` instead.
- Defining a struct field as `&str` without a lifetime parameter.
- Treating lifetime elision as broad inference; the compiler only applies the three deterministic rules.
- Expecting elision to infer the original `longest` signature with two input references and one output reference.
- Forgetting to declare a struct field lifetime after `impl` when implementing methods on a lifetime-parameterized struct.
- Overusing `'static` to silence lifetime errors instead of fixing dangling references or lifetime mismatches.
- Creating cards that imply lifetimes affect runtime performance; the chapter states the analysis is compile-time.

#### Comparisons

- Lifetime generics vs type generics: lifetimes describe reference validity relationships; type generics abstract over concrete types.
- Types vs lifetimes inference: both are often inferred, but both need annotations when multiple possibilities remain.
- Listing 10-16 vs Listing 10-18: referent shorter than reference is rejected; referent longer than reference is accepted.
- Lifetime annotation vs lifetime duration: annotations describe relationships; they do not lengthen any value's scope.
- `longest` without annotations vs with `'a`: ambiguous return borrow vs explicit relation among both inputs and output.
- Listing 10-22 vs Listing 10-23: using the return inside the shorter argument's scope compiles; using it after that scope ends fails.
- Returning a parameter reference vs returning a local reference: parameter lifetimes can be tied to the return; local references would dangle after the function returns.
- Structs with owned data vs structs with references: owned fields need no lifetime parameter; reference fields require lifetime annotations.
- Explicit lifetime annotations vs elision: explicit annotations write the relationship; elision lets the compiler fill in common deterministic patterns.
- `first_word` vs `longest`: one input lifetime lets elision determine the output; two input lifetimes leave the output ambiguous.
- Function elision vs method elision: methods can use rule 3 to tie output lifetimes to `self`.
- `'static` string literal vs ordinary borrowed data: string literal data can live for the whole program; most borrowed values cannot.
- Lifetimes vs trait bounds in combined signatures: lifetimes constrain borrowed-reference validity; trait bounds constrain generic type behavior.
