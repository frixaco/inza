### Card Content Candidates

#### Concepts

- Many operations a computer performs can take a while to finish.
- A useful program should sometimes be able to do other work while waiting for a long-running operation.
- Modern computers offer parallelism and concurrency as techniques for working on more than one operation at a time.
- Program logic is often written in a mostly linear fashion.
- Asynchronous programming lets code express operations, potential pausing points, and eventual results without specifying every scheduling detail up front.
- Async abstracts over coordination details.
- CH-17 builds on CH-16's threads by introducing a different way to write concurrent code.
- Rust async uses futures, streams, `async`, and `await`.
- Third-party crates implement asynchronous runtimes.
- An asynchronous runtime manages and coordinates execution of asynchronous operations.
- A video export is CPU-bound or compute-bound in the book's example.
- CPU-bound work is limited by CPU/GPU processing speed and how much processing capacity can be dedicated to the operation.
- A video download is I/O-bound in the book's example.
- I/O-bound work is limited by input/output speed, such as how fast network data can arrive.
- A modern processor can perform billions of operations every second, so waiting even a second or two for I/O is a long time.
- Operating-system interrupts can provide concurrency by pausing one program and letting other programs run.
- OS-level concurrency acts at the level of whole programs.
- A program author may see finer-grained concurrency opportunities than the operating system can infer.
- A file-download manager should not lock up the UI while one download runs.
- A file-download manager should allow users to start multiple downloads at the same time.
- Many OS network APIs are blocking.
- A blocking operation blocks the program's progress until the data or resource being processed is completely ready.
- Most function calls block in a general sense, but "blocking" is usually reserved for resource operations where nonblocking behavior would help.
- Resource operations include file, network, and other computer-resource interactions.
- Spawning a dedicated thread per download could avoid blocking the main thread.
- One-thread-per-download designs can become expensive because of thread system-resource overhead.
- Async lets code define tasks for a program to complete and lets the runtime choose the best order and manner to run them.
- `async` is short for asynchronous.
- CH-17 will cover Rust's `async` and `await` syntax and executing asynchronous functions with a runtime.
- CH-17 will cover using async to solve some challenges previously solved with threads in CH-16.
- CH-17 will cover how multithreading and async are complementary and can often be combined.
- In the book's async context, concurrency and parallelism need precise distinction.
- Concurrency means an individual or system works on multiple tasks before any one task is complete by switching between them.
- In the team analogy, one person switching between project tasks is concurrent work.
- Parallelism means independent work happens at the exact same time.
- In the team analogy, each team member taking one task and working at the same time is parallel work.
- Serial work means tasks must happen in sequence, one after another.
- Work can be partly parallel and partly serial if one task eventually blocks on another task's result.
- A person's own concurrent work can become serial if one of their tasks depends on another of their tasks.
- Parallelism and concurrency can intersect.
- If one coworker is blocked until another coworker finishes a task, the team may temporarily lose both parallelism and individual concurrency.
- On a single CPU core, a computer can perform only one operation at a time.
- A single-core machine can still work concurrently by pausing one activity and switching to another before cycling back.
- Threads, processes, and async are tools that can support this kind of switching.
- On a multicore machine, work can also happen in parallel.
- Parallel work on multiple cores means one core can run one task while another core runs an unrelated task at the same time.
- Rust async code usually runs concurrently.
- Rust async concurrency may also use parallelism under the hood depending on hardware, operating system, and async runtime.

#### Failure Modes

- Treating concurrency and parallelism as interchangeable in CH-17 can obscure how async actually schedules work.
- Blocking resource calls can make a program unresponsive if the program has other useful work to do.
- Thread-per-task designs can become resource-heavy when many tasks are waiting on I/O.
- Assuming async always means parallel execution is wrong; async usually means concurrent execution and may or may not use parallelism.
- Assuming the operating system can always find all useful concurrency opportunities is too broad; application-level structure can expose finer-grained opportunities.

#### Comparisons

- CPU-bound vs I/O-bound: CPU-bound work is limited by processing capacity; I/O-bound work is limited by input/output speed.
- Blocking vs nonblocking: blocking waits until data or a resource is ready; nonblocking allows other work to proceed while waiting.
- OS-level concurrency vs application-level async: OS interrupts can switch between programs; async lets the program express finer-grained pausing points and tasks.
- Threads vs async in the opener: a dedicated thread can avoid blocking but adds system-resource overhead; async lets a runtime coordinate tasks without one thread per task.
- Concurrency vs parallelism: concurrency switches among multiple in-progress tasks; parallelism runs independent tasks at the same time.
- Parallel vs serial work: parallel work progresses independently; serial work must happen in sequence because of dependencies.
- Single-core vs multicore: single-core machines can be concurrent through switching; multicore machines can also run tasks in parallel.
- CH-16 threads vs CH-17 async: threads were the earlier concurrency mechanism; CH-17 introduces futures, streams, `async`, `await`, and runtimes as another model.

#### Project / Architecture Decisions

- Consider async when a program has many tasks that may spend time waiting on files, networks, or other resources.
- Consider CPU-bound work separately from I/O-bound work; async is motivated strongly by waiting and coordination, not by making compute-heavy work disappear.
- Avoid blocking a UI or main coordination path with resource calls when the program has other useful work to do.
- Avoid assuming one thread per waiting task is always scalable.
- Choose between threads, async, or a combination based on the work shape and runtime needs.

### Card Content Candidates

#### Concepts

- The key async elements introduced here are futures plus Rust's `async` and `await` keywords.
- A future is a value that may not be ready now but will become ready later.
- Similar ideas are called task or promise in some other languages.
- Rust provides the `Future` trait as a shared interface for async operations.
- Different async operations can use different data structures while sharing the `Future` trait interface.
- A Rust future is a type that implements the `Future` trait.
- Each future stores its own progress state and its own definition of readiness.
- The `async` keyword can be applied to blocks and functions.
- Marking a block or function `async` specifies that it can be interrupted and resumed.
- Inside an async block or async function, `await` waits for a future to become ready.
- Any `.await` point in async code is a possible pause/resume point.
- Polling is checking with a future to see whether its value is available yet.
- Rust compiles `async` and `await` syntax into equivalent code using the `Future` trait.
- The `Future` trait relationship is similar to how Rust compiles `for` loops into equivalent code using the `Iterator` trait.
- Code can implement `Future` for custom data types when needed.
- The `trpl` crate is short for The Rust Programming Language.
- The `trpl` crate re-exports async types, traits, and functions needed for this chapter.
- `trpl` primarily re-exports from the `futures` and `tokio` crates.
- The `futures` crate is an official home for Rust async experimentation and is where `Future` was originally designed.
- Tokio is described as the most widely used async runtime in Rust today, especially for web applications.
- The book uses `tokio` under the hood for `trpl` because it is well tested and widely used.
- The section's setup command creates a binary project named `hello-async`.
- `cargo add trpl` adds the chapter helper crate dependency.
- Listing 17-1 defines `async fn page_title(url: &str) -> Option<String>`.
- `page_title` fetches a URL, reads response text, parses HTML, selects the first `title` element, and returns an `Option<String>`.
- `trpl::get(url)` is asynchronous because it waits for the server response.
- `response.text()` is asynchronous because the full response body may take time to arrive.
- Both the `get` future and the `text` future must be awaited explicitly.
- Rust futures are lazy.
- A Rust future does not do work until asked with `.await` or another polling mechanism.
- Rust will warn if a future is not used.
- Future laziness is compared with iterator laziness: iterators do nothing unless `next` is called directly or indirectly.
- Future laziness differs from `thread::spawn`, where the spawned closure starts running immediately.
- Rust's future laziness also differs from async behavior in many other languages.
- Rust uses future laziness as part of delivering performance guarantees.
- `Html::parse(&response_text)` converts raw HTML text into a richer data structure.
- `select_first("title")` returns `Option<ElementRef>` because a document might not have a matching element.
- `Option::map` is used to transform a present title element into its `inner_html`.
- The final `page_title` result in Listing 17-1 is `Option<String>`.
- Rust's `await` keyword is postfix.
- Postfix await means `.await` appears after the expression being awaited.
- Postfix `.await` makes method chains easier to read and write.
- Listing 17-2 chains `trpl::get(url).await.text().await`.
- An `async` block compiles to a unique anonymous data type implementing `Future`.
- An `async fn` compiles to a non-async function whose body is an async block.
- An async function's return type is the anonymous future type generated for that async block.
- Writing `async fn` is equivalent to writing a function that returns a future of the return type.
- The approximate desugaring of `async fn page_title(...) -> Option<String>` returns `impl Future<Output = Option<String>>`.
- The desugared function body is an `async move` block.
- The async block's produced value must match the `Future::Output` associated type.
- The transformed `page_title` uses `async move` because it uses the `url` parameter.
- Listing 17-3 attempts to make `main` async and await `page_title(url)`.
- The only place `.await` can be used is inside async functions or async blocks.
- Rust does not allow the special `main` function to be marked `async` directly.
- Listing 17-3 fails with E0752: `main` function is not allowed to be `async`.
- Async code needs a runtime.
- A runtime is a Rust crate that manages details of executing asynchronous code.
- A program's `main` function can initialize a runtime, but `main` itself is not a runtime.
- Every Rust program that executes async code has at least one place where it sets up a runtime to execute futures.
- Rust does not bundle one async runtime into the language.
- Different async runtimes make different tradeoffs for different use cases.
- A high-throughput web server and a small microcontroller can need very different runtime tradeoffs.
- Runtime crates often provide async versions of common operations such as file I/O and network I/O.
- `trpl::block_on` takes a future as an argument and blocks the current thread until the future completes.
- Calling `trpl::block_on` sets up a runtime using Tokio behind the scenes.
- When the future passed to `block_on` completes, `block_on` returns the future's produced value.
- Listing 17-4 keeps `main` synchronous and calls `trpl::block_on(async { ... })`.
- Listing 17-4 awaits `page_title(url)` inside the async block passed to `block_on`.
- `block_on` is the bridge from synchronous `main` to async execution in this chapter.
- Each await point hands control back to the runtime.
- Rust tracks async-block state so the runtime can run other work and later resume the first future.
- The source models this hidden state as an enum with `Initial`, `GetAwaitPoint`, and `TextAwaitPoint` states.
- The compiler creates and manages async state-machine data structures automatically.
- Normal borrowing and ownership rules still apply to async state-machine data.
- An executor is the part of a runtime responsible for executing async code.
- Some runtimes provide macros that let code write `async fn main`.
- Async-main macros rewrite `async fn main` into a normal `fn main` that runs a future to completion, like `trpl::block_on`.
- Listing 17-5 creates two futures by calling `page_title` for two command-line URLs.
- The futures in Listing 17-5 do not start doing work immediately because futures are lazy and have not been awaited yet.
- `trpl::select(title_fut_1, title_fut_2).await` races two futures.
- `trpl::select` returns a value indicating which future finishes first.
- `trpl::select` is built on a more general `select` function from the `futures` crate.
- The more general `futures` `select` can do more but has additional complexity.
- Because either future can legitimately win, `trpl::select` returns `trpl::Either` rather than `Result`.
- `Either` has `Left` and `Right` variants without success/failure meaning.
- `trpl::select` returns `Either::Left` if the first future argument wins.
- `trpl::select` returns `Either::Right` if the second future argument wins.
- Listing 17-5 updates `page_title` to return both the URL and its optional title as `(&str, Option<String>)`.
- Returning the URL lets the program print a meaningful message even if the winning page has no title.
- Running the two-URL tool may show one site consistently faster or the winner varying across runs.

  ```rust
  use trpl::Html;

  async fn page_title(url: &str) -> Option<String> {
      let response = trpl::get(url).await;
      let response_text = response.text().await;
      Html::parse(&response_text)
          .select_first("title")
          .map(|title| title.inner_html())
  }
  ```

- Approximate `async fn` desugaring:
  ```rust
  use std::future::Future;
  use trpl::Html;

  fn page_title(url: &str) -> impl Future<Output = Option<String>> {
      async move {
          let text = trpl::get(url).await.text().await;
          Html::parse(&text)
              .select_first("title")
              .map(|title| title.inner_html())
      }
  }
  ```


  ```rust

      let args: Vec<String> = std::env::args().collect();

      trpl::block_on(async {
          let url = &args[1];
          match page_title(url).await {
              Some(title) => println!("The title for {url} was {title}"),

      })

  ```

- Race two futures with `trpl::select` and `Either`:
  ```rust
  use trpl::{Either, Html};

  trpl::block_on(async {
      let title_fut_1 = page_title(&args[1]);
      let title_fut_2 = page_title(&args[2]);

      let (url, maybe_title) =
          match trpl::select(title_fut_1, title_fut_2).await {
              Either::Left(left) => left,
              Either::Right(right) => right,

      println!("{url} returned first");
  ```

#### Prediction / Diagnostic Examples

- Predict Listing 17-1: calling `page_title(url)` produces a future; the body does not run to completion until the future is awaited or otherwise polled.
- Predict missing await: a future returned by `trpl::get(url)` or `response.text()` does no work unless explicitly awaited; Rust warns if a future is unused.
- Predict chained await: `trpl::get(url).await.text().await` first waits for the response, then calls `text`, then waits for the body text.
- Diagnose `async fn main`: Listing 17-3 fails with E0752 because the `main` function is not allowed to be `async`.
- Explain why E0752 occurs: an async `main` would return a future, but something must set up a runtime and execute that future.
- Predict Listing 17-4: `trpl::block_on(async { ... })` sets up a runtime and runs the async block until `page_title(url).await` completes.
- Predict an await point: at `trpl::get(url).await`, control can return to the runtime while waiting for the response.
- Predict state-machine contents: the future must remember enough state to resume after the `get` await point and after the `text` await point.
- Predict Listing 17-5 before `select`: `title_fut_1` and `title_fut_2` have not started doing network work merely because they were created.
- Predict Listing 17-5 after `select(...).await`: either URL can win; the result is `Either::Left` for the first argument or `Either::Right` for the second.
- Diagnose `Either` vs `Result`: use `Either` because the first or second future winning is not success vs failure.

#### Failure Modes

- Forgetting `.await` leaves a future lazy and unexecuted.
- Treating Rust futures like `thread::spawn` is wrong: spawned threads start immediately, while futures need polling.
- Putting `await` before an expression is not Rust syntax; Rust uses postfix `.await`.
- Attempting to await in non-async code fails because `.await` is only valid in async functions or blocks.
- Marking `main` directly as `async` fails with E0752.
- Choosing a runtime is part of executing async Rust; Rust does not provide one bundled runtime for every program.
- Writing async state transitions manually would be tedious and error-prone; the compiler-generated state machine handles this automatically.
- Assuming `select` returns `Result` is wrong because racing two futures has no inherent success/failure side.

#### Comparisons

- Future vs task/promise terminology: the same general concept appears under other names in other languages.
- `async` block vs `async fn`: an async block becomes an anonymous future type; an async function becomes a function returning such a future.
- `async fn` syntax vs desugared form: `async fn page_title(...) -> Option<String>` roughly becomes `fn page_title(...) -> impl Future<Output = Option<String>>`.
- Futures vs iterators: both are lazy; iterators require `next`, futures require polling or awaiting.
- Futures vs spawned threads: futures do not run immediately; a spawned thread's closure starts running immediately.
- Prefix await in some languages vs Rust postfix `.await`: Rust puts await after the expression, improving method chaining.
- `main` vs runtime: `main` can initialize a runtime, but the runtime executes async futures.
- `block_on` vs async-main macro: `block_on` is explicit; a runtime macro rewrites async main into a normal main that runs a future to completion.
- `Result` vs `Either`: `Result` encodes success/failure; `Either` encodes first/second or left/right with no success/failure meaning.
- `trpl::select` vs `futures::select`: `trpl::select` is simpler for this chapter; `futures::select` is more general and more complex.

#### Project / Architecture Decisions

- Use `trpl` in chapter examples to focus on async concepts rather than ecosystem setup details.
- Explicitly await each future whose work must happen; creating the future alone is not enough.
- Use postfix `.await` to keep method chains readable.
- Keep `main` synchronous unless using a runtime macro; call `block_on` or an equivalent runtime entry point to execute async code.
- Select a runtime according to the target environment and tradeoffs; a web server and a constrained microcontroller may need different runtimes.
- Use an async block inside `block_on` when real async code needs more than one awaited call.
- Use `select` when the program needs whichever of two futures finishes first, not when the program needs both results.
- Preserve later CH-17 extraction coverage for deeper `Future::poll`, `Poll::Ready`, `Poll::Pending`, `Pin`, `Unpin`, tasks, async channels, streams, and larger join/select patterns.

#### Failure Modes

- Similar async/thread API names can hide different semantics and performance behavior.
- A spawned async task can be canceled or shut down when the top-level future completes if its handle is not awaited.
- Awaiting future blocks one by one can accidentally serialize work.
- A single async block with multiple await points still executes linearly.
- Sending and then receiving in the same async block can delay receiving until all sending work is done.
- Receiver loops can wait forever if a channel sender remains alive.
- Borrowing `tx` in a sender future can keep the channel open beyond the sender future's useful work.
- Forgetting `async move` on sender blocks can prevent sender drop and keep the receiver loop from ending.
- Assuming `send` on this channel must be awaited is wrong in the book's example because the channel is unbounded and `send` does not block.
- Assuming runtime fairness for every async operation is too broad; runtimes may expose different fairness behaviors.

#### Comparisons

- `trpl::spawn_task` vs `thread::spawn`: similar API shape, but async tasks do not require spawning an operating system thread.
- `trpl::sleep(...).await` vs `thread::sleep`: async sleep yields to the runtime; thread sleep blocks a thread.
- Task handle await vs thread handle join: awaiting a task handle waits for async task completion; thread `join` blocks until an OS thread completes.
- `trpl::join` vs `JoinHandle::join`: `trpl::join` combines futures into a new future; thread join waits on a spawned thread handle.
- Spawned task vs anonymous future: a task can be spawned, but two async blocks can also be joined directly without spawning a task.
- `trpl::join` vs sequential awaits: `join` lets two futures make progress together; sequential awaits wait for one before starting/waiting on the other.
- OS scheduling vs runtime scheduling: OS chooses among threads; async runtime chooses which task/future to poll.
- Synchronous channel `recv` vs async channel `recv`: synchronous `recv` blocks a thread; async `recv().await` yields to the runtime.
- Single async block vs multiple async blocks joined together: one block runs linearly; joined blocks can make concurrent progress.
- `trpl::join` vs `trpl::join!`: `join` handles two futures; `join!` handles an arbitrary number known at compile time.
- Known number of futures vs unknown collection: `join!` handles a known compile-time number; arbitrary collections are deferred to later CH-17 coverage.

#### Project / Architecture Decisions

- Await a spawned task handle when correctness requires the task to finish before the top-level async block ends.
- Prefer joining anonymous futures when no separately spawned task is needed.
- Use `trpl::join` when two futures should both complete and can make progress together.
- Avoid awaiting futures individually in sequence when the goal is concurrent progress.
- Use async channels for message passing between futures and await receiver operations instead of blocking a thread.
- Use `while let Some(value) = rx.recv().await` when the number of async messages is not known in advance.
- Split sender and receiver work into separate async blocks when they need to make progress concurrently.
- Move channel senders into async blocks when sender drop should signal completion to receivers.
- Clone senders for multiple producer futures.
- Use `trpl::join!` when joining a compile-time-known number of futures greater than two.
- Preserve later CH-17 coverage for handling unknown numbers of futures, streams, and low-level future polling.

#### Concepts

- Rust gives the runtime a chance to pause a task and switch to another task at each `.await` point.
- Rust only pauses async blocks and hands control to the runtime at await points.
- Everything between await points is synchronous.
- A future can starve other futures if it does a lot of work without reaching an await point.
- Starvation can matter for expensive setup, long-running work, or futures that run indefinitely.
- Listing 17-14 defines `slow(name, ms)` as a blocking helper that calls `std::thread::sleep(Duration::from_millis(ms))`.
- `slow` intentionally uses `std::thread::sleep` instead of `trpl::sleep`, so it blocks the current thread.
- Listing 17-15 puts several blocking `slow` calls in each of two async futures.
- In Listing 17-15, each future hands control back only after completing its group of `slow` calls and reaching `trpl::sleep(...).await`.
- `trpl::select(a, b).await` still finishes as soon as future `a` is done in Listing 17-15.
- `select` racing futures does not make blocking work inside each future interleave by itself.
- Removing the final `trpl::sleep` from the `a` future in Listing 17-15 would let `a` complete without `b` running at all.
- Listing 17-16 adds `trpl::sleep(one_ms).await` between the blocking `slow` calls.
- Await points between slow operations let the `a` and `b` futures switch off making progress.
- In Listing 17-16, `a` still runs its first `slow` call before `b` starts because the first await point in `a` comes after that call.
- Sleeping is not the real goal when yielding for fairness; handing control back to the runtime is the goal.
- `trpl::yield_now().await` directly yields control to the runtime.
- Listing 17-17 replaces the small async sleeps with `trpl::yield_now().await`.
- `yield_now` communicates the intent to yield more clearly than a fake sleep.
- `yield_now` can be significantly faster than using a timer because timers often have minimum granularity.
- The book's `trpl::sleep` always sleeps for at least a millisecond, even if passed a nanosecond duration.
- Async can help structure compute-bound tasks when a program needs coordinated progress among parts, but async state machines have overhead.
- Cooperative multitasking means each future controls when it hands control back by reaching await points.
- Cooperative multitasking also means each future is responsible for not blocking too long.
- Some Rust-based embedded operating systems use cooperative multitasking as their only multitasking model.
- Yielding is relatively inexpensive but not free.
- Breaking up a compute-bound task can sometimes make overall performance significantly slower.
- Performance bottlenecks should be measured before adding many yield points.
- A `timeout` helper can be built by composing smaller async building blocks.
- The timeout helper in Listing 17-20 races a caller-provided future against a timer future from `trpl::sleep(max_time)`.
- The `timeout` helper is itself async so callers can await it.
- The timeout helper's first parameter is generic over any `Future`.
- The timeout helper's second parameter is a `Duration`.
- The timeout helper returns `Ok(output)` when the caller's future completes first.
- The timeout helper returns `Err(max_time)` when the timer elapses first.
- `F::Output` names the output type produced by the generic future `F`.
- `trpl::select` returns `Either::Left` when its first argument completes first.
- `trpl::select` returns `Either::Right` when its second argument completes first.
- The implementation of `trpl::select` used in the book is not fair: it always polls arguments in the order they are passed.
- Other `select` implementations may randomly choose which argument to poll first.
- Listing 17-20 passes `future_to_try` to `select` before the timer so it gets a chance to complete even with a very short timeout.
- When the timer wins, the timer's `()` output is ignored and `Err(max_time)` is returned.
- Futures compose with other futures, so small async helpers can be combined into larger async abstractions.
- The same compositional approach can combine timeouts with retries and network operations.
- In practice, Rust async code usually uses `async` and `await` directly, plus helpers like `select` and `join!` to control outermost future execution.

- Assuming async Rust preempts futures anywhere inside their bodies is wrong; handoff happens at await points.
- Putting long blocking work between await points can starve other futures.
- Calling `std::thread::sleep` inside an async future blocks the current thread.

- Using `trpl::sleep` only to yield can hide intent and add timer-granularity delay.

- Breaking up compute-bound work without measuring can make the program slower.

#### Comparisons

- Work between await points vs work at await points: between await points, code is synchronous; at await points, the runtime may switch tasks.
- `std::thread::sleep` vs `trpl::sleep(...).await`: `thread::sleep` blocks the thread; async sleep creates an awaitable timer and yields to the runtime.
- `trpl::sleep` as a timer vs `trpl::yield_now`: sleep waits for a time duration; `yield_now` hands control back as soon as possible.
- `select` vs `join`: `select` completes when one raced future completes; `join` waits for both futures to complete.
- Cooperative multitasking vs preemptive scheduling: cooperative async futures yield at await points they reach; preemptive scheduling can interrupt work without cooperation from the task.

- `Future::Output` vs `Iterator::Item`: `Output` is the future's single resolved value; `Item` is each value in an iterator sequence.
- `Poll<T>` vs `Option<T>`: both have value/no-value-like variants, but `Poll::Pending` means check again later while `Option::None` usually means no value.
- `Poll::Pending` vs `Poll::Ready(None)` for streams: `Pending` means no next item is ready yet; `Ready(None)` means the stream is finished.
- `.await` vs direct `poll`: `.await` is ergonomic syntax compiled into polling coordinated by a runtime; direct `poll` is low-level.
- `trpl::join!` vs `trpl::join_all`: `join!` handles a compile-time-known set of futures; `join_all` handles a collection whose size can vary at runtime.
- Async block output type vs async block concrete type: several async blocks can all output `()`, but still have different concrete future types.
- Direct await pinning vs collection pinning: direct await pins implicitly; collections used with `join_all` may require explicit `pin!`.
- `Pin` vs `Unpin`: `Pin` provides a no-move guarantee through a pointer; `Unpin` marks types that do not require that guarantee.
- Pinned pointee vs moved pointer: the underlying value must stay in place, but a pointer such as a `Box` can move while still pointing to stable data.
- `Unpin` vs `!Unpin`: `Unpin` is the normal movable case; `!Unpin` is the special case that needs pinning guarantees.
- `Send`/`Sync` vs `Unpin`: all are marker traits, but `Send`/`Sync` describe thread-safety transfer/sharing while `Unpin` describes whether pinning move guarantees are needed.
- `Future::poll` vs `Stream::poll_next`: `Future::poll` checks readiness for one output; `Stream::poll_next` checks readiness for the next item in a sequence.
- `Iterator::next` vs `Stream::poll_next`: iterator `next` synchronously returns `Option<Item>`; stream `poll_next` returns `Poll<Option<Item>>`.
- `Stream` vs `StreamExt`: `Stream` is the foundational polling trait; `StreamExt` supplies ergonomic utility methods such as `next`.

#### Project / Architecture Decisions

- Avoid calling `poll` directly unless implementing or debugging low-level async behavior.
- If you implement a custom `Future`, understand `Context`, `Poll`, and the `Pin<&mut Self>` receiver.
- Use `trpl::join_all` when the number of futures is only known at runtime.
- Use trait objects or another unifying type when storing distinct async-block futures in one collection.
- Pin async-block futures before storing them as `Pin<&mut dyn Future<Output = ()>>` for `join_all`.
- Consider `Box::pin` when a pinned value needs to be accessed outside the current scope, as the compiler diagnostic suggests.
- Treat `Pin`/`Unpin` errors as signals that a future may need an explicit pinning strategy.
- Prefer high-level `.await`, `join!`, `join_all`, and `StreamExt` APIs in application code where possible.
- Implement `Stream` rather than reimplementing `StreamExt` methods when defining a custom streaming data type.
- Use `Poll<Option<Item>>` carefully so "not ready yet" and "finished" remain distinct.
- Record that this section closes CH-17 requirements for arbitrary runtime collections of futures, `Future::poll`, `Poll::Ready`, `Poll::Pending`, `Pin`, and `Unpin`.

#### Concepts

- Threads provide one approach to concurrency.
- Async with futures and streams provides another approach to concurrency.

- Many programming languages support threading-based concurrency models.
- Threading models have tradeoffs.
- On many operating systems, each thread uses a fair amount of memory.
- Threads require operating-system and hardware support.
- Some embedded systems have no operating system and therefore no threads.
- Async provides a different and complementary set of tradeoffs from threads.
- In the async model, concurrent operations do not require their own threads.
- Async operations can run on tasks.
- The book previously used `trpl::spawn_task` to start task work.
- A task is similar to a thread.
- A task is managed by library-level runtime code rather than by the operating system.
- Thread-spawning and task-spawning APIs are similar because both create concurrency boundaries.
- Threads act as boundaries for sets of synchronous operations.
- Concurrency is possible between threads.
- Tasks act as boundaries for sets of asynchronous operations.
- Concurrency is possible both between tasks and within tasks.
- Concurrency is possible within a task because the task can switch between futures in its body.
- Futures are Rust's most granular unit of concurrency in this section's explanation.
- Each future may represent a tree of other futures.
- The runtime's executor manages tasks.
- Tasks manage futures.
- Tasks are like lightweight runtime-managed threads with added runtime-managed capabilities.
- Async tasks are not always better than threads.
- Threads are not always better than async tasks.
- Thread concurrency is in some ways a simpler programming model than async concurrency.
- Thread-model simplicity can be either a strength or a weakness.
- Threads are somewhat "fire and forget" in this comparison.
- Threads have no native equivalent to a future.
- Threads run to completion unless interrupted by the operating system.
- Threads and tasks often work well together.
- In some runtimes, tasks can be moved between threads.

- Many runtimes use work stealing.

- Work stealing aims to improve overall system performance.

#### Syntax Forms

- Spawn a blocking thread and receive its messages asynchronously:
  ```rust
  use std::{thread, time::Duration};

  fn main() {
      let (tx, mut rx) = trpl::channel();

      thread::spawn(move || {
          for i in 1..11 {
              tx.send(i).unwrap();
              thread::sleep(Duration::from_secs(1));
          }
      });

      trpl::block_on(async {
          while let Some(message) = rx.recv().await {
              println!("{message}");
          }
      });
  }
  ```

#### Prediction / Diagnostic Examples

- Choose threads for a workload that is very parallelizable and CPU-bound, such as independent pieces of data processing.
- Choose async for a workload that is very concurrent and I/O-bound, such as handling messages from many sources at varying rates.
- Predict Listing 17-25 behavior: the async receiver prints numbers sent by the blocking thread.
- Predict Listing 17-25 timing: values arrive roughly once per second because the producer thread calls `thread::sleep(Duration::from_secs(1))`.
- Predict why Listing 17-25 exits: when the sending thread finishes and drops `tx`, the async receiver eventually gets `None` and the `while let` loop ends.
- Diagnose a memory-constrained or no-OS embedded context: threads may be unavailable or too expensive, making async attractive.
- Diagnose a compute-heavy operation run on async without care: threads may be a better fit if the work is CPU-bound and very parallelizable.
- Diagnose an I/O-heavy operation implemented as one thread per source: async may be a better fit if many sources mostly wait at different intervals.
- Explain why an async runtime may still use threads: some runtimes move tasks between worker threads for performance.
- Explain why work stealing is not "async instead of threads": it uses threads, tasks, and futures together.
- Explain why task APIs resemble thread APIs: both start concurrent units of work, but one is runtime-managed and async-oriented while the other is OS-managed and synchronous-oriented.

#### Failure Modes

- Treating async tasks as always better than threads ignores CPU-bound parallel workloads and simpler thread programming models.
- Treating threads as always better than async ignores thread memory overhead and platform availability limits.
- Assuming async means no threads are involved is too broad; many async runtimes are multithreaded.
- Assuming tasks are operating-system threads is wrong; tasks are managed by runtime/library code.
- Assuming futures, tasks, and threads are the same level of abstraction obscures the executor/task/future hierarchy.
- Using blocking work directly inside async tasks can work against the async model unless the runtime provides a strategy such as `spawn_blocking`.
- Using one OS thread per highly concurrent I/O source can become expensive.
- Using only async for highly parallel CPU-bound work may underuse the simpler and more direct thread-based model.
- Forgetting `move` on the producer thread closure would prevent the thread from owning the channel sender as shown in Listing 17-25.
- Keeping senders alive accidentally would prevent the async receiver loop from ending.

#### Comparisons

- Threads vs async: both support concurrency, but with different tradeoffs and often complementary use.
- Threads vs tasks: threads are managed by the operating system; tasks are managed by the runtime.
- Threads as boundaries vs tasks as boundaries: threads bound synchronous operations; tasks bound asynchronous operations.
- Between-thread concurrency vs within-task concurrency: concurrency can happen between OS threads, and a task can also switch among futures inside its body.
- Task vs future: a task is a runtime-managed unit of async work; a future is the more granular unit that may compose a tree of futures.
- Runtime executor vs operating system: the executor manages tasks; the OS manages threads.
- Fire-and-forget threads vs futures: threads run to completion without a native future-like value; futures represent pollable asynchronous progress and completion.
- CPU-bound vs I/O-bound rule of thumb: CPU-bound very parallelizable work favors threads; I/O-bound very concurrent work favors async.
- Parallelism vs concurrency in tool choice: parallel data processing maps well to threads; high-concurrency waiting maps well to async.
- `thread::sleep` in Listing 17-25 vs `rx.recv().await`: the producer blocks its OS thread; the receiver awaits asynchronously.
- `thread::spawn` vs `trpl::spawn_task`: both spawn work, but `thread::spawn` creates OS-managed thread work and `spawn_task` creates runtime-managed task work.
- Threads only vs tasks only vs combined runtimes: real systems may use both, especially when runtimes move tasks across worker threads.

#### Project / Architecture Decisions

- Choose threads for very parallelizable CPU-bound work where independent pieces can run at the same time.
- Choose async for very concurrent I/O-bound work where many sources wait and become ready at different rates.
- Combine threads and async when a system needs both parallel compute and asynchronous coordination.
- Use a thread for blocking or compute-bound work and an async channel to notify async/UI code when results are ready.
- Consider runtime behavior before assuming async eliminates threads; many runtimes are multithreaded.
- Consider memory and platform support before choosing thread-heavy designs.
- Consider embedded constraints when deciding whether OS threads are available at all.
- Use `move` when a spawned thread must own the channel sender.
- Let sender drop close the channel so async receiver loops can finish.
