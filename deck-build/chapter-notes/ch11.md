#### Concepts

- Testing can show that bugs are present, but testing cannot prove that bugs are absent.
- Rust programs still need tests even though Rust's type system catches many problems.
- Correctness is the extent to which code does what we intend it to do.
- Rust is designed with strong concern for program correctness.
- Correctness is complex and not easy to prove.
- Rust's type system shoulders a large part of the correctness burden.
- Rust's type system cannot catch every kind of correctness problem.
- Rust includes support for writing automated software tests.
- A function signature such as `add_two(input: integer) -> integer` lets Rust check argument and return types.

- Tests can be run whenever code changes.
- Running tests after changes helps detect regressions in existing correct behavior.

- CH-11 focuses on the mechanics of Rust's testing facilities.

- CH-11 covers default behavior and options for running tests.

### Card Content Candidates

#### Concepts

- Tests are Rust functions that verify non-test code behaves as expected.
- Test bodies typically set up needed data or state, run the code under test, and assert that results match expectations.
- Rust test-writing features include the `test` attribute, assertion macros, and the `should_panic` attribute.
- A Rust test is a function annotated with `#[test]`.
- Attributes are metadata about pieces of Rust code.
- `#[test]` goes on the line before `fn`.
- `cargo test` builds a test runner binary.
- The test runner binary runs functions annotated with `#[test]`.
- The test runner reports whether each test function passes or fails.
- New Cargo library projects include a generated test module and test function.
- The generated `tests` module is a template for test structure and syntax.
- A project can contain many test functions and many test modules.
- The generated `it_works` test uses `assert_eq!(result, 4)` after calling `add(2, 2)`.
- Passing `cargo test` output shows the test name and `ok`.
- `test result: ok.` means all tests passed.
- The summary counts passed, failed, ignored, measured, and filtered-out tests.
- The `0 measured` statistic refers to benchmark tests, which are only available in nightly Rust as of the book text.
- The `Doc-tests` section reports documentation tests; documentation tests are covered later in Chapter 14.
- A test function's name appears in the test output.
- Changing `it_works` to `exploration` changes the displayed test name.
- Tests fail when something in the test function panics.
- Each test runs in a new thread.
- When the main test thread sees a test thread die, that test is marked failed.
- A test can be made to fail directly with `panic!`.
- Failing test output includes the failing test name, panic message, source location, a failure list, and a failed summary.
- The name of a failing test can be used later to run just that test for debugging.
- `assert!` checks that a Boolean condition is true.
- If an `assert!` argument is `true`, nothing happens and the test continues.
- If an `assert!` argument is `false`, `assert!` calls `panic!` and the test fails.
- `Rectangle::can_hold` returns a Boolean, so it is a good fit for `assert!`.
- A test module is a regular module and follows normal visibility rules.
- Because the generated `tests` module is an inner module, it uses `use super::*;` to bring outer-module code into scope.
- `larger_can_hold_smaller` creates a larger and smaller `Rectangle` and asserts `larger.can_hold(&smaller)`.
- `smaller_cannot_hold_larger` negates the Boolean with `!` and asserts `!smaller.can_hold(&larger)`.
- Changing `can_hold` from width `>` to width `<` makes `larger_can_hold_smaller` fail.
- The failing `assert!` output reports the failed expression but not the values inside it.
- `assert_eq!` compares two arguments for equality.
- `assert_ne!` compares two arguments for inequality.
- `assert_eq!` and `assert_ne!` are convenient alternatives to `assert!(left == right)` and `assert!(left != right)`.
- When equality assertions fail, they print the compared values, which helps explain the failure.
- `assert!` with `==` only reports that the Boolean expression was false.
- The `add_two` test stores `add_two(2)` in `result` and asserts `assert_eq!(result, 4)`.
- If `add_two` accidentally adds 3, `assert_eq!(result, 4)` fails with `left: 5` and `right: 4`.
- Rust equality assertion output calls the arguments `left` and `right`, not `expected` and `actual`.
- In Rust, the order of expected and actual values in `assert_eq!` is not semantically important.
- `assert_ne!` passes when two values are not equal and fails when they are equal.
- `assert_ne!` is useful when output is variable but must not equal a particular value.
- `assert_eq!` uses `==` under the surface.
- `assert_ne!` uses `!=` under the surface.
- Failed `assert_eq!` and `assert_ne!` output uses debug formatting.
- Values compared by `assert_eq!` or `assert_ne!` must implement `PartialEq` and `Debug` for failed assertion output.
- Primitive types and most standard library types implement `PartialEq` and `Debug`.
- Custom structs and enums usually need `#[derive(PartialEq, Debug)]` before they can be compared and printed by equality assertions.
- Custom failure messages can be added to `assert!`, `assert_eq!`, and `assert_ne!`.
- Assertion arguments after the required arguments are passed to `format!`.
- Custom failure messages can include `{}` placeholders and values.
- Custom failure messages document what an assertion means.
- The greeting example tests `result.contains("Carol")` instead of exact equality because the greeting prefix requirements might change.
- Without a custom message, a failed `assert!(result.contains("Carol"))` reports only the failed expression.
- With a custom message, the greeting test prints the actual greeting value `Hello!`.
- `#[should_panic]` marks a test as passing only if code inside the test panics.
- `#[should_panic]` goes after `#[test]` and before the test function.
- `Guess::new(200)` should panic when valid guesses must be between 1 and 100.
- A `#[should_panic]` test fails if the code does not panic.
- A plain `#[should_panic]` test can pass for the wrong panic reason.
- `#[should_panic(expected = "...")]` checks that the panic message contains the specified text.
- The `expected` value can be a substring rather than the entire panic message.
- The amount of panic-message text to specify depends on how unique or dynamic the message is and how precise the test should be.
- If a `#[should_panic(expected = "...")]` test panics with the wrong message, the test fails and reports the expected substring and actual message.
- Tests can return `Result<T, E>` instead of panicking.
- A test returning `Result<(), String>` returns `Ok(())` to pass.
- A test returning `Result<(), String>` returns `Err(String)` to fail.
- Result-returning tests allow using `?` inside tests.
- `?` is convenient when the test should fail if any operation returns `Err`.
- `#[should_panic]` cannot be used on tests that return `Result<T, E>`.
- To assert that an operation returns an `Err`, do not use `?` on that `Result`; use `assert!(value.is_err())`.

#### Failure Modes

- Forgetting `#[test]`, causing a test-looking function not to be run by the test runner.
- Assuming `cargo test` runs all helper functions in a `tests` module; only `#[test]` functions are test cases.
- Forgetting `use super::*;` inside an inner test module when testing outer-module items.
- Assuming a test failure requires an assertion macro; any panic in a test fails it.
- Using `assert!` with an equality expression when `assert_eq!` would produce more useful failure output.
- Forgetting to negate a condition when the correct result should be false.
- Treating Rust equality assertion arguments as `expected` and `actual`; Rust reports `left` and `right`.
- Using `assert_eq!` or `assert_ne!` on custom types without `PartialEq` and `Debug`.
- Writing custom failure messages that duplicate the assertion instead of adding useful state.
- Using plain `#[should_panic]` when multiple panic paths could make the test pass for the wrong reason.
- Making a `should_panic(expected = "...")` string too broad to identify the intended panic path.
- Trying to use `#[should_panic]` on a test that returns `Result<T, E>`.
- Using `?` on a `Result` when the test is supposed to assert that the value is `Err`.
- Creating cards about test-thread counts, output capture options, name filtering, or ignored tests from this section; those are covered in `ch11-02-running-tests`.

#### Comparisons

- Test function vs helper function: a test function has `#[test]`; a helper may live in the same module but is not run as a test unless annotated.
- Passing test vs failing test output: passing output shows `ok`; failing output shows `FAILED`, failure details, failing names, and failed summary.
- `panic!` vs assertion macro failure: direct panic and failed assertions both panic and fail the test.
- `assert!` vs `assert_eq!`: `assert!` checks any Boolean expression; `assert_eq!` compares equality and prints both values on failure.
- `assert_eq!` vs `assert_ne!`: equality must hold vs inequality must hold.
- `assert!(condition)` vs `assert!(!condition)`: assert that a condition is true vs assert that it is false.
- Default assertion failure vs custom failure message: default output reports the failed assertion; custom output can include domain-specific state.
- Plain `#[should_panic]` vs `expected`: any panic passes vs panic message must contain a specified substring.
- Panic-based tests vs Result-returning tests: panic-based tests fail by panicking; Result-returning tests fail by returning `Err`.
- `?` in Result-returning tests vs `assert!(value.is_err())`: `?` fails on unexpected `Err`; `assert!(value.is_err())` checks that an `Err` is expected.

### Card Content Candidates

#### Concepts

- `cargo test` compiles code in test mode and runs the resulting test binary.
- The default test binary runs all tests in parallel.
- The default test binary captures output generated during test runs.
- Capturing output from passing tests makes test-result output easier to read.
- Command-line options can change default test behavior.
- Some options are for `cargo test` itself.

#### Concepts

- Rust test organization has two main categories: unit tests and integration tests.
- Unit tests are small and focused.
- Unit tests test one module in isolation at a time.
- Unit tests can test private interfaces.
- Integration tests are external to the library.
- Integration tests use library code the same way any other external code would.
- Integration tests use only the public interface.
- Integration tests can exercise multiple modules in one test.
- Writing both unit and integration tests helps verify that library pieces work separately and together.
- Unit tests help quickly pinpoint where code is or is not working as expected.
- Unit tests live in the `src` directory in the same file as the code they test.
- The convention for unit tests is a module named `tests`.
- The unit-test `tests` module is annotated with `#[cfg(test)]`.
- `#[cfg(test)]` tells Rust to compile and run test code only during `cargo test`.
- Unit-test code is not compiled during `cargo build`.
- Excluding unit-test code from normal builds saves compile time.
- Excluding unit-test code from normal builds saves space in compiled artifacts.
- Integration tests do not need `#[cfg(test)]` because they live in a special `tests` directory.
- The `cfg` attribute stands for configuration.
- The `test` configuration option is provided by Rust for compiling and running tests.
- `#[cfg(test)]` applies to helper functions inside the `tests` module as well as `#[test]` functions.
- Rust's privacy rules allow private functions to be tested from child test modules.
- Tests are ordinary Rust code.
- The unit-test `tests` module is a child module of the file's module.
- Child modules can use items from ancestor modules.
- `use super::*;` brings the parent module's items into the unit-test module's scope.
- Listing 11-12 tests private function `internal_adder` even though it is not `pub`.
- Rust allows private-function tests, but it does not force a testing ideology.
- Integration tests are entirely external to the library.
- Integration tests can call only functions that are part of the library's public API.
- Integration tests check whether many parts of a library work together correctly.
- Code units that work separately can still have problems when integrated.
- Integration tests require a top-level `tests` directory next to `src`.
- Cargo looks for integration test files in the top-level `tests` directory.
- Each file in the `tests` directory is compiled as its own separate crate.
- Each integration test file needs to import the library crate into scope.
- Listing 11-13 uses `use adder::add_two;` in `tests/integration_test.rs`.
- Unit tests do not need `use adder::...` because they are inside the library crate's module tree.
- `tests/integration_test.rs` does not need `#[cfg(test)]`.
- Cargo compiles integration test files only when `cargo test` runs.
- Full `cargo test` output can include separate sections for unit tests, integration tests, and doc tests.
- If any test in a section fails, following sections are not run.
- If a unit test fails, integration and doc test sections are not shown.
- Each integration test file gets its own output section.
- Adding more files in `tests` creates more integration test sections.
- A particular integration test function can still be run by passing the function name to `cargo test`.
- All tests in one integration test file can be run with `cargo test --test integration_test`.
- The `--test` argument takes the integration test file name without the `.rs` extension.
- Each file directly under `tests` is treated as an integration test crate.
- Creating `tests/common.rs` for shared helpers causes Cargo to compile it as a separate integration test crate.
- `tests/common.rs` with no tests appears in output as `running 0 tests`.
- `tests/common.rs` appearing in test output is usually not the intended way to share helper code.
- To share helper code without a separate output section, use `tests/common/mod.rs`.
- Files in subdirectories of `tests` are not compiled as separate crates.
- `mod common;` in an integration test file can load `tests/common/mod.rs`.
- After declaring `mod common;`, an integration test can call `common::setup()`.
- Binary crates with only `src/main.rs` do not expose functions for integration test crates to import with `use`.
- Only library crates expose functions other crates can use.
- Binary crates are meant to be run on their own.
- Projects that provide a binary commonly keep `src/main.rs` small and put important logic in `src/lib.rs`.
- Integration tests can then test the library crate with `use`.
- If important library logic works, the small amount of code in `src/main.rs` that calls it usually does not need separate integration testing.
- CH-11 summary: unit tests exercise parts separately and can test private details; integration tests check public API behavior across parts.
