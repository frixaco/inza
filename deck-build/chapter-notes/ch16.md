## Section: Fearless Concurrency

Source: `rust-book/src/ch16-00-concurrency.md`
Coverage status: extracted
Coverage id: `ch16-00-concurrency`

### Learning Objectives

- Learner can distinguish concurrent programming from parallel programming using the book's definitions.
- Learner can explain why concurrent and parallel programming have historically been difficult and error-prone.
- Learner can explain how Rust's ownership and type systems support both memory safety and concurrency safety.
- Learner can define "fearless concurrency" as the book uses it.
- Learner can explain why Rust can turn many concurrency errors into compile-time errors.
- Learner can explain why CH-16 often says "concurrent" as shorthand for "concurrent and/or parallel."
- Learner can contrast Rust's multi-tool concurrency approach with languages that emphasize one concurrency model.
- Learner can name the CH-16 topic map: threads, message passing, shared state, and `Send`/`Sync`.

### Card Content Candidates

#### Concepts

- Concurrent programming means different parts of a program execute independently.
- Parallel programming means different parts of a program execute at the same time.
- The practical importance of concurrency and parallelism increases as computers use multiple processors.
- Historically, concurrent and parallel programming have been difficult and error-prone.
- Rust treats memory safety and concurrency safety as related problems rather than fully separate problems.
- Rust's ownership and type systems help manage both memory-safety problems and concurrency problems.
- By using ownership and type checking, Rust can make many concurrency errors compile-time errors instead of runtime errors.
- Compile-time rejection means incorrect concurrent code can fail during development instead of only after a hard-to-reproduce production bug.
- "Fearless concurrency" is the book's name for writing concurrent code with fewer subtle bugs and refactoring it without introducing new concurrency bugs.
- In CH-16, the book often uses "concurrent" as shorthand for "concurrent and/or parallel."
- CH-17 is where the book starts treating the concurrency/parallelism distinction more precisely.
- Some languages strongly prefer one concurrency model; the book names Erlang as having elegant message-passing support and less-obvious shared-state mechanisms.
- A higher-level language can reasonably offer fewer concurrency choices because its abstractions intentionally trade away some control.
- A lower-level language is expected to offer tools that can fit the best-performance solution for a given situation.
- Rust offers multiple concurrency tools so programs can model concurrency according to their situation and requirements.
- CH-16 covers creating threads to run code at the same time.
- CH-16 covers message-passing concurrency, where channels send messages between threads.
- CH-16 covers shared-state concurrency, where multiple threads can access the same data.
- CH-16 covers the `Sync` and `Send` traits, which extend Rust's concurrency guarantees to standard-library and user-defined types.

#### Syntax Forms

- No section-specific Rust syntax appears in this overview.
- The syntax-bearing sections that follow introduce `thread::spawn`, channels, `Mutex<T>`, `Arc<T>`, and the `Send`/`Sync` marker-trait boundary.

#### Prediction / Diagnostic Examples

- If concurrent code violates a rule encoded by ownership or type checking, Rust's intended behavior is to reject the program at compile time rather than leave the bug to runtime scheduling.
- If a design problem is naturally message based, CH-16 points toward channels; if it is naturally shared-state based, CH-16 points toward shared-state primitives.

#### Failure Modes

- Runtime concurrency bugs can be difficult to reproduce because the problematic circumstances depend on execution timing.
- Rust's concurrency guarantees do not mean every possible concurrency design bug is impossible; they mean many categories are caught by ownership and type checking.
- Choosing a single dogmatic concurrency model can be a poor fit when a lower-level program needs a different performance or modeling tradeoff.

#### Comparisons

- Concurrent vs parallel: independent execution vs simultaneous execution.
- CH-16 terminology vs CH-17 terminology: CH-16 uses "concurrent" loosely for concurrent and/or parallel; CH-17 becomes more precise when the distinction matters.
- Message-passing concurrency vs shared-state concurrency: communicate by sending messages between threads vs let multiple threads access a shared piece of data.
- Higher-level language strategy vs Rust strategy: restrict solutions behind stronger abstractions vs provide several lower-level tools for the situation.
- Memory-safety checking vs concurrency-safety checking: initially treated as separate by the Rust team, but both are helped by ownership and the type system.

#### Project / Architecture Decisions

- Pick a Rust concurrency primitive based on the problem shape and requirements instead of assuming one model is always best.
- Treat ownership and type constraints as part of the concurrent design, not as after-the-fact compiler hurdles.
- Preserve the CH-16 requirement coverage across later sections: threads, joins, `move` closures, channels, ownership transfer, cloned senders, shared state, `Mutex<T>`, guards, `Arc<T>`, `Rc<T>` not being thread-safe, and `Send`/`Sync`.

### Learning Objectives

- Learner can define a thread as an independent part of a program that can run simultaneously with other parts.
- Learner can explain why splitting work into threads can improve performance but adds complexity.
- Learner can identify race conditions, deadlocks, and timing-dependent bugs as thread-related risks.
- Learner can state that Rust's standard library uses a 1:1 threading model: one language thread per operating system thread.
- Learner can create a thread with `thread::spawn` and a closure.
- Learner can explain why spawned threads shut down when the main thread exits.
- Learner can explain what `thread::sleep` does and why scheduling order is not guaranteed.
- Learner can use `JoinHandle<T>` and `join` to wait for a spawned thread to finish.
- Learner can explain how the placement of `join` affects whether output can be interleaved.
- Learner can explain why closures passed to `thread::spawn` often use `move`.
- Learner can diagnose E0373 when a spawned-thread closure borrows a local value that might not live long enough.
- Learner can diagnose E0382 when code tries to use a value after moving it into a spawned-thread closure.

### Card Content Candidates

#### Concepts

- In most current operating systems, an executed program's code runs in a process.
- The operating system manages multiple processes at once.
- A program can have independent parts that run simultaneously within that program.
- The features that run independent parts of a program are called threads.
- A web server can use multiple threads to respond to more than one request at the same time.
- Multiple threads can improve performance by running multiple tasks at the same time.
- Threads add complexity because there is no inherent guarantee about the order in which code on different threads runs.
- A race condition happens when threads access data or resources in an inconsistent order.
- A deadlock happens when two threads wait for each other and both are prevented from continuing.
- Timing-dependent thread bugs can be hard to reproduce and fix reliably.
- Rust mitigates some negative effects of threads, but multithreaded code still requires careful thought and different structure from single-threaded code.
- Programming languages implement threads in different ways.
- Many operating systems expose APIs for creating new threads.
- Rust's standard library uses a 1:1 thread implementation model.
- A 1:1 model means one Rust language thread maps to one operating system thread.
- Other crates can implement other threading models with different tradeoffs.
- Rust's async system, introduced in CH-17, is another approach to concurrency.
- `thread::spawn` creates a new thread.
- `thread::spawn` takes a closure containing the code to run in the new thread.
- In Listing 16-1, the spawned thread prints numbers 1 through 9 while the main thread prints numbers 1 through 4.
- When the main thread of a Rust program completes, all spawned threads are shut down whether or not they finished.
- Listing 16-1 can stop the spawned thread before it reaches the end of its loop.
- A spawned thread might not get to run at all before the main thread exits.
- `thread::sleep(Duration::from_millis(1))` forces the current thread to stop executing briefly.
- Sleeping gives another thread an opportunity to run, but it does not guarantee a particular schedule.
- Output order from multiple threads can vary between runs because the operating system schedules the threads.
- `thread::spawn` returns `JoinHandle<T>`.
- `JoinHandle<T>` is an owned value representing the spawned thread.
- Calling `join` on a `JoinHandle<T>` waits for the represented thread to finish.
- Calling `join` blocks the thread currently running.
- Blocking a thread means the thread is prevented from doing work or exiting until the blocking operation completes.
- In Listing 16-2, placing `handle.join().unwrap()` after the main thread's loop lets both loops run concurrently and then waits before `main` exits.
- Moving `handle.join().unwrap()` before the main thread's loop makes the main thread wait first, so the output is not interleaved.
- The exact placement of `join` can determine whether threads actually run at the same time.
- Closures passed to `thread::spawn` often use `move`.
- `move` forces the closure to take ownership of values it uses from the surrounding environment.
- Moving ownership into a spawned-thread closure transfers ownership from one thread to another.
- In Listing 16-1, the spawned closure takes no arguments and captures no data from the main thread.
- To use data from the main thread in a spawned thread, the spawned thread's closure must capture the values it needs.
- In Listing 16-3, `println!` only needs a reference to `v`, so Rust infers that the closure should borrow `v`.
- A borrowed local value is not safe for a spawned thread if Rust cannot prove the spawned thread ends before the local value is dropped.
- Rust rejects Listing 16-3 with E0373 because the closure may outlive the current function while borrowing `v`.
- The `thread::spawn` closure must satisfy a lifetime requirement because the spawned thread may outlive the current function.
- Listing 16-4 shows the danger explicitly: the main thread can call `drop(v)` before the spawned thread uses its borrowed reference.
- Adding `move` to Listing 16-3 fixes the error by moving `v` into the spawned thread, so the main thread can no longer invalidate a borrowed reference to it.
- Listing 16-5 compiles because the spawned closure owns `v`.
- Adding `move` to the Listing 16-4 scenario does not permit the main thread to call `drop(v)` afterward.
- Moving `v` into the closure makes a later `drop(v)` in the main thread a use after move.
- Rust rejects the move-plus-drop variant with E0382.
- `move` overrides Rust's conservative default of borrowing for closure captures; it does not bypass ownership rules.

#### Syntax Forms

- Import thread APIs:
  ```rust
  use std::thread;
  use std::time::Duration;
  ```
- Create a spawned thread with a closure:
  ```rust
  thread::spawn(|| {
      for i in 1..10 {
          println!("hi number {i} from the spawned thread!");
          thread::sleep(Duration::from_millis(1));
      }
  });
  ```
- Save a join handle:
  ```rust
  let handle = thread::spawn(|| {
      for i in 1..10 {
          println!("hi number {i} from the spawned thread!");
          thread::sleep(Duration::from_millis(1));
      }
  });
  ```
- Wait for the spawned thread to finish:
  ```rust
  handle.join().unwrap();
  ```
- Joining after other main-thread work:
  ```rust
  for i in 1..5 {
      println!("hi number {i} from the main thread!");
      thread::sleep(Duration::from_millis(1));
  }

  handle.join().unwrap();
  ```
- Joining before other main-thread work:
  ```rust
  handle.join().unwrap();

  for i in 1..5 {
      println!("hi number {i} from the main thread!");
      thread::sleep(Duration::from_millis(1));
  }
  ```
- Spawn a thread that owns captured data:
  ```rust
  let v = vec![1, 2, 3];

  let handle = thread::spawn(move || {
      println!("Here's a vector: {v:?}");
  });

  handle.join().unwrap();
  ```

#### Prediction / Diagnostic Examples

- Predict Listing 16-1: the spawned thread might print only part of its `1..10` loop because `main` exits after its `1..5` loop and shuts down spawned threads.
- Predict Listing 16-1: output can be interleaved in different orders across runs because scheduling is controlled by the operating system.
- Predict Listing 16-2: `handle.join().unwrap()` after the main loop makes `main` wait before exiting, so the spawned thread reaches the end of its loop.
- Predict the join-too-early variant: if `handle.join().unwrap()` appears before the main loop, the spawned thread finishes first and main-thread output happens afterward.
- Diagnose Listing 16-3: a non-`move` closure captures `v` by reference, but the spawned thread may outlive the current function.
- Expected Listing 16-3 diagnostic: E0373, "closure may outlive the current function, but it borrows `v`."
- Compiler help for Listing 16-3: add `move` before `||` to force the closure to take ownership of `v`.
- Diagnose Listing 16-4: the main thread can drop `v` before the spawned thread uses a borrowed reference to it.
- Diagnose the move-plus-drop variant: `move ||` transfers `v` into the closure, so `drop(v)` afterward is a use of a moved value.
- Expected move-plus-drop diagnostic: E0382, "use of moved value: `v`."

#### Failure Modes

- A spawned thread can be shut down before finishing if the main thread exits and no `join` waits for it.
- A spawned thread might not run at all before `main` exits.
- Thread output order should not be treated as deterministic unless the program explicitly synchronizes.
- `thread::sleep` is not a synchronization guarantee; it only pauses the current thread for at least the requested duration.
- Joining too early can serialize work that was intended to run concurrently.
- Borrowing main-thread locals into a spawned thread can be invalid because the spawned thread may outlive those locals.
- Using `move` can fix the lifetime problem by transferring ownership, but the moved value is then unavailable in the original thread.
- `move` cannot be used to keep using the same owned value in both the main thread and the spawned thread.

#### Comparisons

- Process vs thread: an executed program runs in a process; threads are independent parts within a program.
- Single-threaded structure vs multithreaded structure: multithreaded code needs explicit thought about ordering, synchronization, and ownership across threads.
- Rust standard-library threads vs other threading models: standard library uses one operating system thread per language thread; crates can provide other models.
- Threads vs async: standard-library threads are one concurrency tool; the book introduces async as a different approach in CH-17.
- Spawn without join vs spawn with join: without join, the spawned thread may be cut off when `main` exits; with join, the waiting thread blocks until the spawned thread finishes.
- Join after work vs join before work: joining after the main work permits overlap; joining before the main work makes the main thread wait and removes interleaving.
- Borrow capture vs `move` capture: default inference may borrow a used value; `move` forces ownership transfer into the closure.
- Conservative compile rejection vs runtime dangling reference: Rust rejects the borrowed-thread case because the thread might use a reference after the owner is dropped.

#### Project / Architecture Decisions

- Use `join` when program correctness requires a spawned thread to finish before the current thread exits.
- Place `join` at the point where waiting is semantically required, because placing it too early can remove intended concurrency.
- Do not rely on observed output ordering from thread examples as a correctness property.
- Use `move` for spawned-thread closures when the thread needs data from the parent thread and ownership transfer is appropriate.
- Once data is moved into a spawned thread, redesign if the original thread also needs that data: cloning, shared ownership, channels, or synchronization primitives may be required depending on the later CH-16 sections.

#### Listings Worth Converting

- Listing 16-1: `thread::spawn`, two loops, `thread::sleep`, nondeterministic interleaving, and premature shutdown when `main` exits.
- Listing 16-2: `let handle = thread::spawn(...)` and `handle.join().unwrap()` after the main loop to guarantee spawned-thread completion.
- No-listing join-too-early variant: moving `handle.join().unwrap()` before the main loop removes output interleaving.
- Listing 16-3: non-`move` closure tries to print `v` from a spawned thread and fails with E0373.
- Listing 16-4: main thread drops `v` while spawned thread might still hold a borrowed reference, illustrating why Listing 16-3 is rejected.
- Listing 16-5: `thread::spawn(move || { ... })` transfers `v` into the spawned thread and compiles.
- Output-only move/drop variant: adding `move` while still calling `drop(v)` in `main` fails with E0382.

### Card Content Candidates

#### Concepts

- Message passing is a concurrency strategy where threads or actors communicate by sending messages containing data.
- The book introduces the Go slogan: do not communicate by sharing memory; share memory by communicating.
- Rust's standard library provides channels for message-sending concurrency.
- A channel sends data from one thread to another.
- A channel has two halves: a transmitter and a receiver.
- The transmitter is the sending end of the channel.
- The receiver is the receiving end of the channel.
- One part of code calls methods on the transmitter with data to send.
- Another part checks the receiver for arriving messages.
- A channel is closed if either the transmitter half or the receiver half is dropped.
- `mpsc::channel` creates a new channel.
- `mpsc` stands for multiple producer, single consumer.
- Rust standard-library channels can have multiple sending ends that produce values.
- Rust standard-library channels have one receiving end that consumes values.
- Listing 16-6 creates a channel with `let (tx, rx) = mpsc::channel();` but does not compile because Rust cannot infer the channel's message type.
- `mpsc::channel` returns a tuple.
- The first element of the `mpsc::channel` tuple is the transmitter.
- The second element of the `mpsc::channel` tuple is the receiver.
- `tx` and `rx` are conventional abbreviations for transmitter and receiver.
- A `let` pattern can destructure the `(tx, rx)` tuple returned by `mpsc::channel`.
- To send from a spawned thread, move the transmitter into the spawned thread closure.
- The spawned thread needs to own the transmitter to send messages through the channel.
- `tx.send(value)` sends `value` through the channel.
- `send` returns `Result<T, E>`.
- `send` returns an error if the receiver has already been dropped.
- The book uses `unwrap` in simple channel examples but says real applications should handle errors properly.
- `rx.recv()` receives a value from the channel.
- `recv` is short for receive.
- `recv` blocks the current thread until a value is sent.
- `recv` returns the received value inside `Ok`.
- If the transmitter closes, `recv` returns an error to signal that no more values will arrive.
- `try_recv` does not block.
- `try_recv` returns immediately with `Ok(message)` if a message is available.
- `try_recv` returns `Err` immediately if no message is available at that moment.
- `try_recv` is useful when a thread has other work to do while waiting for messages.
- In Listing 16-8, blocking with `recv` is appropriate because the main thread has no other work besides waiting for a message.
- Channel sending interacts with ownership.
- `send` takes ownership of the value being sent.
- Once a value is sent, the receiver owns that value.
- Rust prevents code from using a sent value again in the sending thread.
- Listing 16-9 tries to use `val` after `tx.send(val).unwrap()`.
- Listing 16-9 fails because `String` does not implement `Copy` and `val` is moved into `send`.
- Rust rejects Listing 16-9 with E0382: borrow of moved value.
- The ownership transfer prevents the sending thread from using data that another thread could modify or drop.
- Listing 16-10 sends multiple `String` values from a spawned thread.
- Listing 16-10 pauses one second between sends with `thread::sleep(Duration::from_secs(1))`.
- A receiver can be treated as an iterator.
- Iterating over `rx` yields each received value.
- Iteration over `rx` ends when the channel is closed.
- The main thread waiting in `for received in rx` demonstrates that the receiving thread is waiting for values from the spawned thread.
- Cloning a transmitter creates another sending end for the same receiver.
- Listing 16-11 calls `let tx1 = tx.clone();` before spawning producer threads.
- Listing 16-11 moves `tx1` into one spawned producer and the original `tx` into another spawned producer.
- Multiple producer threads can send different messages to the same single receiver.
- Output from multiple producers may arrive in different orders depending on scheduling.
- Changing sleeps in producer threads can make output more nondeterministic.

#### Syntax Forms

- Import channel APIs:
  ```rust
  use std::sync::mpsc;
  ```
- Create a channel and destructure transmitter/receiver:
  ```rust
  let (tx, rx) = mpsc::channel();
  ```
- Move a transmitter into a spawned thread and send one value:
  ```rust
  let (tx, rx) = mpsc::channel();

  thread::spawn(move || {
      let val = String::from("hi");
      tx.send(val).unwrap();
  });
  ```
- Receive one value and print it:
  ```rust
  let received = rx.recv().unwrap();
  println!("Got: {received}");
  ```
- Compile-fail use after send:
  ```rust
  thread::spawn(move || {
      let val = String::from("hi");
      tx.send(val).unwrap();
      println!("val is {val}");
  });
  ```
- Send multiple values with a pause:
  ```rust
  let vals = vec![
      String::from("hi"),
      String::from("from"),
      String::from("the"),
      String::from("thread"),
  ];

  for val in vals {
      tx.send(val).unwrap();
      thread::sleep(Duration::from_secs(1));
  }
  ```
- Iterate over a receiver:
  ```rust
  for received in rx {
      println!("Got: {received}");
  }
  ```
- Clone a transmitter for multiple producers:
  ```rust
  let tx1 = tx.clone();

  thread::spawn(move || {
      tx1.send(String::from("hi")).unwrap();
  });

  thread::spawn(move || {
      tx.send(String::from("more")).unwrap();
  });
  ```

#### Prediction / Diagnostic Examples

- Predict Listing 16-6: `let (tx, rx) = mpsc::channel();` alone does not compile because the compiler cannot infer what type of values the channel sends.
- Predict Listing 16-7: the spawned thread owns `tx` and can send `"hi"`, but without receiving code the example does not print the message.
- Predict Listing 16-8: `rx.recv().unwrap()` blocks until the spawned thread sends `"hi"`, then `println!` prints `Got: hi`.
- Diagnose receiver-dropped send: `tx.send(value)` returns an error if the receiving half has already been dropped.
- Diagnose Listing 16-9: `tx.send(val).unwrap()` moves the `String` into the channel, so `println!("val is {val}")` borrows a moved value.
- Expected Listing 16-9 diagnostic: E0382, "borrow of moved value: `val`."
- Predict Listing 16-10: each received line appears about one second apart because the sender sleeps between sends and the receiver waits.
- Predict receiver iteration: `for received in rx` continues until all transmitters are dropped and the channel closes.
- Predict Listing 16-11: messages from the two producer threads can be interleaved in different orders across runs.

#### Failure Modes

- A channel with no type usage may fail type inference because Rust cannot know the message type.
- Sending fails if the receiver has already been dropped.
- `recv` can block the current thread indefinitely if no value is sent and the channel remains open.
- `recv` returns an error when all transmitters are closed and no more values can arrive.
- `try_recv` can return an error because there is no message available yet, not only because the channel is permanently closed.
- Using a value after sending it through a channel fails because ownership was transferred.
- Treating multi-producer message order as deterministic is a concurrency bug unless additional ordering is enforced.
- Keeping extra transmitter clones alive can keep receiver iteration from ending because the channel is not closed until sending ends are dropped.

#### Comparisons

- Message passing vs shared state: message passing communicates by sending owned messages; shared state lets multiple threads access the same data.
- Transmitter vs receiver: the transmitter sends values into the channel; the receiver consumes values from the channel.
- Single producer vs multiple producer: one transmitter can send values; cloned transmitters allow multiple producer threads to send into one receiver.
- `recv` vs `try_recv`: `recv` blocks until a message or closure; `try_recv` returns immediately.
- Sending by move vs sharing by reference: `send` transfers ownership, preventing the sender from using the sent value afterward.
- `unwrap` in examples vs real error handling: examples panic on channel errors for simplicity; production code should handle `Result` deliberately.
- `thread::spawn(move || ...)` for channel transmitters vs ordinary borrowed closure: the spawned thread must own the transmitter it uses.

#### Project / Architecture Decisions

- Use message passing when the problem naturally fits one thread producing data and another thread consuming or aggregating it.
- Use `recv` when the receiving thread has no useful work to do until a message arrives.
- Use `try_recv` when the receiving thread should keep doing other work while periodically checking for messages.
- Treat `send` as an ownership transfer in the design: after sending, the sender should not expect to read, mutate, or drop the sent value.
- Clone the transmitter when multiple producer threads should feed one receiving thread.
- Design shutdown so transmitter halves are dropped when no more messages should arrive; otherwise receiver iteration may not finish.
- Do not assume multi-producer message ordering unless the protocol explicitly encodes ordering.

### Card Content Candidates

#### Concepts

- Message passing is not the only concurrency method.
- Shared-state concurrency allows multiple threads to access the same shared data.
- Channels are similar to single ownership because once a value is sent through a channel, the sender should no longer use it.
- Shared-memory concurrency is similar to multiple ownership because multiple threads can access the same memory location.
- Multiple ownership adds management complexity because different owners must be coordinated.
- Rust's type system and ownership rules help manage shared-memory concurrency correctly.
- A mutex is a common shared-memory concurrency primitive.
- `Mutex` is short for mutual exclusion.
- A mutex allows only one thread to access some data at a given time.
- To access data in a mutex, a thread must acquire the mutex's lock.
- A lock is the mutex data structure that tracks which thread currently has exclusive access.
- A mutex is described as guarding the data it holds.
- Mutex rule 1: acquire the lock before using the data.
- Mutex rule 2: unlock the data when done so another thread can acquire the lock.
- Rust's type system and ownership rules make it hard to forget locking and unlocking.
- `Mutex<T>::new(value)` creates a mutex containing `value`.
- `lock` acquires the mutex lock.
- `lock` blocks the current thread until the lock can be acquired.
- `lock` can fail if another thread holding the lock panicked.
- The book examples call `unwrap` on `lock` so the current thread panics if the lock is poisoned.
- The type of `Mutex<i32>` is not `i32`, so code must call `lock` before accessing the inner integer.
- `lock` returns `LockResult<MutexGuard<T>>`.
- `MutexGuard<T>` implements `Deref` to point at the inner data.
- `MutexGuard<T>` also supports mutable access to the inner data when bound mutably.
- `MutexGuard<T>` implements `Drop`.
- The `Drop` implementation releases the mutex lock automatically when the guard goes out of scope.
- Automatic lock release prevents forgetting to unlock the mutex.
- Listing 16-12 uses an inner block so `num` drops before `println!("m = {m:?}")`.
- Listing 16-12 changes a guarded `i32` from `5` to `6`.
- Listing 16-13 tries to spawn 10 threads and increment a mutex-protected counter once per thread.
- Listing 16-13 creates `counter = Mutex::new(0)` and collects thread join handles in a vector.
- Listing 16-13 moves `counter` into the first spawned closure and cannot move it again in later loop iterations.
- Listing 16-13 fails because `Mutex<i32>` does not implement `Copy`.
- Rust rejects Listing 16-13 with E0382: borrow of moved value `counter`.
- `Rc<T>` gives multiple ownership in single-threaded code, but it is not safe to share across threads.
- Listing 16-14 wraps `Mutex<i32>` in `Rc<T>` and clones the `Rc` before moving it into each thread.
- Listing 16-14 fails because `Rc<Mutex<i32>>` cannot be sent between threads safely.
- Rust rejects Listing 16-14 with E0277 because `Send` is not implemented for `Rc<Mutex<i32>>`.
- `Rc<T>` is not thread-safe because it changes its reference count without concurrency primitives.
- Concurrent interruptions of `Rc<T>` reference-count updates could create wrong counts.
- Wrong reference counts could lead to memory leaks or dropping a value before all users are done with it.
- `Arc<T>` is a thread-safe reference-counted type.
- `Arc` stands for atomic reference counting.
- Atomics are concurrency primitives that are safe to share across threads.
- Atomics are not covered in detail in this chapter beyond the role of `Arc<T>`.
- Thread safety has a performance cost.
- Standard-library types do not use `Arc<T>` by default because single-threaded code should not pay the atomic cost unnecessarily.
- `Arc<T>` and `Rc<T>` have the same API shape for this example: `new` and `clone`.
- Listing 16-15 fixes the counter by using `Arc<Mutex<i32>>`.
- Listing 16-15 clones the `Arc` in each loop iteration and moves that clone into the spawned thread.
- Each thread locks the mutex, increments the counter, and drops the guard when the closure ends.
- After joining all handles, the main thread locks the counter and prints `Result: 10`.
- The same structure can divide a calculation into independent pieces, run them on threads, and use a mutex to update the final result.
- For simple numerical operations, `std::sync::atomic` provides simpler safe concurrent atomic access to primitive types.
- `Mutex<T>` provides interior mutability because an immutable `Mutex<T>` value can yield mutable access to its inner data after locking.
- `RefCell<T>` lets code mutate contents inside `Rc<T>`.
- `Mutex<T>` lets code mutate contents inside `Arc<T>`.
- Rust cannot prevent all mutex logic errors.
- A deadlock can happen when an operation needs two resources and two threads each hold one lock while waiting for the other lock forever.
- The standard-library docs for `Mutex<T>` and `MutexGuard` are useful for deadlock and locking details.

#### Syntax Forms

- Create and mutate a mutex in one thread:
  ```rust
  use std::sync::Mutex;

  let m = Mutex::new(5);

  {
      let mut num = m.lock().unwrap();
      *num = 6;
  }

  println!("m = {m:?}");
  ```
- Compile-fail attempt to move one `Mutex` into multiple threads:
  ```rust
  let counter = Mutex::new(0);
  let mut handles = vec![];

  for _ in 0..10 {
      let handle = thread::spawn(move || {
          let mut num = counter.lock().unwrap();
          *num += 1;
      });
      handles.push(handle);
  }
  ```
- Compile-fail attempt with `Rc<Mutex<i32>>`:
  ```rust
  use std::rc::Rc;
  use std::sync::Mutex;

  let counter = Rc::new(Mutex::new(0));

  for _ in 0..10 {
      let counter = Rc::clone(&counter);
      let handle = thread::spawn(move || {
          let mut num = counter.lock().unwrap();
          *num += 1;
      });
      handles.push(handle);
  }
  ```
- Share mutable state across threads with `Arc<Mutex<i32>>`:
  ```rust
  use std::sync::{Arc, Mutex};
  use std::thread;

  let counter = Arc::new(Mutex::new(0));
  let mut handles = vec![];

  for _ in 0..10 {
      let counter = Arc::clone(&counter);
      let handle = thread::spawn(move || {
          let mut num = counter.lock().unwrap();
          *num += 1;
      });
      handles.push(handle);
  }

  for handle in handles {
      handle.join().unwrap();
  }

  println!("Result: {}", *counter.lock().unwrap());
  ```

#### Prediction / Diagnostic Examples

- Predict Listing 16-12: after locking and assigning `*num = 6`, printing the mutex shows the inner data changed to `6`.
- Predict Listing 16-12 guard behavior: the lock is released at the end of the inner block when `num` goes out of scope.
- Diagnose Listing 16-13: the first loop iteration moves `counter` into a spawned closure, so later iterations and the final print cannot use the same `counter`.
- Expected Listing 16-13 diagnostic: E0382, "borrow of moved value: `counter`."
- Diagnose Listing 16-14: `Rc<Mutex<i32>>` gives multiple ownership but cannot be sent between threads safely.
- Expected Listing 16-14 diagnostic: E0277, "`Rc<std::sync::Mutex<i32>>` cannot be sent between threads safely."
- Key Listing 16-14 trait reason: `Send` is not implemented for `Rc<Mutex<i32>>`.
- Predict Listing 16-15: after 10 spawned threads each increment once and all handles are joined, the program prints `Result: 10`.
- Predict `lock` failure handling in the examples: if a lock is poisoned by a panic while held, `lock().unwrap()` panics.
- Predict deadlock shape: if two threads each hold one mutex and wait for the other, both can wait forever.

#### Failure Modes

- Forgetting to acquire a lock before using guarded data is a mutex API error in many languages; Rust prevents direct access because the inner value is behind `Mutex<T>`.
- Forgetting to release a lock can block other threads forever; Rust reduces this risk by releasing the lock when `MutexGuard<T>` is dropped.
- `lock` blocks, so waiting for a mutex can prevent a thread from doing other work.
- `lock` can fail if another thread panicked while holding the lock.
- Moving one `Mutex<T>` into multiple threads fails because a non-`Copy` value can only be moved once.
- `Rc<T>` reference counts are not thread-safe, so `Rc<Mutex<T>>` cannot be sent between threads.
- `Arc<T>` thread safety has performance overhead, so using it everywhere is not free.
- `Mutex<T>` can still be used in programs with deadlock logic bugs.
- `Mutex<T>` around primitive numeric operations can be more than needed when atomic primitive types fit the problem.

#### Comparisons

- Message passing vs shared-state concurrency: channels transfer ownership of values; shared state lets multiple threads access one memory location.
- Single ownership vs multiple ownership analogy: channel send is like single ownership transfer; shared memory is like multiple ownership.
- `Mutex<T>` vs inner `T`: `Mutex<i32>` must be locked before code can access the inner `i32`.
- Manual lock/unlock in general vs Rust mutex guard: Rust releases the lock automatically when the guard is dropped.
- `Rc<T>` vs `Arc<T>`: both provide reference-counted shared ownership, but `Rc<T>` is single-threaded and `Arc<T>` is safe to use across threads.
- `Rc<RefCell<T>>` vs `Arc<Mutex<T>>`: `Rc<RefCell<T>>` supports single-threaded shared mutation; `Arc<Mutex<T>>` supports shared mutation across threads.
- `RefCell<T>` vs `Mutex<T>`: both provide interior mutability, but `Mutex<T>` coordinates access across threads and can block.
- `Mutex<T>` vs atomic primitives: mutexes guard arbitrary data through locking; atomics provide simpler concurrent access for primitive numeric operations.
- `Arc<T>` default vs pay-as-needed: Rust does not make every shared value atomic because atomics impose a performance penalty.

#### Project / Architecture Decisions

- Use shared-state concurrency when the problem naturally requires multiple threads to update or consult the same shared state.
- Put shared mutable thread state behind `Arc<Mutex<T>>` when multiple spawned threads need ownership of the same mutex-protected value.
- Clone the `Arc`, not the underlying mutex-protected value, before moving it into each thread.
- Keep the critical section small: lock, update the guarded data, then let the guard drop.
- Join worker threads before reading a final shared result that depends on all workers.
- Do not use `Rc<T>` for cross-thread sharing; use `Arc<T>` when shared ownership must cross thread boundaries.
- Consider atomic primitive types instead of `Mutex<T>` for simple counters or numeric operations where atomics fit.
- Treat deadlock avoidance as a design responsibility even though Rust helps with lock acquisition and release mechanics.

### Card Content Candidates

#### Concepts

- Most concurrency features covered in CH-16 are part of the standard library, not the Rust language itself.
- Rust concurrency options are not limited to the language or standard library.
- Programmers can write custom concurrency features or use concurrency features written by others.
- `Send` and `Sync` are key concurrency concepts embedded in the language.
- `Send` and `Sync` are `std::marker` traits.
- A marker trait has no methods to implement.
- Marker traits are useful for enforcing invariants.
- `Send` indicates that ownership of values of the implementing type can be transferred between threads.
- Almost every Rust type implements `Send`.
- `Rc<T>` does not implement `Send`.
- `Rc<T>` cannot implement `Send` because cloned `Rc<T>` values in multiple threads could update the reference count at the same time.
- `Rc<T>` is for single-threaded situations where code should not pay the thread-safe performance penalty.
- Rust's type system and trait bounds prevent accidentally sending `Rc<T>` values across threads unsafely.
- Listing 16-14 failed because `Send` is not implemented for `Rc<Mutex<i32>>`.
- Listing 16-15 compiled after switching to `Arc<T>` because `Arc<T>` implements `Send`.
- Any type composed entirely of `Send` types is automatically marked as `Send`.
- Almost all primitive types are `Send`.
- Raw pointers are an exception to the "almost all primitive types are `Send`" statement and are deferred to Chapter 20.
- `Sync` indicates that it is safe for values of the implementing type to be referenced from multiple threads.
- A type `T` implements `Sync` if `&T` implements `Send`.
- `&T: Send` means an immutable reference to `T` can be sent safely to another thread.
- Primitive types all implement `Sync`.
- Types composed entirely of `Sync` types automatically implement `Sync`.
- `Rc<T>` does not implement `Sync` for the same reason it does not implement `Send`.
- `RefCell<T>` does not implement `Sync`.
- The related family of `Cell<T>` types does not implement `Sync`.
- `RefCell<T>` runtime borrow checking is not thread-safe.
- `Mutex<T>` implements `Sync`.
- `Mutex<T>` can be used to share access with multiple threads.
- Types composed entirely of `Send` and `Sync` parts automatically implement `Send` and `Sync`.
- Because of automatic marker-trait implementation, ordinary code usually does not manually implement `Send` or `Sync`.
- Manually implementing `Send` or `Sync` involves unsafe Rust code.
- Building new concurrent types from parts that are not already `Send` and `Sync` requires careful thought to uphold safety guarantees.
- The Rustonomicon has more information about the guarantees behind unsafe concurrent type implementations.
- CH-17 focuses on async programming.
- CH-21 uses CH-16 concurrency concepts in a more realistic project.
- Many concurrency solutions are implemented as crates and can evolve faster than the standard library.
- The standard library provides channels for message passing.
- The standard library provides smart pointer types such as `Mutex<T>` and `Arc<T>` that are safe to use in concurrent contexts.
- The type system and borrow checker ensure code using the covered solutions avoids data races and invalid references.
- Once concurrent Rust code using these tools compiles, the book presents it as protected from many hard-to-track-down bugs common in other languages.

#### Failure Modes

- Sending `Rc<T>` across threads would be unsafe because multiple threads could update the same reference count concurrently.
- Sharing `Rc<T>` references across threads is unsafe for the same reference-counting reason.
- Sharing `RefCell<T>` or `Cell<T>` across threads is unsafe because their interior-mutability bookkeeping is not thread-safe.
- Manually implementing `Send` or `Sync` without upholding the required invariants can make a custom concurrent type unsound.
- Treating compile success as proof of all possible logical correctness is too broad; the guarantees here are about data races, invalid references, and the encoded trait invariants.

#### Comparisons

- Standard library vs language: channels, `Mutex<T>`, and `Arc<T>` are standard-library tools; `Send` and `Sync` are marker traits in the language's concurrency model.
- `Send` vs `Sync`: `Send` is about transferring ownership between threads; `Sync` is about allowing references from multiple threads.
- `Rc<T>` vs `Arc<T>` through `Send`: `Rc<T>` is single-threaded and not `Send`; `Arc<T>` is atomically reference counted and can satisfy thread-transfer requirements.
- `RefCell<T>` vs `Mutex<T>` through `Sync`: `RefCell<T>` runtime borrow checking is not thread-safe; `Mutex<T>` coordinates access and implements `Sync`.

#### Project / Architecture Decisions

- Let the compiler derive `Send` and `Sync` for types composed of thread-safe parts instead of manually implementing them.
- Avoid manually implementing `Send` or `Sync` unless building a low-level concurrent abstraction and prepared to reason with unsafe Rust invariants.
