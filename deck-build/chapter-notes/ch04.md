### Card Content Candidates

#### Concepts

- Ownership is a set of rules that governs how a Rust program manages memory.
- All programs must manage how they use memory while running.
- Other memory-management approaches named here: garbage collection and explicit allocate/free.
- Rust manages memory through ownership rules that the compiler checks.
- If ownership rules are violated, the program will not compile.
- Ownership features do not slow a program while it is running.
- Ownership becomes easier to use as familiarity with Rust's rules grows.
- Strings are used in this chapter because they are common and exercise heap ownership.
- Stack and heap are both runtime memory available to code, but they are structured differently.
- Stack storage is last in, first out (LIFO).
- Adding stack data is pushing onto the stack; removing it is popping off the stack.
- Stack data must have a known, fixed size.
- Data with an unknown compile-time size or a size that might change must be stored on the heap.
- Heap allocation requests an amount of space from the memory allocator.
- The allocator finds a big enough empty spot, marks it in use, and returns a pointer to that address.
- A pointer has a known, fixed size and can be stored on the stack.
- Accessing heap data requires following the pointer.
- Pushing to the stack is faster than allocating on the heap because the stack location is always at the top.
- Allocating on the heap is more work because the allocator must find space and perform bookkeeping.
- Heap access is generally slower than stack access because pointer following jumps around in memory.
- Function arguments, including possible heap pointers, and local variables are pushed onto the stack during a function call and popped when the function ends.
- Ownership addresses tracking heap data use, minimizing duplicate heap data, and cleaning up unused heap data.
- The main purpose of ownership is to manage heap data.
- Ownership rules:
  - Each value in Rust has an owner.
  - There can only be one owner at a time.
  - When the owner goes out of scope, the value is dropped.
- Scope is the range in a program for which an item is valid.
- A variable is valid from its declaration until the end of its current scope.
- A string literal's text is hardcoded into the program.
- String literals are immutable.
- `String` manages heap-allocated data.
- `String` can store text whose amount is unknown at compile time.
- `String::from("hello")` creates a `String` from a string literal.
- The `::` operator namespaces `from` under the `String` type.
- `String` can be mutated when the binding is mutable, as with `let mut s`.
- `push_str` appends a string literal to a `String`.
- A string literal is fast and efficient because known immutable text can be hardcoded into the executable.
- A mutable growable `String` needs heap memory whose size is unknown at compile time.
- `String::from` requests heap memory at runtime.
- Rust automatically returns a `String`'s memory to the allocator when the owning variable goes out of scope.
- Rust calls the special `drop` function automatically at the closing curly bracket when an owner goes out of scope.
- RAII is mentioned as the C++ name for deallocating resources at the end of an item's lifetime.
- Assigning an integer like `let y = x;` copies the value because integers are fixed-size stack data.
- A `String` value on the stack contains a pointer, a length, and a capacity.
- The heap holds the actual `String` contents.
- Assigning `let s2 = s1;` copies the stack metadata: pointer, length, and capacity.
- Assigning `let s2 = s1;` does not copy the heap data.
- If two `String` variables both stayed valid while pointing at the same heap allocation, both would try to free it, causing a double free.
- Double free is a memory safety bug that can lead to memory corruption and security vulnerabilities.
- To preserve memory safety, after `let s2 = s1;`, Rust considers `s1` no longer valid.
- The ownership transfer from `s1` to `s2` is a move.
- A Rust move is not just a shallow copy because the previous variable is invalidated.
- Rust never automatically creates deep copies of data.
- Automatic copying can be assumed inexpensive in runtime-performance terms.
- Assigning a completely new value to an existing variable causes Rust to call `drop` and free the original value's memory immediately.
- In `let mut s = String::from("hello"); s = String::from("ahoy");`, the original `"hello"` allocation is freed before the later print.
- `clone` explicitly deeply copies heap data.
- A `clone` call is a visual indicator that arbitrary code may run and may be expensive.
- Stack-only data such as integers can remain valid after assignment because copying the actual values is quick and there is no heap ownership to transfer.
- `Copy` is a trait for stack-stored types whose variables are trivially copied instead of moved.
- If a type implements `Copy`, variables of that type remain valid after assignment to another variable.
- Rust will not allow a type to implement `Copy` if the type, or any part of it, implements `Drop`.
- General `Copy` rule: simple scalar groups can implement `Copy`; anything requiring allocation or another resource cannot.
- Types named as `Copy`: all integer types such as `u32`, `bool`, all floating-point types such as `f64`, `char`, and tuples containing only `Copy` types.
- Tuple example: `(i32, i32)` implements `Copy`, but `(i32, String)` does not.
- Passing a value to a function moves or copies just like assignment.
- Passing a `String` to a function transfers ownership to the function parameter.
- Passing an `i32` to a function copies it, so the caller can still use the original.
- Returning a value can transfer ownership to the caller.
- Assigning a returned value moves it into the receiving variable.
- Heap data is cleaned up by `drop` when its owner goes out of scope unless ownership has moved elsewhere.
- Returning a tuple such as `(String, usize)` can return ownership of a parameter along with another result.
- Returning ownership in tuples is cumbersome enough that the next section introduces references for using a value without transferring ownership.

#### Failure Modes

- Treating ownership rules as runtime checks; this section says the compiler checks them and they do not slow runtime execution.
- Assuming stack and heap data behave the same for ownership.
- Assuming `String` literals and `String` have the same memory behavior.
- Forgetting that string literals are immutable and hardcoded in the executable.
- Forgetting that mutable growable `String` data is allocated on the heap.
- Trying to use a `String` after moving it to another variable.
- Calling `let s2 = s1;` a shallow copy; Rust calls this a move because `s1` is invalidated.
- Expecting Rust to automatically deep-copy heap data.
- Assuming `clone` is free or always cheap.
- Forgetting that reassigning a new value to an existing owning variable drops the previous value immediately.
- Believing two owners can safely free the same heap allocation; Rust prevents this double-free scenario.
- Assuming every type is `Copy`; resource-owning or allocating types such as `String` are not.
- Trying to implement `Copy` on a type that implements `Drop` or contains a `Drop` part.
- Using a moved `String` after passing it by value into a function.
- Forgetting that returning ownership with every function can become tedious; this is the motivation for references in the next section.

#### Comparisons

- Garbage collection vs explicit free vs Rust ownership: GC cleans unused memory automatically, manual languages require explicit free, and Rust uses compiler-checked ownership plus automatic `drop`.
- Stack vs heap: LIFO fixed-size storage vs allocator-managed variable-size storage reached through pointers.
- Push/pop vs allocate: stack operations use the top of the stack; heap allocation searches for space and performs bookkeeping.
- Stack access vs heap access: direct nearby data vs pointer-following to less-local data.
- String literal vs `String`: hardcoded immutable text known at compile time vs heap-allocated growable text whose size can be unknown at compile time.
- Move vs shallow copy: both copy pointer/length/capacity, but a Rust move invalidates the source.
- Move vs deep copy: move copies stack metadata and transfers ownership; deep copy duplicates heap data too.
- Assignment move vs function argument move: passing a value to a function follows the same move/copy rules as assignment.
- `clone` vs automatic copy: explicit potentially expensive heap copy vs implicit cheap copy.
- `Copy` vs move: `Copy` types remain valid after assignment; moved non-`Copy` values do not.
- `Copy` vs `Drop`: a type cannot be `Copy` if it needs `Drop` behavior.
- Returning ownership vs borrowing: returning ownership works, including through tuples, but references are introduced to use values without transferring ownership.

### Learning Objectives

- Learner can explain a reference as an address to data owned by another variable, guaranteed valid for the reference's lifetime.
- Learner can use `&` to pass a reference without transferring ownership.
- Learner can explain borrowing as creating a reference and using a value without owning it.
- Learner can write a function parameter of type `&String` and explain why the caller can still use the original `String`.
- Learner can diagnose E0596 when code tries to mutate through an immutable reference.
- Learner can write and explain a mutable reference with `&mut`.
- Learner can apply the rule that at any time a value can have either one mutable reference or any number of immutable references.
- Learner can diagnose E0499 for simultaneous mutable borrows and E0502 for overlapping immutable and mutable borrows.
- Learner can explain how reference scope runs from introduction through last use, not necessarily to the end of the lexical block.
- Learner can identify dangling-reference attempts and explain why Rust rejects them.
- Learner can state the two recap rules for references: one mutable or any number of immutable references, and references must always be valid.

### Card Content Candidates

#### Concepts

- Returning ownership in tuples, as in Listing 4-5, is tedious because the caller needs the original `String` after `calculate_length`.
- A reference lets a function access a `String` value without taking ownership of it.
- A reference is like a pointer because it is an address that can be followed to access data stored at that address.
- The data behind a reference is owned by another variable.
- Unlike a raw pointer, a Rust reference is guaranteed to point to a valid value of a particular type for the life of that reference.
- `&s1` creates a reference to the value of `s1`.
- Passing `&s1` into `calculate_length` means the function borrows the string instead of taking ownership.
- A function parameter type `&String` means the parameter is a reference to a `String`.
- The ampersand `&` in expressions and types represents references in this section.
- A reference does not own the value it points to.
- Because a reference does not own its referent, the referent is not dropped when the reference stops being used.
- The parameter reference `s` in `fn calculate_length(s: &String)` has an ordinary parameter scope, but it does not drop the `String` when it goes out of scope.
- If a function takes references rather than owned values, it does not need to return values just to give ownership back.
- Borrowing is the action of creating a reference.
- References are immutable by default, like variables.
- Code cannot mutate something through an immutable reference.
- A mutable reference is written with `&mut`.
- To mutate through a reference, the original binding must be mutable, the call must pass `&mut value`, and the function parameter must accept `&mut Type`.
- A function taking `some_string: &mut String` makes clear that it will mutate the borrowed value.
- Mutable-reference restriction: if there is a mutable reference to a value, there can be no other references to that value at the same time.
- Creating two mutable references to the same value in overlapping scopes is disallowed.
- The rule against multiple simultaneous mutable references allows mutation, but only in controlled fashion.
- Rust's mutable-reference restrictions prevent data races at compile time.
- A data race occurs when:
  - two or more pointers access the same data at the same time,
  - at least one pointer is writing to the data,
  - and no synchronization mechanism is used.
- Data races cause undefined behavior and are difficult to diagnose at runtime.
- Separate nested scopes can make multiple mutable references valid if they are not simultaneous.
- Rust also forbids a mutable reference while immutable references to the same value are still in use.
- Multiple immutable references are allowed because readers cannot affect each other's reads.
- Users of immutable references do not expect the value to change underneath them.
- A reference's scope starts when it is introduced and continues through the last time that reference is used.
- A mutable reference can be created after immutable references' last use, even within the same lexical block.
- Borrowing errors are compile-time reports of potential bugs, not runtime surprises.
- A dangling pointer is a pointer to memory that may have been given to someone else.
- Rust guarantees references will never be dangling references.
- If a reference exists, the compiler ensures the referenced data does not go out of scope before the reference does.
- Returning `&s` from a function where `s` is local would create a dangling reference because `s` is deallocated when the function ends.
- The dangling-reference error output mentions lifetimes, which are detailed in Chapter 10.
- The key dangling-reference diagnostic text: the return type contains a borrowed value, but there is no value for it to be borrowed from.
- The fix for the `dangle` example is to return the owned `String` directly.
- Returning `String` from `no_dangle` moves ownership out, so nothing is deallocated before the caller receives it.
- Reference recap rule 1: at any given time, you can have either one mutable reference or any number of immutable references.
- Reference recap rule 2: references must always be valid.
- Dereferencing is the opposite of referencing and uses `*`, but detailed dereferencing is deferred to Chapters 8 and 15.

#### Syntax Forms

- Borrowing a `String` to calculate its length without moving it:
  ```rust
  fn main() {
      let s1 = String::from("hello");

      let len = calculate_length(&s1);

      println!("The length of '{s1}' is {len}.");
  }

  fn calculate_length(s: &String) -> usize {
      s.len()
  }
  ```
- Focused call form:
  ```rust

  ```
- Reference parameter form:
  ```rust

  }
  ```
- Attempting to mutate through an immutable reference, intentionally compile-fail:
  ```rust
  fn main() {

  }

  fn change(some_string: &String) {
      some_string.push_str(", world");
  }
  ```

  ```rust
  fn main() {
      let mut s = String::from("hello");

      change(&mut s);
  }

  fn change(some_string: &mut String) {
      some_string.push_str(", world");
  }
  ```
- Two simultaneous mutable references, intentionally compile-fail:
  ```rust
  let mut s = String::from("hello");

  let r1 = &mut s;
  let r2 = &mut s;

  println!("{r1}, {r2}");
  ```
- Multiple mutable references in separate scopes:
  ```rust
  let mut s = String::from("hello");

  {
      let r1 = &mut s;
  }

  let r2 = &mut s;
  ```
- Immutable and mutable references overlapping, intentionally compile-fail:
  ```rust
  let mut s = String::from("hello");

  let r1 = &s;
  let r2 = &s;
  let r3 = &mut s;

  println!("{r1}, {r2}, and {r3}");
  ```
- Immutable reference scopes end at last use, so later mutable borrow is valid:
  ```rust
  let mut s = String::from("hello");

  let r1 = &s;
  let r2 = &s;
  println!("{r1} and {r2}");

  let r3 = &mut s;
  println!("{r3}");
  ```
- Dangling reference attempt, intentionally compile-fail:
  ```rust
  fn main() {
      let reference_to_nothing = dangle();
  }

  fn dangle() -> &String {
      let s = String::from("hello");

      &s
  }
  ```
- Return owned value instead of dangling reference:
  ```rust
  fn main() {
      let string = no_dangle();
  }

  fn no_dangle() -> String {
      let s = String::from("hello");

      s
  }
  ```

#### Failure Modes

- Returning ownership from helper functions just to keep using a value when a reference would avoid ownership transfer.
- Treating a reference as an owner of the underlying value.
- Expecting the referent to be dropped when a reference goes out of scope.
- Trying to mutate through an immutable reference.
- Adding `&mut` only at the call site without also making the original binding mutable and the parameter type mutable.
- Creating two mutable references to the same value and using both in overlapping scopes.
- Assuming mutable references and immutable references can overlap because immutable references are "only reads".
- Forgetting that multiple immutable references are allowed only because none can mutate the data.
- Treating reference scope as always ending at the lexical closing brace; this section says it extends through the last use.
- Returning a reference to a local value that will be deallocated when the function returns.
- Over-teaching explicit lifetime syntax from this section; lifetimes are named in the error but deferred to Chapter 10.
- Treating the suggested `'static` lifetime in E0106 as the usual fix; the compiler output says returning an owned value is more likely.

#### Comparisons

- Owned value parameter vs reference parameter: takes ownership and may require returning ownership vs borrows without taking ownership.
- Reference vs pointer: both are addresses to data, but references are guaranteed valid for their lifetime and have a particular type.
- Referencing vs dereferencing: `&` creates a reference; `*` dereferences, with details deferred.
- Immutable reference vs mutable reference: `&T` cannot mutate; `&mut T` can mutate if borrow rules permit it.
- One mutable reference vs many immutable references: exclusive mutation vs shared reading.
- Simultaneous mutable borrows vs sequential mutable borrows: overlapping `&mut` is disallowed; separated scopes can be allowed.
- Lexical scope vs reference-use scope: variable block may continue, but a reference's borrow scope can end after its last use.
- Dangling pointer vs Rust reference: dangling pointers are possible in pointer languages; Rust references are compiler-checked to remain valid.
- Returning `&String` local reference vs returning `String`: invalid borrowed return from deallocated local vs valid ownership move to caller.

### Card Content Candidates

#### Concepts

- A slice references a contiguous sequence of elements in a collection.
- A slice is a kind of reference, so it does not own the data it refers to.
- The section's first-word problem assumes ASCII only; fuller UTF-8 text handling is deferred to Chapter 8.
- A `first_word(s: &String) -> usize` function can return the byte index of the first space.
- `s.as_bytes()` converts a `String` reference into an array of bytes for byte-by-byte inspection.
- `.iter()` returns each element in a collection.
- `.enumerate()` wraps iterator results and returns a tuple containing the index and a reference to the element.
- The `for (i, &item)` pattern destructures the `(index, reference_to_byte)` tuple from `.iter().enumerate()`.
- The byte literal `b' '` represents the space byte.
- If `first_word` finds a space byte, it returns that position.
- If `first_word` finds no space, it returns `s.len()` because the whole string is one word.
- A standalone `usize` index is only meaningful in the context of the `String` state it came from.
- A returned index can get out of sync with the `String` if the string changes later.
- Listing 4-8 compiles even though `word` still contains `5` after `s.clear()` empties the string.
- A `second_word` function returning indices would need both a starting and ending index, increasing the number of values that must stay in sync.
- String slices solve the stale-index problem by tying the result to the underlying data.
- A string slice is a reference to a contiguous sequence of elements in a `String`.
- String slice type is written `&str`.
- `&s[0..5]` creates a slice of `s` using the range inside square brackets.
- In `[starting_index..ending_index]`, the starting index is included and the ending index is one more than the last position included.
- A string slice internally stores a pointer to the start of the slice and the length of the slice.
- For `let world = &s[6..11];`, the slice points to byte index `6` with length `5`.
- If a slice starts at index `0`, the leading `0` can be omitted: `&s[0..2]` and `&s[..2]` are equal.
- If a slice includes the last byte of the string, the trailing length can be omitted: `&s[3..len]` and `&s[3..]` are equal.
- A whole-string slice can omit both bounds: `&s[0..len]` and `&s[..]` are equal.
- String slice range indices must be valid UTF-8 character boundaries.
- Attempting to create a string slice in the middle of a multibyte character makes the program exit with an error.
- A slice-returning `first_word` returns `&s[0..i]` when it finds a space and `&s[..]` when the whole string is one word.
- A returned string slice is a single value made of a reference to the slice start and a number of elements.
- A slice-returning API is harder to misuse because the compiler ensures references into the `String` remain valid.
- In the slice-error example, `word` is an immutable reference into `s`.
- `s.clear()` needs a mutable reference because it truncates the `String`.
- The `println!` after `s.clear()` uses `word`, so the immutable reference remains active through that use.
- Rust rejects the `clear` call because it would require a mutable reference while an immutable reference is still active.
- String literals are stored in the binary.
- A string literal such as `"Hello, world!"` has type `&str`.
- String literals are immutable because `&str` is an immutable reference.
- `fn first_word(s: &str) -> &str` is more general than `fn first_word(s: &String) -> &str`.
- A `&str` parameter allows the same function to accept string slices, whole `String` slices, references to `String`, and string literals.
- Passing `&String` to an `&str` parameter works because of deref coercions, which are deferred to Chapter 15.
- Array slices use the same kind of slice idea for arrays and have types such as `&[i32]`.
- `&a[1..3]` over `[1, 2, 3, 4, 5]` refers to `[2, 3]`.
- General slices store a reference to the first element and a length.
- Ownership, borrowing, and slices ensure memory safety at compile time.
- Rust gives systems-programming memory control while automatically cleaning up data when its owner goes out of scope.

#### Syntax Forms

- Index-returning `first_word`:
  ```rust
  fn first_word(s: &String) -> usize {
      let bytes = s.as_bytes();

      for (i, &item) in bytes.iter().enumerate() {
          if item == b' ' {
              return i;
          }
      }

      s.len()
  }
  ```
- Stale index after mutating the `String`:
  ```rust
  fn main() {
      let mut s = String::from("hello world");

      let word = first_word(&s);

      s.clear();
  }
  ```
- Basic string slices:
  ```rust
  let s = String::from("hello world");

  let hello = &s[0..5];
  let world = &s[6..11];
  ```
- Equivalent slice forms from the beginning:
  ```rust
  let s = String::from("hello");

  let slice = &s[0..2];
  let slice = &s[..2];
  ```
- Equivalent slice forms through the end:
  ```rust
  let s = String::from("hello");

  let len = s.len();

  let slice = &s[3..len];
  let slice = &s[3..];
  ```
- Equivalent whole-string slice forms:
  ```rust
  let s = String::from("hello");

  let len = s.len();

  let slice = &s[0..len];
  let slice = &s[..];
  ```
- `first_word` returning a string slice:
  ```rust
  fn first_word(s: &String) -> &str {
      let bytes = s.as_bytes();

      for (i, &item) in bytes.iter().enumerate() {
          if item == b' ' {
              return &s[0..i];
          }
      }

      &s[..]
  }
  ```
- Clearing a `String` while a slice is still used, intentionally compile-fail:
  ```rust
  fn main() {
      let mut s = String::from("hello world");

      let word = first_word(&s);

      s.clear();

      println!("the first word is: {word}");
  }
  ```
- String literal as `&str`:
  ```rust
  let s = "Hello, world!";
  ```
- More general `first_word` signature:
  ```rust
  fn first_word(s: &str) -> &str {
      let bytes = s.as_bytes();

      for (i, &item) in bytes.iter().enumerate() {
          if item == b' ' {
              return &s[0..i];
          }
      }

      &s[..]
  }
  ```
- Calling `first_word` with `String` slices, `&String`, and string literals:
  ```rust
  fn main() {
      let my_string = String::from("hello world");

      let word = first_word(&my_string[0..6]);
      let word = first_word(&my_string[..]);
      let word = first_word(&my_string);

      let my_string_literal = "hello world";

      let word = first_word(&my_string_literal[0..6]);
      let word = first_word(&my_string_literal[..]);
      let word = first_word(my_string_literal);
  }
  ```
- Array slice:
  ```rust
  let a = [1, 2, 3, 4, 5];

  let slice = &a[1..3];

  assert_eq!(slice, &[2, 3]);
  ```

#### Failure Modes

- Returning a standalone index that is meaningful only for one state of a `String`.
- Keeping multiple unrelated index variables that must stay synchronized with changing string data.
- Treating `usize` indices as safe references to string content.
- Assuming Listing 4-8 is safe because it compiles; the source calls it logically incorrect.
- Forgetting that string-slice end indices are exclusive.
- Slicing a `String` at non-UTF-8 character boundaries.
- Treating a string slice as owning data; slices are references and do not own data.
- Calling `s.clear()` while a string slice into `s` will still be used.
- Writing APIs that accept `&String` when `&str` would accept both `String` data and string literals.
- Over-teaching deref coercions here; the source names them but defers details to Chapter 15.
- Treating string literals as owned `String` values; the source says their type is `&str`.

#### Comparisons

- Index return vs slice return: standalone `usize` can go stale; `&str` remains tied to the underlying data by borrow checking.
- `first_word(s: &String) -> usize` vs `first_word(s: &String) -> &str`: byte index into a state vs reference to the first-word data.
- `&String` parameter vs `&str` parameter: less general owned-string reference vs more general string slice interface.
- String slice vs string literal: both are `&str`; literals point into the binary.
- String slice vs array slice: `&str` for string data vs `&[T]` for sequences such as arrays; both store a start reference and length.
- Partial slice vs whole slice: bounded range such as `&s[0..5]` vs `&s[..]`.
- Immutable slice borrow vs mutable `clear`: shared read reference remains active vs mutable truncation of the underlying `String`.
