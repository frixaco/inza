#### Concepts

- Safe Rust enforces memory safety guarantees at compile time.
- Unsafe Rust is a second part of Rust that works like regular Rust but allows extra operations.
- Unsafe Rust exists because static analysis is conservative.
- The compiler should reject some valid programs rather than accept invalid programs.
- Unsafe code lets the programmer tell the compiler to trust that the programmer knows what they are doing.
- Incorrect unsafe code can create memory unsafety, such as null pointer dereferencing.
- Unsafe Rust also exists because computer hardware is inherently unsafe.
- Some low-level systems programming tasks require operations Rust cannot prove safe.
- Direct operating system interaction and writing an operating system are examples of tasks that can need unsafe operations.
- To switch to unsafe Rust, use the `unsafe` keyword and start a new block containing unsafe code.
- The five unsafe capabilities are called unsafe superpowers in the source.
- The first unsafe capability is dereferencing a raw pointer.
- The second unsafe capability is calling an unsafe function or method.
- The third unsafe capability is accessing or modifying a mutable static variable.
- The fourth unsafe capability is implementing an unsafe trait.
- The fifth unsafe capability is accessing fields of a `union`.
- `unsafe` does not turn off the borrow checker.
- `unsafe` does not disable Rust's other safety checks.
- References used in unsafe code are still checked.
- `unsafe` only grants access to the five operations whose memory safety the compiler cannot check.
- Code inside an `unsafe` block is not necessarily dangerous or memory-unsafe.
- The programmer must ensure code inside an `unsafe` block accesses memory validly.
- Requiring unsafe operations to be inside `unsafe` blocks localizes likely memory-safety bugs.
- Unsafe blocks should be kept small.
- Unsafe code should be isolated inside safe abstractions when possible.
- Parts of the standard library are safe abstractions over audited unsafe code.
- Safe abstractions prevent unsafe requirements from leaking into every caller.
- Raw pointers are similar to references but are not checked like references.
- Raw pointer types are written `*const T` and `*mut T`.
- `*const T` is an immutable raw pointer type.
- `*mut T` is a mutable raw pointer type.
- In raw pointer type names, `*` is part of the type name rather than the dereference operator.
- For raw pointers, immutable means the pointer cannot be directly assigned to after being dereferenced.
- Raw pointers can ignore borrowing rules by allowing immutable and mutable pointers or multiple mutable pointers to the same location.
- Raw pointers are not guaranteed to point to valid memory.
- Raw pointers are allowed to be null.
- Raw pointers do not implement automatic cleanup.
- Raw pointers trade guaranteed safety for performance or interoperability with other languages or hardware.
- Listing 20-1 creates raw pointers with raw borrow operators.
- `&raw const num` creates a `*const i32`.
- `&raw mut num` creates a `*mut i32`.
- Creating raw pointers is allowed in safe code.
- Dereferencing raw pointers is not allowed outside an `unsafe` block.
- Raw pointers created directly from a local variable are known valid in that local case.
- Listing 20-2 creates a raw pointer from an arbitrary address with `as`.
- Creating a raw pointer to arbitrary memory is possible but usually has no good reason when raw borrow operators can be used.
- Using arbitrary memory is undefined because the address might not contain valid data, might not be accessed after optimization, or might segfault.
- Listing 20-3 dereferences raw pointers with `*r1` and `*r2` inside an `unsafe` block.
- Creating a pointer does no harm by itself.
- Accessing the value behind a raw pointer is where invalid memory can become a problem.
- Raw pointers can point mutably and immutably to the same memory at the same time.
- Equivalent immutable and mutable references to the same value would violate Rust ownership rules.
- Changing data through a raw pointer while other pointers exist can potentially create a data race.
- A major raw-pointer use case is interfacing with C code.
- Another raw-pointer use case is building safe abstractions the borrow checker does not understand.
- Unsafe functions and methods have `unsafe` before their definition.
- `unsafe fn` means callers must uphold requirements Rust cannot guarantee.
- Calling an unsafe function requires an `unsafe` block.
- Calling an unsafe function asserts that the caller has read the documentation, understands proper use, and verified the function contract.
- Calling `dangerous()` without an unsafe block produces E0133.
- E0133 says a call to an unsafe function requires an unsafe block.
- Unsafe operations inside an `unsafe fn` still require `unsafe` blocks.
- The compiler warns if unsafe operations inside an unsafe function are not enclosed in an unsafe block.
- Inner unsafe blocks inside unsafe functions keep unsafe operations as small as possible.
- A function containing unsafe code does not necessarily need to be marked unsafe.
- Wrapping unsafe code in a safe function is a common abstraction.
- `split_at_mut` is a safe standard-library method on mutable slices.
- `split_at_mut` takes one mutable slice and returns two mutable slices split at an index.
- Listing 20-4 safely uses `split_at_mut(3)` on `[1, 2, 3, 4, 5, 6]`.
- Listing 20-4 returns `[1, 2, 3]` and `[4, 5, 6]`.
- Listing 20-5 attempts to implement `split_at_mut` using only safe Rust.
- Listing 20-5 asserts `mid <= len` before slicing.
- Listing 20-5 fails with E0499 because the borrow checker sees two mutable borrows from the same slice.
- The two mutable subslices are non-overlapping, but safe Rust's borrow checker cannot prove that from the slicing expression.
- When the programmer knows code is okay but Rust cannot prove it, unsafe code can be appropriate.
- Listing 20-6 implements `split_at_mut` with `values.as_mut_ptr()`, `slice::from_raw_parts_mut`, and `ptr.add(mid)`.
- `as_mut_ptr` returns a raw `*mut i32` pointer for a mutable `i32` slice.
- `slice::from_raw_parts_mut` takes a raw pointer and a length and creates a mutable slice.
- `ptr.add(mid)` gets a raw pointer starting at the split index.
- `slice::from_raw_parts_mut` is unsafe because it must trust that the pointer is valid.
- Raw pointer `add` is unsafe because it must trust that the offset location is valid.
- Listing 20-6 keeps `assert!(mid <= len)` so the computed pointers stay within the original slice.
- Listing 20-6 is a safe abstraction because the public function is safe and the internal unsafe code creates only valid non-overlapping slices.
- Listing 20-7 shows `slice::from_raw_parts_mut` used unsafely with an arbitrary memory address.
- Listing 20-7 creates a slice 10,000 items long from `0x01234usize as *mut i32`.
- Listing 20-7 is undefined behavior when used as a valid slice because the program does not own that memory and cannot guarantee valid `i32` values.
- Rust uses `extern` for foreign function interfaces.
- FFI lets one programming language define functions that another language can call.
- `unsafe extern "C"` declares external functions using the C ABI.
- Functions declared inside `unsafe extern` blocks are generally unsafe to call from Rust.
- `extern` blocks must be marked `unsafe`.
- Other languages do not enforce Rust's rules and guarantees, so the programmer must ensure FFI safety.
- The `"C"` ABI defines how to call a function at the assembly level using the common C ABI.
- Listing 20-8 declares C's `abs(input: i32) -> i32` in an `unsafe extern "C"` block.
- Listing 20-8 calls `abs(-3)` inside an `unsafe` block.
- Every item declared inside an `unsafe extern` block is implicitly unsafe by default.
- Some FFI functions are safe to call.
- C `abs` has no memory safety considerations and can be called with any `i32`.
- Listing 20-9 marks `safe fn abs(input: i32) -> i32` inside an `unsafe extern "C"` block.
- Marking an extern function `safe` allows calling it without an `unsafe` block.
- Marking a function `safe` is a promise to Rust; it does not inherently make the function safe.
- It remains the programmer's responsibility to keep the `safe` promise.
- Rust functions can be exported for other languages to call.
- To export a Rust function for C, put `extern "C"` before `fn` on the function.
- `#[unsafe(no_mangle)]` tells the compiler not to mangle the exported function name.
- Name mangling changes a function name into a less human-readable symbol with extra compiler information.
- Different language compilers mangle names differently.
- Disabling mangling makes a Rust function nameable by other languages.
- `#[unsafe(no_mangle)]` is unsafe because exported unmangled names can collide across libraries.
- The programmer must ensure the exported unmangled name is safe.
- Exporting with `pub extern "C" fn` requires `unsafe` only on the `#[unsafe(no_mangle)]` attribute in the book's example.
- Rust global variables are called static variables.
- Listing 20-10 declares `static HELLO_WORLD: &str = "Hello, world!";`.
- Static variable names conventionally use `SCREAMING_SNAKE_CASE`.
- Static variables can only store references with the `'static` lifetime.
- The compiler can infer a static variable reference lifetime, so explicit annotation is not required in Listing 20-10.
- Accessing an immutable static variable is safe.
- Immutable static variables have a fixed address in memory.
- Constants are allowed to duplicate their data whenever used.
- Static variables can be mutable.
- Accessing and modifying mutable static variables is unsafe.
- Listing 20-11 declares `static mut COUNTER: u32 = 0;`.
- Listing 20-11 wraps `COUNTER += inc` in an unsafe block.
- Listing 20-11 marks `add_to_count` as unsafe because callers must ensure single-threaded access.
- Listing 20-11's `SAFETY` documentation states that calling from more than one thread at a time is undefined behavior.
- Listing 20-11's `main` uses an unsafe block because it calls `add_to_count` and reads `COUNTER`.
- Listing 20-11 reads `COUNTER` with `*(&raw const COUNTER)` to avoid creating a reference to a mutable static.
- Listing 20-11 prints `COUNTER: 3` in the single-threaded example.
- Multiple threads accessing a mutable static likely cause data races and undefined behavior.
- Unsafe functions should have a `SAFETY` comment explaining what callers must do.
- Unsafe operations should have a `SAFETY` comment explaining how safety rules are upheld.
- The compiler denies attempts to create references to mutable static variables by default through a lint.
- Code can opt out with `#[allow(static_mut_refs)]`, but the source recommends raw pointers from raw borrow operators.
- References to mutable statics can be created invisibly, such as through `println!`.
- Raw-pointer access makes mutable-static safety requirements more obvious.
- Where possible, use CH-16 concurrency techniques and thread-safe smart pointers instead of mutable statics.
- A trait is unsafe when at least one method has an invariant the compiler cannot verify.
- Declare an unsafe trait with `unsafe trait`.
- Implement an unsafe trait with `unsafe impl`.
- Listing 20-12 defines `unsafe trait Foo` and `unsafe impl Foo for i32`.
- `unsafe impl` promises to uphold invariants the compiler cannot verify.
- `Send` and `Sync` are marker traits that can require unsafe implementation for custom types containing non-`Send` or non-`Sync` parts such as raw pointers.
- If a type contains raw pointers and the programmer wants to mark it `Send` or `Sync`, Rust cannot verify the guarantees, so the programmer must use `unsafe` and check manually.
- A union is similar to a struct, but only one declared field is used in a particular instance at one time.
- Unions are mainly used to interface with C unions.
- Accessing union fields is unsafe because Rust cannot guarantee the type of data currently stored in the union.
- Miri is an official Rust tool for detecting undefined behavior in unsafe code.
- The borrow checker is a static compile-time tool.
- Miri is a dynamic runtime tool.
- Miri runs a program or test suite and detects violations of rules it understands about how Rust should work.
- Miri requires a nightly build of Rust.
- Install Miri with `rustup +nightly component add miri`.
- Run Miri with `cargo +nightly miri run` or `cargo +nightly miri test`.

- If Miri catches a problem, there is a bug.
- If Miri does not catch a bug, that does not prove there is no problem.
- Miri only catches problems in code that actually runs.
- Miri should be used with good testing techniques.
- Miri does not cover every possible way code can be unsound.
- Using unsafe is not wrong or frowned upon when there is a real reason.
- Unsafe code is trickier because the compiler cannot help uphold memory safety for the unsafe operations.
- Explicit `unsafe` annotations make memory-safety problem sources easier to track down.
- The source points to the Rustonomicon for deeper unsafe Rust guidance.

#### Failure Modes

- Treating `unsafe` as "turn off all checks" is wrong; borrow checking and other safety checks still apply.
- Letting unsafe blocks grow large makes memory-safety bugs harder to localize.
- Exposing unsafe requirements to every caller instead of wrapping them in safe abstractions spreads risk.
- Dereferencing arbitrary or null raw pointers can cause undefined behavior.
- Assuming raw pointer creation proves validity is wrong; creation is safe, but validity matters when dereferencing or building references/slices.
- Creating mutable and immutable raw pointers to the same memory and mutating through them can create data races.
- Calling an unsafe function without documenting or upholding its contract misuses the unsafe function boundary.
- Assuming an `unsafe fn` body is implicitly allowed to perform unsafe operations without inner unsafe blocks misses the current required style and compiler warnings.
- Implementing `split_at_mut` with two safe mutable slices over the same source fails because the borrow checker cannot prove non-overlap.
- Calling `slice::from_raw_parts_mut` with an arbitrary pointer and length can create undefined behavior.
- Treating `safe fn` inside `unsafe extern` as magically safe is wrong; it is an assertion the programmer must justify.
- Exporting functions with `#[unsafe(no_mangle)]` without checking symbol collisions can be unsafe across libraries.
- Reading or writing mutable statics from multiple threads can cause undefined behavior through data races.
- Creating references to mutable statics is denied by default; use raw borrow operators or explicitly opt out only with justification.
- Implementing unsafe traits without manually checking invariants can make otherwise safe-looking code unsound.
- Assuming Miri finds all unsafe-code bugs is wrong because it is dynamic and incomplete.

#### Comparisons

- Safe Rust vs unsafe Rust: safe Rust enforces memory safety at compile time; unsafe Rust allows five unchecked capabilities while keeping other checks.
- Unsafe block vs unsafe function: an unsafe block is where unsafe operations are performed; an unsafe function marks a call contract the caller must uphold.
- Raw pointer creation vs raw pointer dereference: creation is safe; dereference is unsafe because it accesses possibly invalid memory.
- `*const T` vs `*mut T`: `*const T` is an immutable raw pointer; `*mut T` is a mutable raw pointer.
- References vs raw pointers: references must be valid, non-null, borrow-checked, and cleaned up by normal ownership; raw pointers may be invalid/null/aliasing and do not clean up.
- Unsafe implementation details vs safe abstraction: unsafe internals can be hidden behind a safe API when the implementation upholds the API's invariants.
- Listing 20-5 vs Listing 20-6: safe slicing fails because Rust cannot prove non-overlap; raw-pointer construction succeeds when bounds and non-overlap are manually upheld.
- Unsafe FFI item vs `safe fn` FFI item: normal extern items in `unsafe extern` are implicitly unsafe; a `safe fn` item can be called safely when the programmer promises it is sound.
- Immutable static vs constant: immutable static has a fixed memory address; constants can duplicate data at use sites.
- `_` unsafe confidence vs Miri confidence: an unsafe block is the programmer's assertion; Miri is runtime evidence for executed paths but not a complete proof.

#### Project / Architecture Decisions

- Prefer safe Rust; use unsafe only for a concrete capability safe Rust cannot express.
- Keep unsafe blocks small and focused.
- Document unsafe function contracts and unsafe operation justifications with `SAFETY` comments.
- Build safe abstractions over unsafe internals when callers can use the API without upholding additional contracts.
- Use raw borrow operators when creating raw pointers from existing values.
- Avoid arbitrary address casts unless interfacing with real low-level requirements and the validity contract is explicit.
- Validate indices and lengths before constructing slices from raw parts.
- Prefer thread-safe concurrency primitives from CH-16 over mutable statics where possible.
- Mark individual FFI functions `safe` only when their safety contract has been audited and can be upheld for all safe callers.
- Use `#[unsafe(no_mangle)]` only when exporting a symbol intentionally and checking for naming collisions.
- Use Miri with tests to increase confidence in unsafe code, but do not treat a clean Miri run as proof of soundness.
- Preserve later CH-20 extraction coverage for advanced traits, advanced types, advanced functions and closures, and macros.

#### Concepts

- Advanced type features in this section include more uses of the newtype pattern, type aliases, the never type, dynamically sized types, and `Sized`.
- The newtype pattern creates a wrapper type, usually as a tuple struct with one field.
- Newtypes can statically prevent values from being confused when the wrapped representation is the same.
- `Millimeters(u32)` and `Meters(u32)` are distinct types even though each wraps a `u32`.
- A function parameter typed as `Millimeters` cannot be called with `Meters`.
- A function parameter typed as `Millimeters` also cannot be called with a plain `u32`.
- Newtypes are useful for unit-of-measure boundaries.
- Newtypes can hide implementation details while exposing a different public API.
- A `People` newtype wrapping `HashMap<i32, String>` could expose methods that add names while hiding numeric IDs.
- Newtypes provide lightweight encapsulation.
- Type aliases give an existing type another name.
- Type aliases use the `type` keyword.
- A type alias does not create a separate type.
- `type Kilometers = i32;` makes `Kilometers` a synonym for `i32`.
- A `Kilometers` value can be added to an `i32` value because they are the same underlying type.
- A function expecting `i32` can accept a value typed as `Kilometers`.
- Type aliases do not provide the type-checking benefits of the newtype pattern.
- Type aliases mainly reduce repetition and communicate intent.
- `Box<dyn Fn() + Send + 'static>` is an example of a long closure trait object type repeated in signatures.
- `type Thunk = Box<dyn Fn() + Send + 'static>;` gives that repeated type a meaningful shorter name.
- In the source, a thunk is code to be evaluated later, making `Thunk` a meaningful alias for a stored closure.
- Type aliases are commonly used with `Result<T, E>`.
- Many `std::io` operations return `Result<T, std::io::Error>`.
- `std::io::Result<T>` is an alias for `Result<T, std::io::Error>`.
- The `std::io::Result<T>` alias makes I/O APIs easier to write and presents a consistent interface.
- A result alias is still a normal `Result<T, E>` value, so `Result` methods and the `?` operator still work.
- The never type is written `!`.
- `!` is also called the empty type because it has no values.
- The never type is used as the return type for functions that never return.
- Functions returning `!` are called diverging functions.
- A function such as `fn bar() -> ! { panic!(); }` diverges instead of producing a return value.
- Values of `!` cannot be created.
- `continue` has type `!`.
- In the guessing-game parse `match`, the `Ok(num)` arm produces `u32` and the `Err(_) => continue` arm has type `!`.
- Because `!` can be coerced into any other type, the whole parse `match` can have type `u32`.
- `continue` does not produce a value; it moves control back to the top of the loop.
- `panic!` has type `!`.
- `Option::unwrap` can return `T` in the `Some` arm and call `panic!` in the `None` arm because `panic!` never returns.
- An infinite `loop` expression has type `!` if it never reaches a `break`.
- A loop with a possible `break` does not have type `!`.
- Dynamically sized types (DSTs), also called unsized types, have sizes known only at runtime.
- Rust normally needs to know type sizes at compile time to allocate values.
- `str`, not `&str`, is a dynamically sized type.
- A bare `str` variable cannot be created directly because string contents can have different byte lengths.
- All values of one statically known type must have the same size.
- `&str` is usable because a string slice reference stores a start pointer and a length.
- `&str` has a compile-time-known size: two `usize` values.
- DST pointers include extra metadata that stores dynamic information such as length.
- The golden rule for DSTs in this section is to always put DST values behind a pointer.
- `Box<str>` and `Rc<str>` are examples of pointer types that can hold DSTs.
- Traits are dynamically sized types when used as trait objects.
- Trait objects must be placed behind pointers such as `&dyn Trait`, `Box<dyn Trait>`, or `Rc<dyn Trait>`.
- `Sized` is a trait indicating whether a type's size is known at compile time.
- Rust automatically implements `Sized` for types whose size is known at compile time.
- Generic functions implicitly get a `Sized` bound.
- `fn generic<T>(t: T) {}` is treated as `fn generic<T: Sized>(t: T) {}`.
- `T: ?Sized` relaxes the implicit `Sized` bound.
- `?Sized` means `T` may or may not be `Sized`.
- `?Trait` syntax in this relaxation form is available only for `Sized`.
- A maybe-unsized generic parameter must be used behind a pointer, so the example changes from `t: T` to `t: &T`.

#### Comparisons

- Newtype vs type alias: a newtype creates a distinct wrapper type; a type alias creates only another name for the same type.
- Newtype type safety vs type alias ergonomics: newtypes prevent accidental mixing; aliases reduce repetition and communicate intent.

- `Result<T, std::io::Error>` vs `std::io::Result<T>`: the alias fixes the error type and shortens signatures.
- Ordinary function return type vs never type: ordinary returns produce values; `!` marks code paths that never produce a value.
- `str` vs `&str`: `str` is a DST with runtime-known length; `&str` is a sized pointer-plus-length reference.
- Sized generic vs maybe-unsized generic: default `T` means `T: Sized`; `T: ?Sized` admits sized and unsized types behind a pointer.

- Use standard aliases such as `std::io::Result<T>` when they match the API's fixed error type.
- Model non-returning control paths with `!` when a function truly diverges.
- Store and pass DSTs through pointer types such as references, boxes, `Rc`, or other smart pointers.
- When accepting trait objects, choose an explicit pointer form such as `&dyn Trait`, `Box<dyn Trait>`, or `Rc<dyn Trait>` based on ownership needs.
- Relax `Sized` with `?Sized` only when the API intentionally accepts unsized values through indirection.

#### Concepts

#### Failure Modes

- Treating macros as ordinary runtime function calls misses expansion timing and compile-time code generation.
- Assuming macros and functions have the same parameter rules misses macros' variable-argument flexibility.
- Using a macro when a function would work can make code harder to read and maintain.
- Calling a macro before it is defined or imported in a file fails in a way function calls do not.
- Confusing macro pattern syntax with Chapter 19 value-pattern syntax leads to incorrect `macro_rules!` reasoning.
- Forgetting `$` in macro variables confuses macro variables with ordinary Rust variables.
- Forgetting that `$x:expr` matches Rust expressions, not evaluated values, misses what declarative macros operate on.
- Forgetting `#[macro_export]` prevents the simplified `vec!` macro from being brought into scope from its crate.
- Assuming Listing 20-35 is the full standard-library `vec!` macro misses the omitted pre-allocation optimization.
- Trying to put a procedural macro in an ordinary library crate misses the required special proc-macro crate type.
- Forgetting `[lib] proc-macro = true` prevents a crate from defining procedural macros.
- Expecting `proc_macro_derive` to return `Result` conflicts with the API requirement that it return `TokenStream`.
- Using `unwrap` in a production procedural macro can produce vague errors; the book recommends more specific `panic!` or `expect` messages.
- Assuming Rust can reflect on type names at runtime misses why the `HelloMacro` derive macro is needed.
- Forgetting to add both `hello_macro` and `hello_macro_derive` dependencies in the book's structure prevents using both the trait and derive macro.
- Confusing `quote!` output with the final required type misses the need to convert the generated value with `.into()` to `TokenStream`.
- Confusing `stringify!` with `format!` or `println!` misses that `stringify!` does not evaluate the expression.
- Applying a custom derive macro to arbitrary items misunderstands derive's restriction to structs and enums.
- Treating attribute-like macros as the same as derive misses their two-token-stream signature and broader item applicability.
- Trying to express complex SQL parsing with `macro_rules!` ignores why the book uses `sql!` as a function-like procedural macro example.

#### Comparisons

- Macro vs function: macros write code that expands before semantic interpretation; functions are called at runtime.
- Macro parameter flexibility vs function signatures: macros can accept variable numbers of arguments; functions declare fixed parameter counts and types.
- Macro compile-time effects vs function runtime calls: macros can generate trait implementations; functions cannot add trait impls at runtime.
- Macro maintainability vs function maintainability: macro definitions are more complex and usually harder to read.
- Macro order vs function order: macros must be defined or imported before call; functions can be defined later in the file.
- Declarative macro vs `match`: both are pattern-oriented, but declarative macros match source-code structure while `match` matches values.
- Declarative macro vs procedural macro: declarative macros use match-like patterns and replacement; procedural macros take code tokens, transform them with Rust code, and return code tokens.
- `macro_rules!` macro vs function-like procedural macro: both can look like macro calls and be flexible, but `macro_rules!` uses pattern syntax while function-like procedural macros manipulate `TokenStream` with Rust code.
- Custom derive vs attribute-like macro: derive adds code through `#[derive(...)]` for structs and enums; attribute-like macros define custom attributes usable on more item kinds.
- Attribute-like macro vs function-like macro: attribute-like macros receive attribute tokens plus item tokens; function-like macros receive tokens inside a function-call-looking invocation.
- `proc_macro` vs `syn` vs `quote`: `proc_macro` is Rust's compiler API and token stream type; `syn` parses Rust tokens into syntax data; `quote` turns syntax data back into Rust code.
- `quote!` vs `stringify!`: `quote!` builds generated Rust code; `stringify!` turns tokens into a string literal.
- Manual `HelloMacro` impl vs derive macro: the manual impl is repeated per type; the derive macro generates the impl for the annotated type.
- Book crate structure vs re-export structure: separate trait and derive crates require users to depend on both; re-exporting could simplify use but would couple the trait crate to derive functionality.

#### Project / Architecture Decisions

- Prefer ordinary functions when fixed parameters and runtime behavior are enough.
- Use macros when compile-time code generation, variable argument counts, or syntax-level processing are required.
- Treat macro definitions as higher-maintenance code and keep their purpose clear.
- Use `macro_rules!` for match-like transformations over Rust source structure.
- Use procedural macros when the macro needs to parse and transform token streams with Rust code.
- Put procedural macro definitions in a dedicated `proc-macro` crate.
- Use the `foo_derive` naming convention for custom derive crates associated with a crate named `foo`.
- Keep trait crates usable without derive functionality when that separation matters to users.
- Consider re-exporting derive macros from the main crate if ergonomic single-crate use is more important than separation.
- Use `syn` and `quote` rather than hand-writing a full Rust parser for procedural macro input and output.
- Split procedural macro code into an outer parsing function and an inner transformation function.
- Provide specific procedural macro error messages in production rather than relying on bare `unwrap`.
- Use custom derive macros for repeatable trait implementations on structs and enums.
- Use attribute-like macros for custom annotations on items such as framework route handlers.
- Use function-like procedural macros for call-like syntax that needs token parsing more complex than `macro_rules!`, such as SQL validation.
