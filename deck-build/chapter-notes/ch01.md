### Learning Objectives

- Learner can explain what `rustup` manages: Rust versions and associated tools.
- Learner can install Rust on Linux/macOS using the book's terminal command and recognize the success message.
- Learner can identify when a linker or C compiler is needed and why Rust packages may depend on C code.

- Learner can verify a Rust installation with `rustc --version` and interpret the expected version/commit/date output shape.
- Learner can choose the right PATH inspection command for Windows CMD, PowerShell, or Linux/macOS.
- Learner can update Rust with `rustup update` and uninstall Rust plus `rustup` with `rustup self uninstall`.
- Learner can open local Rust documentation with `rustup doc` and use standard library API docs for unfamiliar types or functions.
- Learner can prepare for offline book examples by caching `rand@0.8.5` and `trpl@0.2.0`, then using `--offline` with later Cargo commands.

### Card Content Candidates

#### Concepts

- `rustup`: command line tool for managing Rust versions and associated tools; used here to install the latest stable Rust compiler.
- Internet requirement: the normal `rustup` installation downloads Rust and needs an internet connection.
- Stability guarantee: newer stable Rust versions should continue compiling book examples that are intended to compile, though error/warning text may differ.
- Command notation: terminal commands shown in the book start with `$`; the `$` prompt is not typed. Output lines generally do not start with `$`. PowerShell-specific command examples use `>`.
- Linux/macOS installation path: run the `curl ... | sh` installer command in a terminal.
- Install success signal: the installer prints `Rust is installed now. Great!`.
- Linker: program Rust uses to join compiled outputs into one file.
- C compiler need: linker errors may mean a C compiler is missing; common Rust packages can depend on C code and need a C compiler.
- macOS C compiler setup: `xcode-select --install`.
- Linux C compiler setup: install GCC or Clang according to distribution docs; Ubuntu example is `build-essential`.
- Windows installation path: use the Rust tools install page; Visual Studio supplies the linker and native libraries needed to compile programs.
- Shell compatibility: the rest of the book uses commands that work in both `cmd.exe` and PowerShell unless differences are called out.
- Installation verification: `rustc --version` should print version number, commit hash, and commit date.
- PATH troubleshooting: if `rustc --version` does not show the expected information, check whether Rust is in the system PATH.
- Updating: `rustup update` updates Rust once it is installed through `rustup`.
- Uninstalling: `rustup self uninstall` removes Rust and `rustup`.
- Local docs: Rust installation includes local documentation; `rustup doc` opens it in a browser.
- API documentation use case: when unsure about a standard library type or function, consult the API docs.
- Editor assumption: the book does not assume a specific text editor or IDE; most editors work, many have Rust support.
- Offline dependency caching: `cargo new get-dependencies`, `cd get-dependencies`, and `cargo add rand@0.8.5 trpl@0.2.0` cache dependencies used in later examples.
- Offline Cargo usage: after caching dependencies, use `--offline` with Cargo commands later in the book to use cached versions instead of the network.
- Temporary offline project: the `get-dependencies` folder does not need to be kept after dependencies are cached.

### Learning Objectives

### Card Content Candidates

#### Concepts

- Tooling assumption: the book assumes basic command-line familiarity, but Rust does not require a particular editor, IDE, or code location.
- IDE support: many IDEs support Rust; the Rust team focuses IDE support through `rust-analyzer`.
- Project organization suggestion: keep exercises and book projects under a `projects` directory in the home directory.
- Rust source extension: Rust files end with `.rs`.
- Rust filename convention: for multiword filenames, use underscores, such as `hello_world.rs`, instead of `helloworld.rs`.
- Listing 1-1: first complete Rust program lives in `main.rs` and prints `Hello, world!`.
- `main` function: special function that is always the first code to run in every executable Rust program.
- `fn main()`: declares a function named `main` with no parameters and no return value.
- Function body braces: Rust requires curly brackets around all function bodies.
- Style convention: put the opening curly brace on the same line as the function declaration with one space before it.
- `rustfmt`: automatic formatter included with the standard Rust distribution; useful for keeping standard style.
- `println!`: macro that prints text to the screen.
- Macro marker: the `!` in `println!` means this is a macro call, not a normal function call; macros do not always follow the same rules as functions.
- String argument: `"Hello, world!"` is passed to `println!` and printed to the terminal.
- Semicolon: the `;` ends the expression and prepares for the next expression; most lines of Rust code end with semicolons.
- Direct compilation: before running this program, compile it with `rustc main.rs`.
- Successful compile output: Rust produces a binary executable.
- Executable names: non-Windows platforms produce `main`; Windows produces `main.exe` and may also produce `main.pdb` debug information.
- Run command: use `./main` on Linux/macOS and `.\main` on Windows.
- Troubleshooting boundary: if `Hello, world!` does not print, refer back to Installation troubleshooting rather than changing the source first.
- Compilation vs execution: Rust compilation and running are separate steps when using `rustc` directly.
- Ahead-of-time compilation: Rust can compile a program into an executable that someone else can run without Rust installed.
- Dynamic language comparison: Ruby/Python/JavaScript source files require their respective runtime implementations; Rust executables can be distributed after compilation.
- Scaling boundary: direct `rustc` is fine for simple programs, but Cargo is introduced next for managing options and sharing code in real-world projects.

### Learning Objectives

- Learner can state Cargo's two primary roles: Rust build system and package manager.
- Learner can explain what Cargo manages beyond compiling local code: downloading dependencies and building those dependencies.
- Learner can verify Cargo installation with `cargo --version`.
- Learner can create a new Cargo project with `cargo new hello_cargo` and enter it with `cd hello_cargo`.
- Learner can describe the files Cargo generates: `Cargo.toml`, `src/main.rs`, and, when appropriate, Git metadata plus `.gitignore`.
- Learner can explain the key sections and fields in the generated `Cargo.toml`: `[package]`, `name`, `version`, `edition = "2024"`, and `[dependencies]`.
- Learner can explain Cargo's project layout convention: source code in `src`, top-level files for README, license, configuration, and other non-code material.
- Learner can convert a non-Cargo project by moving source into `src`, creating `Cargo.toml`, or using `cargo init`.
- Learner can distinguish `cargo build`, direct executable execution, `cargo run`, and `cargo check`.
- Learner can explain why `cargo check` is faster than `cargo build`: it checks compilation without producing an executable.
- Learner can explain where Cargo stores debug and release executables and why `--release` takes longer but produces faster-running code.

### Card Content Candidates

#### Concepts

- Cargo role: Rust's build system and package manager.
- Cargo-managed tasks: building your code, downloading dependency libraries, and building those dependencies.
- Dependency definition: libraries your code depends on are dependencies.
- Simple program boundary: a simple `Hello, world!` program has no dependencies, so Cargo would only build code for that project.
- Cargo adoption: most Rust projects use Cargo, and the rest of the book assumes Cargo.
- Cargo installation check: official Rust installers include Cargo; other installation methods may require checking/installing Cargo separately.
- `cargo new hello_cargo`: creates a new directory and Cargo project named `hello_cargo`.
- Generated project contents: `Cargo.toml` plus `src/main.rs`; Cargo may also initialize Git metadata and `.gitignore`.
- Git behavior: Git files are not generated if `cargo new` is run inside an existing Git repository; `cargo new --vcs=git` can override this behavior.
- Version-control option: `--vcs` controls which VCS Cargo uses, and `cargo new --help` lists available options.
- `Cargo.toml`: Cargo configuration file written in TOML.
- TOML meaning: Tom's Obvious, Minimal Language.
- `[package]`: section heading for package configuration.
- Package metadata: generated `Cargo.toml` includes `name = "hello_cargo"`, `version = "0.1.0"`, and `edition = "2024"`.
- Rust edition key: `edition` tells Cargo which Rust edition to use; Appendix E explains editions.
- `[dependencies]`: section for listing package dependencies.
- Crate terminology: in Rust, packages of code are called crates.
- `src/main.rs`: Cargo-generated Rust source file containing a `Hello, world!` program like Listing 1-1.
- Cargo layout difference from direct `rustc`: Cargo places code in `src` and keeps `Cargo.toml` in the top project directory.
- Source-location convention: Cargo expects source files inside `src`.
- Top-level directory convention: README files, license information, configuration files, and non-code project material live at the top level.
- `cargo init`: can create a `Cargo.toml` for an existing project when converting it to Cargo.
- `cargo build`: compiles the project and puts the debug executable in `target/debug/hello_cargo` or `target\debug\hello_cargo.exe` on Windows.
- Debug build default: Cargo's default build is a debug build and stores binaries under `target/debug`.
- `Cargo.lock`: created by first `cargo build`; tracks exact dependency versions; managed by Cargo and not edited manually.
- `cargo run`: compiles if needed and runs the resulting executable in one command.
- Incremental behavior: if source files have not changed, `cargo run` skips rebuilding and just runs the binary.
- Rebuild behavior: if source code changes, `cargo run` rebuilds before running.
- `cargo check`: quickly checks whether code compiles without producing an executable.
- `cargo check` use case: run periodically while writing code to confirm the project still compiles; run `cargo build` when ready to use an executable.
- OS-independent Cargo commands: after this point, the book no longer gives separate Linux/macOS vs Windows instructions for Cargo commands because they are the same across OSes.
- Release build: `cargo build --release` compiles with optimizations and puts the executable in `target/release`.
- Optimization tradeoff: release builds run faster but take longer to compile.
- Build profiles: development profile rebuilds quickly and often; release profile is for final optimized programs given to users.
- Benchmarking rule: benchmark with the `target/release` executable after `cargo build --release`.
- Cargo convention value: direct `rustc` has little advantage for simple projects, but Cargo becomes valuable for multiple files or dependencies.
- Existing-project workflow: clone with Git, change into the project directory, and run `cargo build`.

#### Prediction / Diagnostic Examples

- Given `cargo --version` prints a version number, conclude Cargo is installed.
- Given `cargo --version` returns `command not found`, consult the installation method's documentation to install Cargo separately.
- Given a new Cargo project, predict that source code belongs in `src/main.rs`, not directly in the project root.
- Given generated `Cargo.toml`, identify `edition = "2024"` as the key selecting the Rust edition for the package.
- Given a project with no dependencies, predict that `[dependencies]` can be empty.
- Given `cargo build` succeeds, predict the default debug executable path rather than expecting the binary in the current directory.
- Given `cargo run` after no source changes, predict Cargo will skip recompilation and run the existing binary.
- Given `cargo run` after source changes, predict Cargo will rebuild before running.
- Given a developer repeatedly checking code while editing, choose `cargo check` over `cargo build` because it skips producing an executable.
- Given benchmarking or final distribution, choose `cargo build --release` and benchmark the `target/release` executable.
- Given a project grows to multiple files or dependencies, choose Cargo conventions over direct `rustc`.

#### Failure Modes

- Assuming Cargo only compiles local code; it also downloads and builds dependencies.
- Expecting `cargo build` to place the binary in the current directory; Cargo stores debug builds in `target/debug`.
- Editing `Cargo.lock` manually; Cargo manages its contents.
- Expecting `cargo run` always to recompile; it skips rebuilding when files have not changed.
- Using `cargo check` when an executable is needed; `cargo check` validates compilation but does not produce a binary.
- Benchmarking debug builds; optimized release builds live in `target/release`.
- Putting Rust source files at the top project level in a Cargo project; Cargo expects source under `src`.

#### Comparisons

- Build system vs package manager: Cargo handles both compiling project code and managing/downloading dependency libraries.
- Direct `rustc` project vs Cargo project: direct project has source in current directory; Cargo project has `src/main.rs` and top-level `Cargo.toml`.
- Project source vs top-level metadata: source belongs in `src`; README/license/configuration/non-code files belong at the top level.
- `cargo new` vs `cargo init`: create a new project directory vs initialize Cargo metadata for an existing project.
- `cargo build` vs `cargo run`: build only vs build-if-needed and run in one command.
- `cargo build` vs `cargo check`: build produces an executable; check only verifies compilation and is often faster.
- Debug build vs release build: debug is default, faster to compile, stored in `target/debug`; release is optimized, slower to compile, stored in `target/release`.
- `target/debug/hello_cargo` vs `target\debug\hello_cargo.exe`: Unix-like path vs Windows path for the same debug executable.
- Empty `[dependencies]` in Chapter 1 vs adding crates in Chapter 2: this project has no dependencies, but the section prepares for later dependency cards.
