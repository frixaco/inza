### Card Content Candidates

#### Concepts

- There is no consensus in the programming community about which features a language must have to count as object oriented.
- Rust is influenced by many programming paradigms.
- Rust is influenced by OOP.
- Rust is also influenced by functional programming, as shown in CH-13.
- OOP languages commonly share objects, encapsulation, and inheritance.
- The Gang of Four book is a catalog of object-oriented design patterns.
- The Gang of Four defines object-oriented programs as programs made up of objects.
- In the Gang of Four definition, an object packages data and procedures operating on that data.
- The procedures that operate on object data are typically called methods or operations.
- Under the Gang of Four object definition, Rust is object oriented.
- Rust structs and enums have data.
- Rust `impl` blocks provide methods on structs and enums.
- Rust structs and enums with methods are not called objects in Rust terminology.
- Even without being called objects, structs and enums with methods provide the same functionality as the Gang of Four definition of objects.
- Encapsulation means an object's implementation details are not accessible to code using that object.
- With encapsulation, code using an object interacts through the object's public API.
- With encapsulation, external code should not reach into an object's internals to change data or behavior directly.
- Encapsulation lets a programmer change or refactor internals without changing code that uses the object.
- Rust controls encapsulation through module privacy and the `pub` keyword.
- `pub` decides which modules, types, functions, and methods are public.
- By default, Rust items are private.
- Listing 18-1 defines `pub struct AveragedCollection`.
- `AveragedCollection` contains a `list: Vec<i32>` field.
- `AveragedCollection` contains an `average: f64` field.
- `AveragedCollection` caches the calculated average instead of computing it on demand every time.
- The `AveragedCollection` struct is public so other code can use the type.
- The `AveragedCollection` fields are private.
- Private fields are important because the cached average must stay synchronized with the list.
- Listing 18-2 implements public `add`, `remove`, and `average` methods.
- `add(&mut self, value: i32)` pushes the value into `self.list` and calls `self.update_average()`.
- `remove(&mut self) -> Option<i32>` pops from the list.
- When `remove` gets `Some(value)`, it updates the average and returns `Some(value)`.
- When `remove` gets `None`, it returns `None`.
- `average(&self) -> f64` returns the cached `average` value.
- `update_average(&mut self)` is private.
- `update_average` computes `let total: i32 = self.list.iter().sum();`.
- `update_average` sets `self.average = total as f64 / self.list.len() as f64;`.
- `add`, `remove`, and `average` are the only public ways to access or modify `AveragedCollection` data.
- External code cannot add or remove items from `list` directly.
- If external code could modify `list` directly, `average` could become out of sync.
- The `average` method allows external code to read the cached average without modifying it.
- Encapsulating `AveragedCollection` lets the internal data structure change later.
- The source example says `AveragedCollection` could use `HashSet<i32>` instead of `Vec<i32>` internally.
- If `add`, `remove`, and `average` signatures stay the same, external code does not need to change when internals change.
- If `list` were public, changing from `Vec<i32>` to `HashSet<i32>` could force external code changes because the two types have different add/remove methods.
- If encapsulation is required for OOP, Rust meets that requirement.
- Inheritance means an object inherits elements from another object's definition.
- Inheritance gives an object the parent object's data and behavior without redefining them.
- If inheritance is required for OOP, Rust is not object oriented under that definition.
- Rust has no built-in way to define a struct that inherits a parent struct's fields and method implementations without using a macro.
- Programmers reach for inheritance for two main reasons: code reuse and type-system polymorphism.
- For code reuse, inheritance lets behavior implemented for one type be reused by another type.
- Rust can support limited code reuse through default trait method implementations.
- A default method on a trait becomes available to any type implementing that trait.
- The source uses the CH-10 `Summary::summarize` default method as the example.
- A type implementing `Summary` can use the default `summarize` implementation without more code.
- A type can override a default trait method implementation.
- Default trait methods are similar to a parent class method inherited by a child class.
- Overriding a default trait method is similar to a child class overriding an inherited method.
- For type-system use, inheritance can let a child type be used where a parent type is expected.
- This type-system use is called polymorphism.
- Polymorphism means code can work with data of multiple types.
- Many people use polymorphism as a synonym for inheritance, but the source says polymorphism is more general.
- With inheritance, the interchangeable types are generally subclasses.
- Rust uses generics to abstract over possible types.
- Rust uses trait bounds to constrain what generic types must provide.
- Generics plus trait bounds are sometimes called bounded parametric polymorphism.
- Rust avoids inheritance as a deliberate tradeoff.
- Inheritance can share more code than necessary.
- Subclasses do not always need all characteristics of their parent class but inherit them anyway.
- Inheritance can make program design less flexible.
- Inheritance can allow methods to be called on subclasses where the methods do not make sense.
- Inheritance can cause errors when inherited methods do not apply to a subclass.
- Single inheritance restricts a subclass to one parent class.
- Single inheritance can further restrict design flexibility.
- Rust uses trait objects instead of inheritance to achieve polymorphism at runtime.

#### Syntax Forms

- Public struct with private fields:
  ```rust
  pub struct AveragedCollection {
      list: Vec<i32>,
      average: f64,
  }
  ```
- Public methods preserving a private invariant:
  ```rust
  impl AveragedCollection {
      pub fn add(&mut self, value: i32) {
          self.list.push(value);
          self.update_average();
      }

      pub fn remove(&mut self) -> Option<i32> {
          let result = self.list.pop();
          match result {
              Some(value) => {
                  self.update_average();
                  Some(value)
              }
              None => None,
          }
      }

      pub fn average(&self) -> f64 {
          self.average
      }

      fn update_average(&mut self) {
          let total: i32 = self.list.iter().sum();
          self.average = total as f64 / self.list.len() as f64;
      }
  }
  ```
- Cross-reference syntax concept, not repeated in this section: a trait can provide a default method implementation, as with the earlier `Summary::summarize` example.

- Choose the Rust mechanism for limited inherited-method-like code reuse: default trait method implementations.

#### Failure Modes

- Calling Rust structs/enums "objects" as standard Rust terminology can mislead; the source says they are not called objects even though they provide object-like functionality under one definition.

- Treating Rust default trait methods as full inheritance is too broad; the source says they support code reuse in a limited way.

#### Comparisons

- Gang of Four object vs Rust struct/enum with methods: both combine data with operations, but Rust does not call structs/enums objects.
- Public API vs implementation details: public methods expose intended behavior; private fields and private helper methods hide representation and invariants.
- `Vec<i32>` internals vs `HashSet<i32>` internals: encapsulation can allow swapping internal representation without changing callers if public signatures stay stable.
- Encapsulation required vs inheritance required definitions of OOP: Rust meets the encapsulation requirement but not the built-in inheritance requirement.
- Inheritance for code reuse vs default trait methods: inheritance reuses parent class methods; Rust traits can provide default method implementations that implementers can use or override.
- Inheritance for type-system substitution vs Rust polymorphism: inheritance uses parent/subclass relationships; Rust uses generics with trait bounds and trait objects.
- Polymorphism vs inheritance: polymorphism is code working with multiple types; inheritance is only one way some languages provide polymorphism.
- Bounded parametric polymorphism vs runtime polymorphism: generics with trait bounds abstract over types at compile time; trait objects provide runtime polymorphism.
- Inheritance vs Rust tradeoffs: inheritance can share too much and reduce flexibility; Rust avoids inheritance and uses trait objects for runtime polymorphism.

#### Project / Architecture Decisions

- Use public methods and private fields to preserve invariants such as cached derived data.
- Keep internal representation private when you may need to change data structures without changing callers.
- Use `pub` selectively to define a public API rather than exposing all implementation details.
- Use default trait method implementations when the goal is limited reusable behavior across implementers.
- Use generics and trait bounds when code should work with multiple types that satisfy compile-time constraints.
- Use trait objects when runtime polymorphism is needed without inheritance.
- Be cautious with inheritance-like designs because inherited behavior may not apply cleanly to every subtype.

### Card Content Candidates

#### Concepts

- A vector can store elements of only one type.
- A fixed enum such as CH-08's `SpreadsheetCell` is a good solution when the interchangeable item types are known at compile time.
- A fixed enum is less suitable when library users must be able to extend the set of valid types.
- The source's GUI example needs to store many values of different concrete types.
- The GUI example needs to call a `draw` method on each differently typed value.
- The GUI library does not need to know exactly what each concrete `draw` implementation will do.
- The GUI library only needs to know that each value has a `draw` method available.
- In an inheritance language, a GUI framework might define a `Component` superclass with a `draw` method.
- In an inheritance language, `Button`, `Image`, and `SelectBox` might inherit from `Component` and override `draw`.
- Rust does not have inheritance, so the GUI library needs another compatibility structure.
- Listing 18-3 defines `pub trait Draw { fn draw(&self); }`.
- A trait object points to an instance of a type implementing a specified trait.
- A trait object also points to a table used to look up trait methods on that type at runtime.
- Creating a trait object requires a pointer-like type.
- The source names a reference and `Box<T>` as examples of pointer-like types for trait objects.
- Trait object syntax uses a pointer-like type, the `dyn` keyword, and the relevant trait.
- `Box<dyn Draw>` is a trait object.
- The reason trait objects require pointers is deferred to CH-20 dynamically sized types and `Sized`.
- Trait objects can be used in place of a generic or concrete type.
- Rust type-checks at compile time that values used as a trait object implement the trait object's trait.
- Trait objects mean the library does not need to know all possible concrete types at compile time.
- Rust avoids calling structs and enums "objects" to distinguish Rust terminology from other languages.
- In Rust, struct/enum data and `impl` behavior are separated.
- In many other languages, data and behavior combined into one concept are called objects.
- Trait objects differ from objects in other languages because data cannot be added to a trait object.
- Trait objects are specifically useful for abstraction across common behavior.
- Listing 18-4 defines `pub struct Screen { pub components: Vec<Box<dyn Draw>>, }`.
- `components: Vec<Box<dyn Draw>>` stores boxed values of any type implementing `Draw`.
- Listing 18-5 defines `Screen::run`.
- `Screen::run` iterates over `self.components.iter()`.
- `Screen::run` calls `component.draw()` for each component.
- A generic type parameter can be substituted with only one concrete type at a time.
- Trait objects allow multiple concrete types to fill in for the trait object at runtime.
- Listing 18-6 shows `pub struct Screen<T: Draw> { pub components: Vec<T>, }`.
- Listing 18-6 implements `impl<T> Screen<T> where T: Draw`.
- The generic `Screen<T>` form restricts one `Screen` instance to all `Button` components or all `TextField` components.
- Homogeneous collections should prefer generics and trait bounds when heterogeneity is not needed.
- Generic definitions are monomorphized at compile time to use concrete types.
- The trait-object `Screen` can hold a `Box<Button>` and a `Box<TextField>` in one `components` vector.
- Listing 18-7 defines a `Button` type with `width`, `height`, and `label` fields.
- Listing 18-7 implements `Draw` for `Button`.
- Different drawable component types may have different fields.
- A `TextField` might have fields that a `Button` does not, such as `placeholder`.
- Each drawable component type implements `Draw` but can use different code in its `draw` method.
- A type such as `Button` can also have other methods that do not apply to all drawable types.

- Listing 18-8 implements `Draw` for `SelectBox`.

- The library did not know about `SelectBox` when it was written.
- `Screen` can still draw `SelectBox` because `SelectBox` implements `Draw`.
- Trait objects focus on the messages a value responds to rather than its concrete type.
- This message-focused behavior resembles duck typing in dynamically typed languages.
- `Screen::run` does not check whether a component is a `Button` or `SelectBox`.
- `Screen::run` just calls `draw`.
- `Box<dyn Draw>` specifies that `Screen` needs values that can receive the `draw` method call.
- Rust trait objects provide duck-typing-like flexibility with compile-time trait checking.
- Rust does not need runtime checks to see whether a trait-object value implements a method.
- Rust will not compile code if trait object values do not implement the required trait.
- Listing 18-10 attempts to use `String` as a `Screen` component.
- Listing 18-10 fails because `String` does not implement `Draw`.
- Listing 18-10 produces E0277: the trait bound `String: Draw` is not satisfied.

- The E0277 output says the error is required for the cast from `Box<String>` to `Box<dyn Draw>`.
- To fix Listing 18-10, pass a different type or implement `Draw` for `String`.
- Monomorphization generates nongeneric implementations for each concrete type used with a generic type parameter.
- Code produced by monomorphization uses static dispatch.
- Static dispatch means the compiler knows at compile time which method is being called.
- Dynamic dispatch means the compiler cannot tell at compile time which method is being called.
- In dynamic dispatch, emitted code determines which method to call at runtime.
- Trait objects require dynamic dispatch.
- With trait objects, the compiler does not know all concrete types that may be used.
- At runtime, Rust uses pointers inside the trait object to know which method to call.
- Dynamic dispatch lookup has a runtime cost that static dispatch does not have.
- Dynamic dispatch can prevent the compiler from inlining method code.
- Preventing inlining can prevent some optimizations.
- Rust has rules about where dynamic dispatch can and cannot be used.
- The source calls those rules dyn compatibility.
- Dyn compatibility rules are beyond this section's detailed scope and are linked to the Rust Reference.
- Trait objects trade runtime cost and some optimization limits for extensibility and heterogeneous collections.

      pub fn run(&self) {

  pub struct Screen<T: Draw> {

#### Comparisons

- Fixed enum vs trait object: an enum is good for a known closed set of variants; trait objects support an open set of implementer types.
- Inheritance `Component` superclass vs Rust `Draw` trait object: inheritance uses parent classes; Rust uses a trait requirement plus `dyn Trait`.
- Rust trait object vs object in many OOP languages: a trait object does not carry arbitrary added data; it abstracts over shared behavior.
- Trait object vs generic type parameter: a trait object can stand in for multiple concrete types at runtime; a generic type parameter represents one concrete type per instantiation.
- `Vec<Box<dyn Draw>>` vs `Vec<T>` where `T: Draw`: the first can hold mixed drawable types; the second is homogeneous for one `T`.
- Duck typing vs Rust trait objects: both focus on supported messages/methods; Rust checks the trait implementation at compile time instead of relying on runtime failure.
- Static dispatch vs dynamic dispatch: static dispatch knows the method at compile time after monomorphization; dynamic dispatch selects the method at runtime through trait-object pointers.
- Flexibility vs performance: trait objects add extensibility and heterogeneous collections but introduce runtime lookup cost and may block inlining.
- `Button` methods vs `Draw::draw`: component-specific methods can exist on concrete types, but `Screen` can only rely on the shared `Draw` behavior.

#### Comparisons

- Traditional state pattern vs type-state rewrite: the traditional pattern hides transitions inside `Post`; the type-state rewrite exposes transitions through type changes.
- Runtime state object vs compile-time state type: `Box<dyn State>` changes behavior at runtime; `DraftPost`/`PendingReviewPost`/`Post` make illegal operations unavailable at compile time.
- Empty content method vs absent content method: the traditional draft returns `""`; the type-state draft has no `content` method.
- Trait-object states vs enum states: trait-object states localize behavior by type; enum states require matching wherever behavior depends on state.
- State-pattern extensibility vs state coupling: adding behavior for a state can be localized, but adding an intermediate state may require changing neighboring transition code.
- Traditional OOP familiarity vs Rust strengths: the traditional pattern may feel familiar but misses compile-time invalid-state prevention.
- Encapsulated transitions vs compile-time guarantees: hiding transitions in `Post` simplifies caller shape; type-state shadowing makes transitions explicit and safer.
- Dynamic dispatch state behavior vs ownership-based transitions: the first approach uses trait objects; the second uses ownership of `self` to transform values into different concrete types.
- `Post::content` responsibility vs `State::content` responsibility: delegating content behavior to state centralizes state rules but mixes state and post responsibilities.

#### Project / Architecture Decisions

- Use the traditional state pattern when hiding state transitions from callers and localizing per-state behavior is the priority.
- Consider enum states when the state set is closed and matching logic stays small enough to remain clear.
- Consider type-state when invalid operations should be impossible at compile time.
- Use consuming transition methods when a state change should invalidate the old state value.
- Keep fields private so users cannot construct invalid workflow states directly.
- Be careful when using trait objects for state transitions because dyn compatibility can rule out some default method patterns.
- Consider macros if many `Post` methods repeat the same `Option::take` transition boilerplate.
- Prefer Rust type-system guarantees when they meaningfully prevent production bugs, such as displaying unpublished post content.
- Treat OOP patterns as available tools, not defaults; compare them with ownership- and type-driven Rust designs.
