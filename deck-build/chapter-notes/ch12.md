#### Concepts

- The first implementation task is making `minigrep` accept two command-line arguments.
- The two arguments are a file path and a string to search for.
- `cargo run -- searchstring example-filename.txt` passes `searchstring` and `example-filename.txt` to the program rather than to Cargo.
- Existing crates on crates.io can help parse command-line arguments.
- The book implements argument handling manually because the chapter is teaching the concept.
- `std::env::args` reads command-line arguments passed to the program.
- `std::env::args` returns an iterator over command-line argument values.
- An iterator produces a series of values.
- Calling `collect` on an iterator can turn it into a collection.
- In Listing 12-1, `collect` turns the command-line argument iterator into a vector.
- Listing 12-1 uses `Vec<String>` because `env::args` yields `String` values.
- `collect` can produce many collection types, so Rust often needs a type annotation to know which collection is desired.
- The code brings `std::env` into scope and then calls `env::args()`.
- Bringing the parent `std::env` module into scope is idiomatic when the desired function is nested under more than one module.
- Calling `env::args()` is less ambiguous than importing `std::env::args` and calling `args()`.
- `std::env::args` panics if any argument contains invalid Unicode.
- Programs that must accept invalid Unicode arguments should use `std::env::args_os`.
- `std::env::args_os` yields `OsString` values.
- The book uses `std::env::args` for simplicity because `OsString` values are platform-specific and more complex than `String` values.
- Running Listing 12-1 with no extra arguments still produces one argument value.
- The first argument value is the binary path/name, such as `target/debug/minigrep`.
- The argument list's first value matching the invoked program name is similar to C argument-list behavior.
- Having access to the program name can help with messages or alias-dependent behavior.
- CH-12 ignores `args[0]` and keeps only the query and file path.
- Listing 12-2 stores `&args[1]` in `query`.
- Listing 12-2 stores `&args[2]` in `file_path`.
- `query` is the string to search for.
- `file_path` is the path to the file to search in.
- Listing 12-2 temporarily prints the extracted arguments to prove they were saved correctly.
- Running Listing 12-2 with `test sample.txt` prints `Searching for test` and `In file sample.txt`.
- Listing 12-2 ignores erroneous situations such as the user providing no arguments.
- Missing-argument error handling is deferred to a later section.
- File-reading capability is the next implementation step after saving arguments.

#### Failure Modes

- Using `println!` for error messages in a command-line tool.
- Redirecting successful output to a file and accidentally hiding errors in that file.
- Assuming `>` redirects both `stdout` and `stderr` in the command shown by the source.
- Printing normal search results with `eprintln!`, which would send successful output to the error stream.
- Changing only one error path in `main` and leaving the other with `println!`.
- Moving error printing out of `main` again and losing the centralized error-handling benefit.
- Treating `process::exit(1)` as the stream-selection mechanism; stream selection is done by `eprintln!`, while `process::exit(1)` sets the error exit status.
- Forgetting that `output.txt` should contain successful search results when the program succeeds.

#### Comparisons

- `stdout` vs `stderr`: `stdout` is for successful/general output; `stderr` is for error messages.
- `println!` vs `eprintln!`: `println!` writes to standard output; `eprintln!` writes to standard error.
- Error redirected before fix vs after fix: before the fix, the parsing error goes to `output.txt`; after the fix, it stays onscreen.
- Error run vs successful run with redirection: the error run leaves `output.txt` empty and shows an error; the successful run fills `output.txt` with search results and shows no terminal output.
- Exit status vs output stream: `process::exit(1)` signals failure to the calling process; `eprintln!` chooses the error output stream.
- Centralized errors vs scattered errors: centralized error handling in `main` makes changing streams a two-call-site update.
