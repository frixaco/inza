## Section: Defining and Instantiating Structs

### Learning Objectives

- Learner can define a named-field struct with `struct`, field names, and field types.
- Learner can instantiate a struct with `key: value` pairs and explain that field order need not match the definition order.
- Learner can access and mutate struct fields with dot notation.
- Learner can explain that a whole struct instance must be mutable; Rust does not allow only selected fields to be marked mutable.
- Learner can return a struct instance as the final expression of a function.
- Learner can use field init shorthand when local variable names match field names.
- Learner can use struct update syntax with `..other_instance` and explain that it must come last.
- Learner can explain the ownership effects of struct update syntax when moved fields are non-`Copy`.
- Learner can define tuple structs and explain why different tuple struct names produce different types even with identical field types.
- Learner can define and instantiate unit-like structs.
- Learner can explain why `User` uses owned `String` fields in this section instead of `&str` fields.
- Learner can diagnose E0106 when a struct stores `&str` fields without lifetime specifiers.

### Card Content Candidates

#### Concepts

- Structs and tuples both hold multiple related values.
- Struct fields can have different types, like tuple elements.
- Unlike tuples, structs name each piece of data, making field meanings clear.
- Naming struct fields makes structs more flexible than tuples because code does not rely on field order to specify or access values.
- A struct definition starts with `struct`, followed by the struct name.
- A struct name should describe the significance of the grouped data.
- Struct fields are the named pieces of data inside the curly-braced struct definition.
- A struct field declaration has a field name and type.
- A struct instance is created by giving concrete values for each field.
- Struct instance syntax uses the struct name followed by curly braces containing `key: value` pairs.
- In struct instance syntax, keys are field names and values are the data to store in those fields.
- Fields in an instance do not need to be written in the same order as the struct definition.
- A struct definition is a general template for the type.
- A struct instance fills the template with particular data to create a value of the type.
- Dot notation accesses a specific field, as in `user1.email`.
- Dot notation can also assign into a field when the struct instance is mutable.
- The entire struct instance must be mutable to mutate any field.
- Rust does not allow only selected struct fields to be marked mutable.
- A new struct instance can be the last expression in a function body and be returned implicitly.
- Naming function parameters the same as struct fields can be useful, especially in constructor-style helper functions.
- Field init shorthand applies when a local variable or parameter has exactly the same name as a struct field.
- With field init shorthand, write `email` instead of `email: email`.
- Struct update syntax creates a new instance using most values from another instance of the same type while overriding selected fields.
- `..user1` means remaining fields not explicitly set should use values from `user1`.
- `..user1` must come last in the struct literal.
- Struct update syntax allows explicitly specified fields in any order.
- Struct update syntax uses `=`-like assignment behavior and can move data.
- In Listing 5-7, `user1.username` moves into `user2`, so `user1` as a whole can no longer be used afterward.
- If struct update only copied `active` and `sign_in_count` from `user1`, then `user1` would still be valid because those fields implement `Copy`.
- In Listing 5-7, `user1.email` remains usable because its value was not moved out of `user1`.
- Tuple structs look similar to tuples but have a struct name.
- Tuple structs have field types but no field names.
- Tuple structs are useful when the whole tuple should have a name and be a distinct type, while field names would be redundant or verbose.
- Tuple struct definition syntax starts with `struct`, the name, then tuple-like field types.
- Each tuple struct definition creates its own type, even if two tuple structs contain fields with the same types.
- `Color(i32, i32, i32)` and `Point(i32, i32, i32)` are different types.
- A function expecting `Color` cannot accept a `Point`, even though both contain three `i32` values.
- Tuple struct instances can be destructured into pieces.
- Tuple struct fields can be accessed with dot-index syntax, as in tuple values.
- Unlike ordinary tuples, tuple struct destructuring must include the tuple struct type name, such as `let Point(x, y, z) = origin;`.
- Unit-like structs have no fields.
- Unit-like structs behave similarly to the unit type `()`.
- Unit-like structs are useful when you need to implement a trait on a type but do not need to store data in the type.
- Unit-like struct definition uses `struct Name;` with a semicolon and no curly braces or parentheses.
- Unit-like struct instantiation uses the name alone.
- The `User` struct uses owned `String` fields rather than `&str` deliberately.
- Owned `String` fields mean each `User` instance owns all of its data.
- Owned fields keep the data valid for as long as the whole struct is valid.
- Structs can store references, but doing so requires lifetimes.
- Lifetimes ensure referenced data in a struct is valid for as long as the struct is.
- Lifetimes are deferred to Chapter 10 in this section.
- A struct with `&str` fields and no lifetime specifiers fails with E0106.
- The current fix in this chapter is to use owned types like `String` instead of references like `&str`.

#### Comparisons

- Struct vs tuple: both hold related values, but structs name fields and do not require order-based access.
- Struct definition vs struct instance: a type template vs a concrete value of that type.
- Field assignment vs field init shorthand: `email: email` vs `email` when names match.
- Manual field reuse vs struct update syntax: listing each reused field vs `..user1`.
- Struct update with moved fields vs copied fields: `String` fields move; `bool` and `u64` copy.
- Regular struct vs tuple struct: named fields vs unnamed typed positions plus a distinct type name.
- Tuple struct vs tuple: tuple struct has its own named type and requires that name for construction/destructuring.
- Tuple struct vs unit-like struct: unnamed fields inside parentheses vs no fields and semicolon definition.
- Owned `String` fields vs `&str` reference fields: data owned by the struct and valid with it vs borrowed data requiring lifetime annotations.

## Section: An Example Program Using Structs

### Learning Objectives

- Learner can explain why two separate parameters for rectangle dimensions are less clear than one grouped rectangle value.
- Learner can compare the tuple refactor with the struct refactor for grouping rectangle dimensions.
- Learner can define and use a `Rectangle` struct whose named `width` and `height` fields make related data explicit.
- Learner can explain why `area` borrows `&Rectangle` instead of taking ownership of the `Rectangle` instance.
- Learner can access fields of a borrowed struct without moving field values.
- Learner can diagnose E0277 when attempting to print a struct with the default `{}` formatter.
- Learner can distinguish `Display` formatting from `Debug` formatting for custom structs.
- Learner can add `#[derive(Debug)]` and use `{:?}` or `{:#?}` to print a struct for debugging.
- Learner can explain how `dbg!` differs from `println!` in ownership, output stream, included location information, and return value.
- Learner can explain why `dbg!(&rect1)` borrows the struct while `dbg!(30 * scale)` can return the owned expression value.

### Card Content Candidates

#### Concepts

- The rectangle example starts with separate variables `width1` and `height1`.
- Listing 5-8's `area(width: u32, height: u32) -> u32` succeeds but does not encode that the two parameters are related dimensions of one rectangle.
- Grouping related data makes code clearer and more manageable.
- The tuple refactor passes one argument, `rect1: (u32, u32)`, to `area`.
- Tuples add some structure but do not name their elements.
- Tuple field access with `.0` and `.1` makes the area calculation less obvious than named fields.
- Width/height order does not matter for area but would matter for drawing a rectangle, making tuple-index meaning a real error risk.
- Structs add meaning by labeling data.
- A `Rectangle` struct names both the whole value and its parts.
- Listing 5-10 defines `Rectangle { width: u32, height: u32 }`.
- A `Rectangle` instance with `width: 30` and `height: 50` represents one specific rectangle.
- In Listing 5-10, `area` takes `rectangle: &Rectangle`.
- Borrowing `&Rectangle` lets `main` retain ownership of `rect1` and continue using it after the call.
- Field access on a borrowed struct instance does not move the field values.
- The `area(&rect1)` signature expresses the intent: compute the area of a `Rectangle` using its `width` and `height`.
- A struct type's named fields communicate the relationship between data more clearly than tuple indexes.
- `println!` with `{}` uses `Display` formatting.
- `Display` is intended for direct end-user consumption.
- Primitive types implement `Display` by default because their user-facing representation is unambiguous.
- Structs do not get a default `Display` implementation because Rust cannot guess which fields or punctuation should be shown.
- `Debug` formatting is intended to print values in a developer-useful form while debugging.
- `Debug` is not automatically available for a custom struct just because the struct exists.
- `#[derive(Debug)]` opts a custom type into compiler-provided debug-printing behavior.
- `#[derive(Debug)]` is an outer attribute placed immediately before the struct definition in this example.
- `{:?}` requests compact `Debug` formatting.
- `{:#?}` requests pretty `Debug` formatting.
- The `Debug` output for `Rectangle` shows all field values.
- The `dbg!` macro prints the source file and line number of the macro call plus the expression and result.
- `dbg!` returns ownership of the expression value, so it can be used inside another expression such as a struct field initializer.
- `dbg!(30 * scale)` returns `60`, so the `width` field receives `60`.
- `dbg!` takes ownership of its expression; passing `&rect1` avoids moving `rect1`.
- `dbg!` prints to `stderr`.
- `println!` prints to `stdout`.
- The section names Appendix C as the place listing derivable traits and Chapter 10 as where custom trait implementations and custom traits are covered.
- The section ends by motivating the next refactor: tying `area` more closely to `Rectangle` by turning it into a method.

#### Syntax Forms

- Listing 5-8, separate width and height parameters:
  ```rust
  fn main() {
      let width1 = 30;
      let height1 = 50;

      println!(
          "The area of the rectangle is {} square pixels.",
          area(width1, height1)
      );
  }

  fn area(width: u32, height: u32) -> u32 {
      width * height
  }
  ```
- Listing 5-9, tuple grouping:
  ```rust
  fn main() {
      let rect1 = (30, 50);

      println!(
          "The area of the rectangle is {} square pixels.",
          area(rect1)
      );
  }

  fn area(dimensions: (u32, u32)) -> u32 {
      dimensions.0 * dimensions.1
  }
  ```
- Listing 5-10, struct grouping and borrowing:
  ```rust
  struct Rectangle {
      width: u32,
      height: u32,
  }

  fn main() {
      let rect1 = Rectangle {
          width: 30,
          height: 50,
      };

      println!(
          "The area of the rectangle is {} square pixels.",
          area(&rect1)
      );
  }

  fn area(rectangle: &Rectangle) -> u32 {
      rectangle.width * rectangle.height
  }
  ```
- Listing 5-11, intentionally compile-fail default formatting:
  ```rust
  struct Rectangle {
      width: u32,
      height: u32,
  }

  fn main() {
      let rect1 = Rectangle {
          width: 30,
          height: 50,
      };

      println!("rect1 is {rect1}");
  }
  ```
- Debug formatting without `derive`, intentionally compile-fail:
  ```rust
  struct Rectangle {
      width: u32,
      height: u32,
  }

  fn main() {
      let rect1 = Rectangle {
          width: 30,
          height: 50,
      };

      println!("rect1 is {:?}", rect1);
  }
  ```
- Listing 5-12, deriving `Debug` and using compact debug formatting:
  ```rust
  #[derive(Debug)]
  struct Rectangle {
      width: u32,
      height: u32,
  }

  fn main() {
      let rect1 = Rectangle {
          width: 30,
          height: 50,
      };

      println!("rect1 is {rect1:?}");
  }
  ```
- Pretty debug formatting:
  ```rust
  println!("rect1 is {rect1:#?}");
  ```
- `dbg!` inside a field initializer and by-reference whole-struct debugging:
  ```rust
  #[derive(Debug)]
  struct Rectangle {
      width: u32,
      height: u32,
  }

  fn main() {
      let scale = 2;
      let rect1 = Rectangle {
          width: dbg!(30 * scale),
          height: 50,
      };

      dbg!(&rect1);
  }
  ```

#### Failure Modes

- Keeping related values as separate parameters when one grouped domain value would better convey intent.
- Replacing separate variables with a tuple but then relying on `.0` and `.1` positional meaning that readers must remember.
- Assuming tuple grouping and struct grouping are equally clear for width/height semantics.
- Passing a `Rectangle` by value to `area` when the caller should retain ownership.
- Assuming field access through `&Rectangle` moves `u32` field values or invalidates the struct borrow.
- Trying to print a custom struct with `{}` before implementing `Display`.
- Assuming `Debug` formatting is available for every custom struct without opting in.
- Adding `:?` to the format string but forgetting `#[derive(Debug)]`.
- Confusing `{:?}` with `{:#?}` and expecting pretty multi-line output from the compact formatter.
- Using `dbg!(rect1)` when subsequent code still needs to own `rect1`; use `dbg!(&rect1)` for a borrowed debug print.

#### Comparisons

- Separate parameters vs tuple parameter: tuple grouping reduces argument count but still hides field meaning behind indexes.
- Tuple parameter vs struct parameter: a struct names both the grouped value and its parts, making the relationship explicit.
- Tuple indexes `.0`/`.1` vs struct fields `.width`/`.height`: indexes require remembered convention; fields carry meaning in the code.
- Passing `Rectangle` by value vs passing `&Rectangle`: by-value transfer would give `area` ownership; borrowing lets `main` keep using `rect1`.
- `Display` vs `Debug`: `Display` is end-user-oriented formatting; `Debug` is developer-oriented inspection output.
- `{:?}` vs `{:#?}`: compact debug output vs pretty multi-line debug output.
- `println!` vs `dbg!`: `println!` formats explicitly for `stdout` and takes references internally; `dbg!` takes ownership of its expression, emits source location plus value to `stderr`, and returns the value.
- Derived `Debug` vs manually implemented formatting: this section uses `#[derive(Debug)]`; custom implementations are deferred to Chapter 10.

### Card Content Candidates

#### Concepts

- Methods are similar to functions: they use `fn`, have a name, can have parameters, can return values, and contain code called from elsewhere.
- Unlike free functions, methods are defined in the context of a struct, enum, or trait object.
- A method's first parameter is always `self`.
- `self` represents the instance the method is called on.
- Method syntax places the call after an instance: dot, method name, parentheses, and any arguments.
- An `impl Rectangle` block associates its contents with the `Rectangle` type.
- Everything inside `impl Rectangle { ... }` is associated with `Rectangle`.
- Listing 5-13 moves `area` into `impl Rectangle`.
- Listing 5-13 changes `area(rectangle: &Rectangle)` to `area(&self)`.
- `&self` is shorthand for `self: &Self`.
- Inside an `impl` block, `Self` is an alias for the type after `impl`.
- Methods must have a first parameter named `self` whose type is `Self`.
- Rust lets method signatures abbreviate the first parameter to `self`, `&self`, or `&mut self`.
- `&self` means the method immutably borrows the instance.
- `&mut self` means the method mutably borrows the instance.
- `self` means the method takes ownership of the instance.
- Listing 5-13 uses `&self` because `area` only reads the rectangle and should not take ownership.
- Use `&mut self` when a method needs to change the instance it is called on.
- A method that takes ownership with `self` is rare and is usually for transforming the instance into something else while preventing the caller from using the original afterward.
- Methods improve organization by grouping the capabilities of a type in `impl` blocks.
- Methods avoid repeating the type of `self` in every method signature.
- A method can have the same name as a struct field.
- Parentheses disambiguate a same-named method from a field: `rect1.width()` calls the method, while `rect1.width` accesses the field.
- A getter is often a method with the same name as a field that returns the field value and does nothing else.
- Rust does not automatically implement getter methods for struct fields.
- Getters are useful when a field is private but a public method should provide read-only access.
- Public/private fields and methods are deferred to Chapter 7.
- Rust has no `->` operator for method calls on pointers.
- Rust method calls use automatic referencing and dereferencing.
- In method-call syntax, Rust may automatically add `&`, `&mut`, or `*` so the receiver matches the method signature.
- `p1.distance(&p2)` and `(&p1).distance(&p2)` are equivalent in the source's automatic-reference example.
- Automatic receiver adjustment works because methods have a clear receiver: the type of `self`.
- Given a receiver and method name, Rust can determine whether the method reads, mutates, or consumes the receiver.
- Implicit receiver borrowing is part of what makes Rust ownership ergonomic in practice.
- Methods can take parameters in addition to `self`.
- Additional method parameters are written after the `self` parameter and work like ordinary function parameters.
- Listing 5-15 defines `can_hold(&self, other: &Rectangle) -> bool`.
- `can_hold` reads both rectangles and returns whether both dimensions of `self` are greater than the corresponding dimensions of `other`.
- `rect1.can_hold(&rect2)` passes an immutable borrow of `rect2` so `main` keeps ownership of `rect2`.
- All functions defined inside an `impl` block are associated functions because they are associated with the type named after `impl`.
- Methods are associated functions whose first parameter is `self`.
- Associated functions without `self` are not methods because they do not work with an instance of the type.
- `String::from` is an example already used in the book of an associated function defined on `String`.
- Associated functions without `self` are often used as constructor-style functions that return a new instance.
- `new` is a conventional constructor name but is not special or built into Rust.
- `Rectangle::square(size)` is a constructor-style associated function that sets both `width` and `height` to `size`.
- In `fn square(size: u32) -> Self`, both the return type `Self` and the struct literal `Self { ... }` refer to `Rectangle`.
- Associated functions are called with `::` and the type name, as in `Rectangle::square(3)`.
- The `::` syntax is used for associated functions and for namespaces created by modules.
- A struct may have multiple `impl` blocks.
- Listing 5-16 splits `area` and `can_hold` into separate `impl Rectangle` blocks while remaining equivalent to Listing 5-15 for this chapter's purposes.
- The source says there is no reason to split these methods here, but it is valid syntax.
- A later Chapter 10 case will make multiple `impl` blocks useful when discussing generic types and traits.
- CH-05 summary: structs create meaningful domain custom types; `impl` blocks define functions associated with a type; methods are associated functions that specify behavior for struct instances.

#### Syntax Forms

- Listing 5-13, defining and calling an `area` method:
  ```rust
  #[derive(Debug)]
  struct Rectangle {
      width: u32,
      height: u32,
  }

  impl Rectangle {
      fn area(&self) -> u32 {
          self.width * self.height
      }
  }

  fn main() {
      let rect1 = Rectangle {
          width: 30,
          height: 50,
      };

      println!(
          "The area of the rectangle is {} square pixels.",
          rect1.area()
      );
  }
  ```

  ```rust
  fn area(&self) -> u32
  ```

  ```rust
  fn area(self: &Self) -> u32
  ```

  ```rust
          self.width > 0
  ```

#### Comparisons

- Function vs method: both use `fn` and can have parameters/returns, but methods are defined in an associated type context and take `self` first.
- Free `area(&Rectangle)` function vs `area(&self)` method: explicit rectangle parameter vs receiver shorthand and method-call syntax.
- `&self` vs `&mut self` vs `self`: immutable borrow, mutable borrow, and ownership transfer of the receiver.
- Field access vs method call: `rect1.width` reads a field; `rect1.width()` calls a method.
- Getter vs public field access: a getter can expose read-only access while keeping the field private; public/private is covered later.
- Rust method calls vs C/C++ pointer method calls: Rust has no `->`; automatic referencing/dereferencing adjusts the receiver.
- Method vs associated function: methods have `self` first and are called on instances; associated functions without `self` are called with `Type::function(...)`.
- `Self` in a return type vs concrete type name: inside `impl Rectangle`, `Self` aliases `Rectangle`.
- One `impl` block vs multiple `impl` blocks: both are valid for the same struct; splitting is not useful in this simple example but matters later with generics and traits.
