### Card Content Candidates

#### Concepts

- As programs grow, organizing code becomes increasingly important.
- Grouping related functionality clarifies where to find code that implements a feature.
- Separating code with distinct features clarifies where to change how a feature works.
- Earlier programs in the book have used one module in one file.
- As a project grows, code should be organized by splitting it into multiple modules and then multiple files.
- A package can contain multiple binary crates.
- A package can optionally contain one library crate.
- As a package grows, parts can be extracted into separate crates that become external dependencies.
- Cargo workspaces are for very large projects made of interrelated packages that evolve together.
- Cargo workspaces are deferred to Chapter 14.
- Encapsulation means hiding implementation details behind a public interface.
- Encapsulation lets other code reuse code at a higher level without knowing how the implementation works.
- How code is written defines which parts are public for other code to use.
- How code is written also defines which parts are private implementation details that can be changed.
- Public/private organization limits the amount of detail a programmer has to keep in mind.
- Scope is the nested context in which code is written.
- A scope contains a set of names that are defined as in scope.
- Programmers and compilers need to know whether a name refers to a variable, function, struct, enum, module, constant, or other item.
- Programmers and compilers also need to know what the named item means at that location.
- Rust lets code create scopes and change which names are in or out of scope.
- Two items with the same name cannot exist in the same scope.
- Tools are available to resolve name conflicts.
- Rust has features for managing code organization, exposed/private details, and names in scope.
- These features are collectively referred to as the module system.
- Packages are a Cargo feature for building, testing, and sharing crates.
- Crates are trees of modules that produce a library or executable.
- Modules and `use` control organization, scope, and privacy of paths.
- Paths are ways of naming an item such as a struct, function, or module.
- The chapter explains how module-system features interact.
- The chapter explains how to use module-system features to manage scope.

### Card Content Candidates

#### Concepts

- Packages and crates are the first module-system pieces covered in CH-07.
- A crate is the smallest amount of code the Rust compiler considers at a time.
- If you run `rustc` directly on a single source file, the compiler considers that file a crate.
- Crates can contain modules.
- Modules in a crate may be defined in other files that are compiled with the crate.
- A crate has one of two forms: binary crate or library crate.
- Binary crates are programs that compile to executable files you can run.
- Command line programs and servers are examples of binary crates.
- Every binary crate must have a function named `main`.
- The `main` function defines what happens when the executable runs.
- The crates created so far in the book have been binary crates.
- Library crates do not have a `main` function.
- Library crates do not compile to executables.
- Library crates define functionality intended to be shared with multiple projects.
- `rand` is the section's example of a library crate.
- When Rustaceans say "crate", they usually mean library crate.
- Rustaceans often use "crate" interchangeably with the general programming concept of a library.
- The crate root is the source file the Rust compiler starts from.
- The crate root makes up the root module of the crate.
- Module details are deferred to `ch07-02-defining-modules-to-control-scope-and-privacy`.
- A package is a bundle of one or more crates that provides a set of functionality.
- A package contains a `Cargo.toml` file.
- `Cargo.toml` describes how to build the package's crates.
- Cargo itself is a package.
- The Cargo package contains the binary crate for the `cargo` command line tool.
- The Cargo package also contains a library crate that the binary crate depends on.
- Other projects can depend on Cargo's library crate to use the same logic as the Cargo command line tool.
- A package can contain as many binary crates as desired.
- A package can contain at most one library crate.
- A package must contain at least one crate.
- The one required crate can be either a library crate or a binary crate.
- `cargo new my-project` creates a binary package by default in this example.
- In the `my-project` directory, `Cargo.toml` indicates the package.
- The generated `src/main.rs` is the source file for the default binary crate.
- Cargo does not need `src/main.rs` listed explicitly in `Cargo.toml`.
- Cargo convention treats `src/main.rs` as the crate root of a binary crate with the same name as the package.
- Cargo convention treats `src/lib.rs` as the crate root of a library crate with the same name as the package.
- Cargo passes crate root files to `rustc` to build the library or binary.
- A package with only `src/main.rs` contains only a binary crate named like the package.
- A package with both `src/main.rs` and `src/lib.rs` has two crates: one binary and one library, both named like the package.
- Files in `src/bin` create additional binary crates.
- Each file in `src/bin` is a separate binary crate.

### Card Content Candidates

#### Concepts

- Modules organize code within a crate for readability and easy reuse.
- Modules control privacy because code within a module is private by default.
- Private items are internal implementation details not available for outside use.
- Public modules and public items expose API surface that outside code can use and depend on.
- The module cheat sheet starts from the crate root: when compiling a crate, the compiler first looks in the crate root file.
- A library crate usually has `src/lib.rs` as its crate root.
- A binary crate usually has `src/main.rs` as its crate root.
- In the crate root file, declaring `mod garden;` makes the compiler look for the module code inline, in `src/garden.rs`, or in `src/garden/mod.rs`.
- In a non-root file such as `src/garden.rs`, declaring `mod vegetables;` makes the compiler look for submodule code inline, in `src/garden/vegetables.rs`, or in `src/garden/vegetables/mod.rs`.
- Once a module is part of the crate, code elsewhere in the same crate can refer to its code by path if the privacy rules allow it.
- The quick-reference path for `Asparagus` is `crate::garden::vegetables::Asparagus`.
- `use` creates a shortcut in a scope so a long path does not need to be repeated.
- In the quick-reference `backyard` crate, `src/main.rs` is the crate root.
- In `backyard`, `pub mod garden;` in `src/main.rs` includes `src/garden.rs`.
- In `backyard`, `pub mod vegetables;` in `src/garden.rs` includes `src/garden/vegetables.rs`.
- In `backyard`, `#[derive(Debug)] pub struct Asparagus {}` defines the public type used from `main`.
- The restaurant example is a library crate created with `cargo new restaurant --lib`.
- Listing 7-1 concentrates on code organization by using empty function bodies.
- `front_of_house` models customer-facing restaurant work.
- `hosting` groups waiting-list and seating functions.
- `serving` groups order, serving, and payment functions.
- The book contrasts front of house with back of house as a domain-driven grouping example.
- A module is defined with `mod` followed by the module name and a body in curly braces when using inline module syntax.
- Modules can contain other modules.
- Modules can contain other items, including structs, enums, constants, traits, and functions.
- Grouping related definitions gives programmers a meaningful navigation structure.
- Grouping related definitions helps maintainers know where to place new functionality.
- The contents of `src/main.rs` or `src/lib.rs` form a module named `crate` at the root of the module tree.
- The module tree is the crate's nested module structure.
- Listing 7-2 shows `front_of_house` as a child of `crate`.
- Listing 7-2 shows `hosting` and `serving` as children of `front_of_house`.
- `hosting` and `serving` are siblings because they are defined in the same module.
- If module A is contained inside module B, A is the child and B is the parent.
- The entire module tree is rooted under the implicit module named `crate`.
- The module tree is analogous to a filesystem directory tree.
- Like files in directories, modules need paths so code can find them.

#### Comparisons

- Module vs crate: a crate is the compiler unit; modules organize code inside a crate.
- Inline module body vs separate module file: curly braces contain the code inline; a semicolon declaration makes the compiler find the code in conventional file locations.
- Crate-root module declaration vs submodule declaration: crate-root declarations look under `src/`; submodule declarations look under the parent module's directory.
- Private vs public item: private implementation detail unavailable for outside use vs exposed API surface other code can depend on.
- Public module vs public item inside a module: a public module opens the module path, but contained items also need `pub` when they should be accessible.
- Parent vs child module: the parent contains the child; the child is nested inside the parent.
- Sibling modules: modules defined in the same containing module.
- Module tree vs filesystem tree: both are hierarchical organization tools, but the module tree is the logical Rust structure and the filesystem is one storage layout.
- `mod` vs `use`: `mod` declares/includes module code in the crate; `use` creates a shorter name for an existing path in a scope.

#### Concepts

- A path tells Rust where to find an item in the module tree.
- Calling a function requires knowing its path.
- An absolute path is the full path starting from a crate root.
- For code from an external crate, an absolute path begins with the crate name.
- For code from the current crate, an absolute path begins with the literal `crate`.
- A relative path starts from the current module.
- A relative path can start with `self`.
- A relative path can start with `super`.
- A relative path can start with an identifier in the current module.
- Absolute and relative paths use identifiers separated by double colons, `::`.
- Listing 7-3 calls `add_to_waitlist` from `eat_at_restaurant` using both absolute and relative paths.
- `eat_at_restaurant` is defined in the crate root in Listing 7-3.
- `pub fn eat_at_restaurant` marks `eat_at_restaurant` as part of the library crate's public API.
- The Listing 7-3 absolute path is `crate::front_of_house::hosting::add_to_waitlist()`.
- The Listing 7-3 relative path is `front_of_house::hosting::add_to_waitlist()`.

- A relative path is more stable when the item definition and use site are moved together into a new module.

- If only `eat_at_restaurant` moves into `dining`, the absolute path remains valid and the relative path must be updated.
- Listing 7-3 has correct paths but does not compile because `hosting` is private.
- Rust privacy applies even when the path itself names the right item.
- All items are private to parent modules by default.
- Items include functions, methods, structs, enums, modules, and constants.
- Putting an item in a module is how Rust makes that item private from parent modules by default.
- Parent modules cannot use private items inside child modules.
- Child modules can use items in ancestor modules.
- Child modules wrap and hide implementation details while still seeing the context in which they are defined.
- Rust defaults to hiding inner implementation details so internal code can change without breaking outer code.
- The `pub` keyword exposes inner parts of child modules to ancestor modules.
- Listing 7-5 makes `hosting` public but still fails because `add_to_waitlist` remains private.

- In Listing 7-7, `add_to_waitlist` is public and its parent module is accessible, so the function call works.

- API design and change management matter because users depend on public items.

- The module tree should be defined in `src/lib.rs` in the binary-plus-library package pattern.
- The binary crate can use library public items by starting paths with the package name.
- In that pattern, the binary crate is a user of the library crate, just like an external crate.
- The binary crate can only use the library crate's public API.
- Using the binary as a client helps the author design a good API.
- `super` starts a relative path from the parent module.

- Public structs still have private fields by default.

#### Comparisons

- Absolute vs relative path: absolute starts from a crate root; relative starts from the current module.
- Current-crate absolute path vs external-crate absolute path: current crate starts with `crate`; external crate starts with the external crate name.
- Relative starts: `self` starts from the current module, `super` starts from the parent module, and an identifier starts from an item in the current module.
- Path correctness vs visibility: a path can name the right item but still fail if a private module or item blocks access.
- `pub mod` vs `pub fn`: `pub mod` exposes the module path; `pub fn` exposes the function item.
- Parent-to-child privacy vs child-to-ancestor visibility: parents cannot use private child items; children can use ancestor items.
- Absolute path move tradeoff vs relative path move tradeoff: absolute paths are usually more stable when definitions and calls move independently; relative paths are more stable when related code moves together.
- `super` vs `crate`: `super` starts from the parent of the current module; `crate` starts from the crate root.
- Public struct vs public enum: a public struct's fields remain private unless individually public; a public enum's variants are public.
- Public field vs private field: public fields can be read and written from outside the module; private fields are controlled by module code.
- Library crate code vs binary crate code in one package: library holds reusable functionality and public API; binary starts the executable and acts as a client of the library.

#### Concepts

- Assuming `use` behaves like a global import across child modules.

#### Comparisons

- Full path call vs `use` shortcut: full path repeats the entire path each time; `use` gives a shorter scoped name.
- `mod` vs `use`: `mod` declares module code as part of the crate; `use` creates a scoped shortcut to an existing path.
- Parent-scope `use` vs child-module use: the parent shortcut is not automatically in the child; the child needs its own `use` or `super::`.
- Function import idiom vs struct/enum import idiom: functions usually import the parent module; structs and enums usually import the full item path.
- Parent-module same-name handling vs `as` alias: parent modules preserve both names through qualification; `as` gives one import a distinct local name.
- Plain `use` vs `pub use`: plain `use` is private to the importing scope; `pub use` re-exports the name for outside code.
- Third-party crate import vs standard library import: third-party crates require `Cargo.toml` dependency entries; `std` ships with Rust.
- Separate imports vs nested paths: separate imports are straightforward; nested paths reduce repeated prefixes and vertical space.
- Nested `self` import vs ordinary nested import: `self` imports the common prefix itself in addition to child items.
- Explicit imports vs glob imports: explicit imports show where names come from; glob imports bring all public names and can obscure provenance.

#### Concepts

- Early CH-07 examples define multiple modules in one file.
- As modules get large, moving module definitions to separate files can make code easier to navigate.
- The section starts from the Listing 7-17 restaurant code and extracts modules into files.
- The crate root in the example is `src/lib.rs`.
- The same extraction procedure works for binary crates with `src/main.rs` as the crate root.
- To extract `front_of_house`, remove the inline module body from `src/lib.rs` and leave `mod front_of_house;`.
- Listing 7-21 does not compile until `src/front_of_house.rs` exists.
- `src/front_of_house.rs` contains the definitions that used to be inside the `front_of_house` curly braces.
- The compiler knows to look in `src/front_of_house.rs` because the crate root has a `mod front_of_house;` declaration.
- A module file only needs to be loaded once with a `mod` declaration in the module tree.
- Once the compiler knows a file is part of the project, other files should refer to that module's code by paths to where the module was declared.
- The location of the `mod` statement tells Rust where the code resides in the module tree.
- `mod` is not an include operation from other programming languages.
- To extract child module `hosting`, first change `src/front_of_house.rs` to contain only `pub mod hosting;`.
- Because `hosting` is a child of `front_of_house`, its file goes under a directory named for its parent module: `src/front_of_house/hosting.rs`.
- `src/front_of_house/hosting.rs` contains the definitions that used to be inside the `hosting` curly braces.
- If `hosting.rs` were placed directly in `src/`, Rust would expect it to be code for a `hosting` module declared in the crate root.
- The compiler's file lookup rules make directories and files closely match the module tree.
- The most idiomatic file path for a root child module named `front_of_house` is `src/front_of_house.rs`.
- The older supported file path for that same module is `src/front_of_house/mod.rs`.
- The most idiomatic file path for a submodule `hosting` under `front_of_house` is `src/front_of_house/hosting.rs`.
- The older supported file path for that same submodule is `src/front_of_house/hosting/mod.rs`.
- Using both idiomatic and older styles for the same module causes a compiler error.
- Mixing styles for different modules in the same project is allowed but can confuse project navigation.
- The main downside of the `mod.rs` style is many files named `mod.rs`, which can be confusing when open in an editor.
- Moving module code to separate files keeps the module tree the same.
- Existing function calls in `eat_at_restaurant` work without modification after the module definitions move to different files.
- `pub use crate::front_of_house::hosting` in `src/lib.rs` does not change during the file split.
- `use` does not determine which files are compiled as part of the crate.
- `mod` declares modules; Rust then looks for a file with the same name as the module for that module's code.
- CH-07 summary: Rust lets you split a package into multiple crates and a crate into modules.
- CH-07 summary: items in one module can be referred to from another module with absolute or relative paths.
- CH-07 summary: `use` brings paths into scope so shorter paths can be reused in that scope.
- CH-07 summary: module code is private by default.
- CH-07 summary: `pub` makes definitions public.

#### Comparisons

- Inline module vs file-backed module: inline modules put the body in curly braces; file-backed modules use a `mod name;` declaration and store the body in a conventional file.
- Crate-root module file vs submodule file: root child `front_of_house` lives under `src/`; child `hosting` under `front_of_house` lives under `src/front_of_house/`.
- `mod` vs path: `mod` declares code into the module tree; paths refer to items already declared in the module tree.
- `mod` vs `use`: `mod` determines module code included in the crate; `use` only creates shortcuts and does not affect compiled files.
- Idiomatic file path vs older `mod.rs` path: `src/module.rs` and `src/module/submodule.rs` are the covered style; `src/module/mod.rs` and `src/module/submodule/mod.rs` are older but still supported.
- Module tree vs file tree: the module tree remains unchanged after splitting files; the file tree mirrors it more closely for navigation.
- Single-file chapter examples vs split-file project structure: small examples are compact in one file; larger modules become easier to navigate when split.
