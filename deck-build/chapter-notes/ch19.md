#### Concepts

- Patterns are valid in many Rust constructs, not only in `match`.
- The section explicitly covers `match` arms, `let` statements, conditional `if let` expressions, `while let` loops, `for` loops, function parameters, and closure parameters.
- A `match` expression consists of the keyword `match`, a value to match on, and one or more match arms.
- Each match arm consists of a pattern and an expression to run when the value matches the arm pattern.
- In `match x { None => None, Some(i) => Some(i + 1) }`, the patterns are `None` and `Some(i)`.
- `match` expressions must be exhaustive.
- Exhaustive means every possibility for the matched value must be accounted for.
- A final catch-all pattern is one way to cover every remaining case.
- A variable-name pattern can match any value and bind it.
- The `_` pattern matches anything but never binds a variable.
- `_` is often useful as the last match arm when the code wants to ignore any value not specified.
- Every `let` statement uses a pattern.
- The formal shape of a `let` statement is `let PATTERN = EXPRESSION;`.
- In `let x = 5;`, `x` is a simple variable-name pattern.
- A variable-name pattern means "bind what matches here to this variable."
- When a variable name is the whole pattern, it binds the entire value.
- Listing 19-1 uses `let (x, y, z) = (1, 2, 3);` to destructure a tuple.
- In Listing 19-1, Rust compares `(1, 2, 3)` to `(x, y, z)`.
- The tuple pattern matches because both sides have three elements.
- Rust binds `1` to `x`, `2` to `y`, and `3` to `z`.
- A tuple pattern can be understood as nested variable patterns.
- Listing 19-2 shows `let (x, y) = (1, 2, 3);`, which does not compile.
- Listing 19-2 fails because the pattern has two tuple elements but the expression has three.
- Listing 19-2 produces E0308, "mismatched types."
- The compiler reports that it expected a tuple with three elements but found one with two.
- To fix an arity mismatch, the pattern and expression types must match.
- If a pattern has too many variables, remove variables until the pattern arity matches the tuple.
- If the code wants to ignore tuple values, later CH-19 syntax uses `_` or `..`.
- `if let` is mainly a shorter way to write a `match` that handles one case.
- `if let` can have a corresponding `else` block that runs when the pattern does not match.
- Listing 19-3 mixes `if let`, `else if`, `else if let`, and `else`.
- An `if let`/`else if` chain is more flexible than a single `match` when conditions do not all compare one value against patterns.
- Rust does not require conditions in an `if let`/`else if` chain to relate to one another.
- Listing 19-3 checks a favorite color, Tuesday status, parsed age, and a final default color.
- With the hardcoded values in Listing 19-3, the program prints `Using purple as the background color`.
- In Listing 19-3, `if let Some(color) = favorite_color` binds `color` only when `favorite_color` is `Some`.
- In Listing 19-3, `else if let Ok(age) = age` creates a new `age` variable containing the value inside `Ok`.

- `if let` does not provide compiler exhaustiveness checking.
- Omitting a final `else` in an `if let` chain can miss cases without a compiler warning.
- `while let` is similar in construction to `if let`.
- A `while let` loop runs as long as a pattern continues to match.
- Listing 19-4 uses `while let Ok(value) = rx.recv()` to print received channel values.
- `rx.recv()` returns `Ok(value)` as long as a message arrives while the sender exists.
- `rx.recv()` returns `Err` once the sender side disconnects.
- Listing 19-4 prints `1`, `2`, and `3`, then stops when the pattern no longer matches.
- In a `for` loop, the value directly after `for` is a pattern.
- In `for x in y`, `x` is the pattern.
- Listing 19-5 uses `for (index, value) in v.iter().enumerate()` to destructure tuple items from `enumerate`.

- Function parameters can be patterns.
- In `fn foo(x: i32)`, `x` is a function-parameter pattern.

- Treating `match` as optional-exhaustive like `if let` is wrong; `match` must account for every possibility.
- Using `_` when the code later needs the value loses the binding because `_` never binds.
- Forgetting that variable-name catch-all patterns bind a value can accidentally introduce or shadow a variable.
- Assuming `let x = 5;` is not pattern matching misses the formal `let PATTERN = EXPRESSION;` shape.
- Destructuring a tuple with the wrong number of variables produces a type mismatch such as E0308.

- Relying on `if let` for exhaustive handling can hide missing cases because the compiler will not alert you.
- Assuming all conditions in an `if let`/`else if` chain must match against the same value misses the flexibility this section highlights.
- Expecting `while let` to run forever ignores that it stops when the pattern no longer matches.

- Treating function parameters as only names misses destructuring forms such as `&(x, y): &(i32, i32)`.

#### Comparisons

- `match` vs `if let`: `match` checks exhaustiveness over one matched value; `if let` is concise for one pattern and can be mixed with unrelated conditions, but lacks exhaustiveness checking.
- Variable catch-all vs `_`: both can match any value, but a variable name binds the value and `_` ignores it.
- `let` simple binding vs tuple destructuring: `let x = 5` binds the whole value; `let (x, y, z) = (1, 2, 3)` binds parts by structure.
- `if let` vs `while let`: `if let` runs a block once if the pattern matches; `while let` repeats while the pattern continues to match.
- `for` loop pattern vs function-parameter pattern: both use pattern positions to bind or destructure incoming values.
- Channel `recv` with `unwrap` or iterator from CH-16 vs `while let`: `while let` handles repeated `Ok` values and stops naturally on `Err`.

- Keep checks that depend on bindings introduced by `if let` inside the block where those bindings are in scope.
- Use `while let` for loops that should continue until an operation stops returning a matching shape, such as repeated `Ok` receives.
- Use tuple patterns in `for` loops and function parameters when destructuring improves local clarity.
- Prefer `_` or `..` only when ignored values truly are not needed; detailed ignore syntax belongs to the later pattern-syntax section.

### Card Content Candidates

#### Concepts

- Patterns come in two forms: refutable and irrefutable.
- An irrefutable pattern will match for any possible value passed.
- `x` in `let x = 5;` is irrefutable because it matches anything.
- A refutable pattern can fail to match for some possible value.
- `Some(x)` in `if let Some(x) = a_value` is refutable.
- `Some(x)` fails to match if `a_value` is `None`.
- Function parameters can only accept irrefutable patterns.
- `let` statements can only accept irrefutable patterns.
- `for` loops can only accept irrefutable patterns.
- Function parameters, `let` statements, and `for` loops require irrefutable patterns because the program cannot do anything meaningful when their values do not match.
- `if let` accepts refutable patterns.
- `while let` accepts refutable patterns.
- `let...else` accepts refutable patterns.
- `if let`, `while let`, and `let...else` also accept irrefutable patterns, but the compiler warns against them.
- The compiler warns against irrefutable patterns in conditional constructs because those constructs are intended to handle possible failure.
- The useful functionality of a conditional pattern construct is performing differently depending on match success or failure.
- The refutable/irrefutable distinction usually matters most when the compiler reports a refutability error or warning.
- When a refutability error appears, the fix is to change either the pattern or the construct using that pattern.
- Listing 19-8 uses `let Some(x) = some_option_value;`, which does not compile.
- In Listing 19-8, `Some(x)` is refutable because `some_option_value` could be `None`.
- A `let` statement cannot use `Some(x)` directly because `let` requires an irrefutable pattern.
- Listing 19-8 produces E0005, "refutable pattern in local binding."
- The E0005 output says pattern `None` is not covered.
- The E0005 output says `let` bindings require an irrefutable pattern.
- The E0005 output identifies the matched value type as `Option<i32>`.
- The E0005 help suggests using `let else` to handle the unmatched variant.
- Listing 19-9 fixes Listing 19-8 with `let Some(x) = some_option_value else { return; };`.
- `let...else` gives the code an explicit out when the refutable pattern does not match.
- In Listing 19-9, if `some_option_value` is `None`, the `else` block handles the unmatched value by returning.
- Listing 19-9 is valid because `let...else` can use refutable patterns.
- Listing 19-10 uses `let x = 5 else { return; };`.
- Listing 19-10 uses an irrefutable pattern in `let...else`.
- Listing 19-10 compiles but emits the `irrefutable_let_patterns` warning.
- The warning says the pattern will always match, so the `else` clause is useless.
- The warning suggests removing the `else` clause.
- Match arms generally use refutable patterns.
- The last match arm should match any remaining values with an irrefutable pattern.
- Rust allows an irrefutable pattern in a `match` with only one arm, but the source says that syntax is not particularly useful and can be replaced with a simpler `let` statement.

- Explain why the last match arm often uses an irrefutable pattern: it covers all remaining unmatched values.

#### Failure Modes

- Using a refutable pattern in a plain `let` statement produces a compile error because `let` has no built-in unmatched-case behavior.
- Treating `Some(x)` as safe in `let Some(x) = option;` ignores the possible `None` variant.
- Trying to use refutable patterns in function parameters or `for` loops conflicts with contexts that require every incoming value to match.
- Using `let...else` with a pattern that always matches makes the `else` branch useless and triggers a warning.
- Treating an `irrefutable_let_patterns` warning as only stylistic misses the construct mismatch: a conditional failure branch cannot fire.
- Fixing a refutability error by changing only the variable name may hide the intended conditional behavior; choose the construct based on whether failure should be handled.
- Using a one-arm `match` with an irrefutable pattern is usually needless compared with a simpler `let`.

#### Comparisons

- Refutable vs irrefutable: refutable patterns can fail for some valid value; irrefutable patterns match every possible value passed.
- `let` vs `let...else`: plain `let` requires an irrefutable pattern; `let...else` can use a refutable pattern because it provides an `else` path.
- `if let`/`while let`/`let...else` vs function params/`let`/`for`: the former are conditional or failure-aware constructs; the latter require a binding/destructuring that always succeeds.
- E0005 error vs `irrefutable_let_patterns` warning: E0005 rejects a refutable pattern where failure cannot be handled; the warning flags an irrefutable pattern in a construct designed for failure handling.
- Final `match` arm vs earlier match arms: earlier arms normally match specific refutable cases; the last arm can use an irrefutable pattern to cover all remaining cases.

#### Project / Architecture Decisions

- Use plain `let` only when the pattern is guaranteed to match every value of the expression's type.
- Use `let...else` when code needs to bind pieces from a refutable pattern and immediately handle the nonmatching case.
- Use `if let` or `while let` when success and failure should branch or loop conditionally rather than simply bind.
- Treat refutability diagnostics as a sign to reconsider both the pattern and the construct.

#### Concepts

- Named variables are irrefutable patterns that match any value.

- Variables declared as part of a pattern inside those expressions shadow outer variables with the same name.

- The `|` syntax is the pattern-or operator.

- The `..=` syntax matches an inclusive range of values.

- Range patterns can be shorter than listing every value with `|`.
- Rust checks at compile time that a pattern range is not empty.
- Pattern ranges are only allowed with numeric values or `char` values, because those are the types Rust can check for empty ranges.
- The numeric range example with `x = 5` prints `one through five`.
- The char range example with `x = 'c'` matches `'a'..='j'` and prints `early ASCII letter`.

- Struct destructuring variable names do not have to match field names.

- Struct field shorthand creates variables with the same names as the fields.
- Struct patterns can combine variable bindings and literal field tests.

- For an enum variant without data, such as `Message::Quit`, the pattern is just the literal variant path.

- For a tuple-like enum variant, such as `Message::Write(text)`, use tuple-pattern syntax after the variant name.

- `_` is a wildcard pattern that matches any value but does not bind it.
- `_` is useful as a final match arm that accounts for all remaining cases without using the value.
- `_` can appear in any pattern, including function parameters.

- The `..` pattern ignores any remaining parts of a value not explicitly matched.
- In Listing 19-23, `Point { x, .. }` binds only `x` and ignores `y` and `z`.

#### Failure Modes

- Expecting `Some(y)` in a `match` arm to compare with an outer `y` is wrong; it shadows by binding a new `y`.

- Trying to use range patterns with unsupported types conflicts with Rust's compile-time empty-range check.
- Destructuring enum variants with the wrong pattern shape or wrong field count will not match the variant's data definition.
- Using `_` when the value is needed later in the arm loses access to it.
- Using `_x` when avoiding a move is required is wrong because `_x` still binds and can take ownership.
- Using `_` in a trait method signature may be appropriate, but deleting the parameter may violate the required trait signature.
- Using `..` in more than one ambiguous tuple position fails because Rust cannot infer how many elements each `..` should ignore.
- Assuming match guards participate in exhaustiveness checking is wrong; the compiler does not try to check exhaustiveness when guards are involved.

- Using a range pattern without `@` when the matched value is needed in the arm loses the concrete value.

#### Comparisons

- Literal pattern vs named-variable pattern: a literal requires a concrete value; a named variable matches anything and binds it.
- Named binding vs match guard comparison: `Some(y)` creates a new binding; `Some(n) if n == y` compares with outer `y`.
- `|` vs `..=`: `|` matches discrete alternatives; `..=` compactly matches an inclusive contiguous numeric or char range.
- Renamed struct destructuring vs field shorthand: `x: a` creates a differently named binding; `x` shorthand creates a binding with the field name.
- Struct pattern vs struct-like enum variant pattern: both use braces and field names; enum variant patterns include the variant path.
- Tuple pattern vs tuple-like enum variant pattern: both bind by position and require matching arity; enum variant patterns include the variant path.
- `_` vs `_x`: `_` does not bind; `_x` binds while suppressing unused-variable warnings.
- Nested `_` vs `..`: nested `_` ignores specific positions; `..` ignores all remaining unspecified parts.
- `..` in structs vs tuples: struct `..` ignores unlisted fields; tuple `..` ignores a variable number of positions but must be unambiguous.
- Pattern-only matching vs match guard: patterns express structural tests; guards add arbitrary boolean conditions using bound values.
- Range-only pattern vs `@` binding: `3..=7` tests the range; `id @ 3..=7` tests and binds the exact matched value.

#### Project / Architecture Decisions

- Use literal patterns for small concrete cases where each value has distinct behavior.
- Use `|` for a small set of alternatives and `..=` for clear contiguous numeric or char ranges.
- Use struct field shorthand when binding variables with the same names as fields.
- Use literal fields in struct patterns when a case depends on a field having a specific value.
- Use nested enum/struct patterns when a single `match` arm can clearly express the full shape being handled.
- Use `_` for values that are intentionally ignored and should not be moved or bound.
- Use a leading-underscore variable name when the value should still be bound but unused warnings should be suppressed.
- Use `..` for large structs or tuples where only a few fields matter, but avoid ambiguous tuple patterns.
- Use match guards for comparisons against outer variables or boolean conditions that patterns cannot express.
- Be cautious with match guards in exhaustive logic because guard expressions are not checked for exhaustiveness.
- Use `@` when the code needs both a structural/range test and the concrete matched value.
